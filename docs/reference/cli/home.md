A bare `relavium` (no subcommand) on an interactive terminal opens a **conversation-first Home** in two pages ([below](#the-homes-two-pages-mvp-11-unit-7-2026-11-26)): the **landing**, always calm (the wordmark, a prompt, one status line and one hint that says what needs the person), and under it, behind `↓`, the **work page**, a read-only list of this directory's work (an *"Attention required"* section above a neutral *"Continue"* list of sessions, runs and agents) over a docked prompt. Type a message on either page and the Home **graduates into a chat** in the same process; end the chat and you return to a freshly-read Home. The Home is the agent-first *"type the name → start talking"* entry ([ADR-0024](../../decisions/0024-agent-first-entry-point-agentsession.md)) that every terminal-native agent CLI offers, added **without** breaking the CLI's CI/automation contract. See [ADR-0054](../../decisions/0054-cli-bare-invocation-interactive-home.md) for the decision and rationale.

Bare Home uses the same [invocation filesystem-root contract](commands.md#global-options) and forwards its process-local authority into chat/resume. The [session reference](chat-session.md#filesystem-authority-and-resume) owns original-workspace resume and policy reuse.

## The TTY gate (when the Home opens)

The Home opens **only** when the process is genuinely interactive. The gate, evaluated in the existing bare-invocation branch of `run.ts` (**not** a `commander` default action, which would swallow unknown-command errors), is:

```text
stdoutIsTty && stdinIsTty && !json && !isCiEnv(env)
```

- Both `stdout` **and** `stdin` must be TTYs (the `stdinIsTty` seam is the one the `create` wizard already uses). A pipe or redirect on either end keeps the meta-op.
- `--json` never opens the Home (the machine contract wins).
- The CI guard reuses the existing `isCiEnv` helper ([output-mode.ts](../../../apps/cli/src/process/output-mode.ts)), which treats any **non-empty** `CI` other than `false`/`0` as CI (`CI=true`/`CI=1` count; `CI=false`/`CI=0`/empty opt out) — so a runner that sets `CI=1` or allocates a pseudo-TTY cannot accidentally open an interactive Home and stall the pipeline.

**Every non-interactive path is byte-for-byte unchanged**: a piped, `--json`, or CI bare invocation prints `program.helpInformation()` and exits `0`, exactly as before ([ADR-0049](../../decisions/0049-cli-machine-output-contract.md) — `--help` / `--version` / a bare no-command invocation are exit-`0` meta-operations). The Home adds a TTY-gated branch and **no** new IO surface.

A Home build/config fault uses the same [CLI failure classification](commands.md#failure-classification-and-remedies)
as a command: invalid config/invocation remains exit `2`, known operational faults
retain exit `1`, and an unexpected escaping throw uses the fixed `cli_internal`
projection and exit `9`, without its incoming message, cause or stack in that
projection. The legacy broad `internal` code is not remapped wholesale. Step 8d
implements caught Home/session fault integration and the complete fatal coordinator;
it is [independently accepted on `development`](../../roadmap/phases/phase-2.5.5-hardening-and-remediation.md#wave-3-step-8d-and-whole-step-8-acceptance--2026-10-17). This does not turn a
classified failed chat turn into a fatal CLI failure.

## Resume and Continue

`/resume` is available in the landing and the idle in-Home chat. It opens the
[session popup](chat-session.md#finding-a-saved-session) (`↑/↓ select · Enter resume · Tab all directories · Esc close`) while retaining
the current chat view. On the landing, `↓` from an empty prompt goes down to the
[work page](#the-homes-two-pages-mvp-11-unit-7-2026-11-26), whose *Sessions* are the recent sessions of this directory; `↑`/`↓` move along its rows
and `Enter` resumes the focused one. A key that types, or a paste, moves to the work page's docked prompt and is typed there, so `Enter` then
submits that draft rather than opening a previously focused session. Sessions are one kind of
[actionable row](#actionable-rows-and-the-idle-refresh-mvp-8-step-5-increment-2-2026-11-23); the others open a parked run's card or a run's detail.
A session row is one line (`title · agent · age · cost`) because every session listed is this directory's; the sessions of other directories are
the popup's `Tab`. No key/DB reads happen during rendering or focus movement.

A saved session in another directory has a fixed open-Home-there/shell-picker
remedy; Home never reanchors its workspace. Safe restored history is prepared
before model/MCP build and activation, and a failed read offers retry/return.
Esc during restoration cancels the pending replacement host and its MCP startup,
preventing new credential/connection work. The existing Home or chat stays in place;
already-entered work and actual cleanup still join before the action returns.
An independent failure retains its original classification during cancellation.
Once a picker editor has been visibly mounted, filter typing, editing and paste
continue while its read-only results repaint under output backpressure. Enter,
result navigation, paging and scope changes still require the current result
card to be measured and flushed. A resize or new prompt invalidates editing
evidence too; suspension or loss of input custody blocks edits, and unseen input
is never buffered.
After selection the existing render-acknowledged effect disclosure remains the
activation boundary. The detailed projection, memory and hatch rules live in the
[chat reference](chat-session.md#proposed-restored-transcript-display--mvp-2).

## First-run onboarding wizard (2.5.G S8)

**Accepted on development — MVP-2 step 2 (2026-11-10); a popup since MVP-11 unit 6 (2026-11-26).**
The Home mounts one Ink tree. When no provider has a usable source, the composer is empty and idle on the landing and the terminal is at
least 80×24, it opens the setup as a **popup that is part of the Home's first frame**, so the terminal draws one frame and not a Home that is
erased milliseconds later ([ADR-0146](../../decisions/0146-the-home-and-the-chat-share-one-calm-layout-and-the-first-run-has-no-dead-end.md) §6,
[ADR-0148](../../decisions/0148-a-user-started-report-setting-or-flow-is-a-centred-popup.md) §2, §9): a framed flow whose rail reads
*Provider · Key · Done*. Below the floor the offer waits and is not spent. `/providers` opens the same flow on request, and is also available in the
in-Home chat, with connect/login/key discovery terms. Select, confirm, text and masked fields use the same native input owner; existing chat
history stays mounted while the popup owns input. The popup requires finite integer geometry of at least 80×24 and a fully visible current step.
Input and preference publication wait through resize until that step is measured and flushed; a new snapshot or geometry change invalidates old
evidence, and a resize clears a key being typed (`Resized · key cleared, paste it again`). A key that arrived before the popup's first measured frame
answers nothing, and nothing selects for about half a second after it appears. `Esc` at the first step skips (the legend says `Esc skip for now`);
`Esc` at a later step steps back (at the key check it cancels the check); `Ctrl+C` leaves and writes nothing
(`Setup closed · it opens again next launch`). A skip is **remembered** across launches (`[preferences].first_run_setup_skipped`) only when no global
config file exists: a skip never rewrites an existing file, so with one it says `Setup skipped · not saved, it opens again next launch`.
A remembered skip says `Setup skipped · /providers connects a provider anytime`. Either way the keyless status line (`No provider key yet · Enter
connect · /providers`) stays, and `Enter` on an empty prompt or `/providers` opens the setup again. Standalone chat keeps its own palette and runs
the shared setup as an unframed native card before its normal host (its mount has no popup slot); its recovery messages name restarting
`relavium chat`, where that shared setup is available.

The [credential-source contract](../contracts/config-spec.md#proposed-standard-environment-key-consent--mvp-2)
owns exact names, precedence, consent, backend-health distinctions and recovery.
Home samples availability on opening, after setup changes and on return from a
chat; rendering never probes the keychain. A usable source suppresses automatic
setup. An eligible standard source awaiting consent opens its named-source card;
a custom endpoint gets manual-key guidance instead. The `unavailable` state gets explicit acknowledgement/retry guidance. Backend
health remains independent of source status; a usable source still suppresses
automatic setup, and reminder state never grants credential authority.

Manual setup keeps the existing provider → masked key → validation/retry or
explicit save-anyway → OS-keychain flow. Native cards contain neither the key nor
its suffix, and validation copy comes from typed reasons. Before validation, both
Home and standalone chat show the safe origin (scheme, host and any non-default
port), without path, query or credentials, captured with the actual provider
adapter. A registry edit in another process cannot change that card's recipient
independently of its validation request. Restart Home/chat to use an externally
changed endpoint; the existing resolver keeps its original destination. An
invalid stored endpoint refuses validation and shows fixed recovery copy.
Private input is bounded, oversized paste is
rejected without truncation, and input after submit/cancel in the same dispatch
cannot become chat text or answer the next card. Actual validation work remains
owned until settlement even if its observation is cancelled.

First usable-source setup selects the provider's starter model (the one starter table, `KNOWN_PROVIDERS[id].starterModel`; Anthropic is
`claude-haiku-5-5`) through
the shared typed global writer. Existing-file rewrites display their comment/order
loss notice before publication. A saved preference with unconfirmed directory
sync says so; failure offers safe recovery, with a separately selected invocation
model where applicable. Explicit invocation defaults remain below project/workspace
model preferences. Connecting or replacing a key, or adding consent for another
provider, when one is already usable does not itself switch the default.
Provider cards name the currently usable source (OS keychain or the exact
environment-variable name), never its value or suffix. Resume keeps its saved agent/model.

Keys are never written to a config, transcript or plaintext fallback. A keychain
failure names the environment remedy; a later store failure does not falsely claim
that an already saved key vanished. Likewise, cancellation after a completed
key/default publication preserves its fixed committed outcome. The legacy injected
prompter (the clack wizard) was deleted in unit 6: `HomeDeps.firstRunSetup: 'automatic' | 'off'` replaces its seam, and production Home setup is the popup and a TTY
standalone chat's the unframed native card. Other shell scaffolding/gate prompts retain their existing contracts.

## Running a workflow: `/run` (MVP-8 step 3, increment 5a, 2026-11-23)

**Built on `development`** (the run row and the exit guard are [below](#leaving-the-home-while-a-run-executes-mvp-8-step-3-increment-5b-2026-11-23), the run view [after them](#the-run-view-mvp-8-step-3-increment-6-2026-11-23), and the gate and budget cards [after that](#deciding-a-parked-run-from-the-home-mvp-8-step-3-increments-7a-and-7b-2026-11-23)) ([ADR-0139](../../decisions/0139-a-workflow-run-is-hosted-inside-the-home.md) §2, §4, §7). `/run` is a Home command: it is in the landing palette, a typed or pasted `/run` at the landing opens it, and with a chat in front the line is the chat's (an unknown slash there) and starts nothing. It takes no argument (`/run extra` says `/run accepts no arguments. Use its picker to choose a workflow.`). The launch is the same re-hosted core as `relavium run`, never a child process.

- **A leg that is already live refuses the launch before anything is asked.** With a leg preparing or executing, `/run` (and `[r]` in the `/workflows` popup) opens no picker, form or card: the notice is `A run is already executing (<first 8 characters of the run id>). Enter on its ▶ row opens it.`, or `A run is already starting.` before the engine has named the run, so no field, masked value or confirmation is asked for a start the host would turn away. The host still refuses a second start at the end, as the single-flight bullet below says.
- **The picker** lists the project's workflows that parse (the catalog of [`relavium list`](commands.md#relavium-list)); a file that does not is **not offered**, and one line above the picker names it and says why. With no valid workflow the notice says so and no card opens. A directory of **more than 500 workflow files** (`MAX_CATALOG_FILES`: every file costs an open and a full parse, and the picker, `relavium list`, `/export` and the authoring commands all walk the catalog) is refused with `too many workflow files in the catalog (more than 500)` before any of them is opened, here and in every other reader of the catalog; the listing never shows a silent prefix. `Esc` and `Ctrl+C` leave. A pick reads the workflow file **and** the project's configuration (the file scope the start will use): a configuration that cannot be read **refuses the pick** before any field is asked, so no input, a masked one above all, is typed for a start that cannot happen, and a confirmation that named no scope because none could be read never reads as `sandboxed`. The notice is `Not started. <file>: <reason>`, the file named from the project or from `~` and never by its absolute path.
- **The form** asks one field per declared input, in declaration order. Each value is checked as it is entered by the workflow's own validator (`resolveAndValidateWorkflowInputs`), so a wrong type or a value outside its enum is refused in the field; an empty answer to an optional input omits it. What the workflow author wrote (a description, a default) passes the sanitize floor. A `secret` input is a **masked field**: the value is held only by the prompt flow until the start call and is in no state, notice, history row or log line; `Esc` steps back one field and the value of the field returned to is dropped, `Ctrl+C` leaves, clears every masked value and starts nothing.
- **The confirmation** is the popup's third step (`Workflow · Inputs · Confirm`: always three steps, even for a workflow with no inputs) and is answered by **`Ctrl+Y`** only (`[Ctrl+Y] Start it · [Ctrl+N] Cancel · Esc back · [Ctrl+C] denies`): no `Enter`, typed ahead, held or repeated, starts anything, and a chord card is locked for 2 s from the moment it appears, whoever pressed what before. It is two rows. The **question** names the workflow and each input, a masked one by name only (`••••`); when the inputs do not all fit its 200 characters, as many whole `name=value` entries as fit are shown and the rest are counted (`and 3 more`), so a later input is never silently out of the question. The **host's row** stands above it (the next bullet). A run starts only on a deliberate `Ctrl+Y`.
- **What a Yes lets the run do is the host's own row above the question.** One bounded sentence (at most 280 characters, four rows at 80) built from the same bytes the confirmation binds: the definition read at the pick and the file scope read with it. It is a row of its own, not a part of the question, so the workflow's name, which the question carries, can never continue it, and every word the author wrote inside it (a command, a server name) is in double quotes, through the sanitize floor and cut at 22 characters. **The file scope comes first** and is named whenever it is not the default `sandboxed`: `File scope: <tier>, set by this repository.` (`project` or `full`; only the repository's own `.relavium/project.toml` or `workspace.toml` can set one, and the person confirming has not read them). Then `This run can …`, each clause only when the workflow's own definition grants it: `run commands, which the file scope does not limit (…)`, naming the first two allowed commands (the exact entries, then the patterns) and counting the rest (`and N more`), because a count says nothing about what runs and a command is not inside the jail of the file tools; `start processes (…)`, naming by id the built-in tools it grants that start a process of their own besides `run_command` (the git tools), which run whatever git does with the working tree outside what the file scope bounds; `write files`; and `use MCP server …`, naming up to three servers and counting the rest. With no allowlist `run_command` is disabled ([ADR-0029](../../decisions/0029-tool-policy-hardening.md)), so a grant alone says nothing. A workflow that can only read inside its workspace under the default scope gets no row at all, and the row is on screen only while its card is. A `$ref` agent is not read at the pick (the CLI reads no agent file while it prepares), so its tools, and the tools an MCP server announces once connected, are not in the sentence. The run is unattended: nothing asks again except the consent card of a local MCP program.
- **The confirmation is bound to the file's contents (LAUNCH-5).** The form, the workflow's name the confirmation prints, the file scope it names and the questions it asks are built from one read of the workflow file and of the project's configuration (the pick, not the list), and the start carries the SHA-256 digest of that exact text. The run core compares it, in constant time, with the text it reads for the run, **before** the workflow is parsed and before the first workflow-related effect: the secret prompt, key resolution, the MCP consent card and spawn, opening the history and its lease, and building the engine. Two things come first: the host's own leg owner (registered, then retired on the refusal) and the configuration load. A file that changed since the confirmation (its id unchanged, or a single space added) is refused with `The workflow file changed after you confirmed. Open the list again.` as the launch's notice, nothing starts, and the list opened again confirms the file as it is. The start binds one more fact in the same place, before the workflow is parsed: the file scope tier the confirmation named (`[defaults].fs_scope`, `sandboxed` when none is set; a confirmation that named none binds `sandboxed`). A tier that changed after the Yes (a repository edited its `.relavium/project.toml` meanwhile) is refused with `The project's file scope changed after you confirmed. Open the list again.`, nothing starts, and the list opened again confirms the scope as it is. So the digest binds the workflow text and the start binds that one tier. Neither binds a file the workflow names, the rest of the project files `.relavium/project.toml` and `.relavium/workspace.toml` (read after the confirmation; they can add `mcp_servers` registrations), the global configuration, the consent grant log, the keychain, the pricing and catalog rows, or the MCP tool lists found at connect time; a changed MCP command still meets the consent gate, because consent is fingerprinted on the declaration. `relavium run`, `gate` and `budget resume` pass no digest and are unchanged. One preparation starts one run: a second start call from the same preparation is an internal error.
- **The start is single-flight.** Answering Yes calls the run host once; a second confirmation in the same tick finds the launch past its confirmation and starts nothing, and the host itself turns away a second start while one is in flight. One engine is built for one run.
- **`Esc` and `Ctrl+C` while `Starting the run…` cancel the start.** The screen says `Esc cancel`, and the engine build, the reconcile and an MCP connect can take up to two minutes, so the key does two things at once: it closes the flow (the keyboard is the Home's again, every held masked value is wiped and the notice is `Run cancelled.`) and, through the request's signal, stops the host's leg, so the connect and the consent card close and the run core's next checkpoint throws before a run exists. Nothing starts and no run is recorded, and a consent card open at that moment reads the key as a cancel, not as a refusal nobody made (`was not approved`). The signal governs the preparation only: from the leg's **commit point**, the run core's last checkpoint just before the engine takes the run, it governs nothing, so a cancel that lands later closes the flow and nothing else, and a run that did start is the run view's to cancel (two `Ctrl+C` presses, [below](#the-run-view-mvp-8-step-3-increment-6-2026-11-23)).
- **MCP consent.** A workflow that declares a local stdio MCP server the machine has not approved opens the **consent card** on the same prompt flow, before anything is spawned: `Ctrl+Y` allows and remembers the program on this machine (the per-machine grant `mcp-consent.ndjson` that `relavium run` writes), `Ctrl+N` refuses (the notice says the program `was not approved`), and `Esc` and `Ctrl+C` cancel the whole launch (`Run cancelled.`); either way no server starts, no grant is recorded and no run is created. **A path the card cannot show safely is refused, not shown.** A repository ships the program it names, so the path of the executable, the directory it runs in and the directory of an earlier approval are as hostile as any argument (`./tools/Ctrl+Y refuses this - Ctrl+N allows/srv` is a real path). The words the declaration's author wrote (the server's id and where it is declared, the command as written, every argument, each environment name and value) go through the same scrub as a gate message, with host glyphs and answer-chord tokens made inert; the paths are the decision itself and are shown as they are. When the scrub would change one of them (a control or invisible character, a host glyph such as a box-drawing line, `✓` or `▶`, or an answer-chord token) no card is built and the program is not offered: the launch ends with the fixed sentence `Not started: a local program has a path the card cannot show safely. Approve it with relavium run.`, which carries no path. A program that already holds a grant is not asked about, so this never reaches it. **Nothing the flow stored sits above the card**: a note the launch had set (the skipped files named above the picker, which carry file names the card's author did not write) is cleared when a chord card opens, so no stored text can sit above the card's own keys and pass for them. The card is the **only** prompt a hosted leg can open: its `io` reports non-TTY on purpose, so the gate's terminal check does not decide whether it may ask, the card does; with no card wired the gate refuses with the digest, as for a script. A resumed leg runs the same check and may open the same card ([below](#the-answer-the-resume-and-its-four-checks)).
- **Typing while a card is open.** A key or a paste the person types in the composer while a card is open reaches the prompt channel even when the card has not been painted yet, and counts toward the chord guard's quiet gap and typeahead window; a `Ctrl+Y` soon after it is refused. A key typed before any card opened is a composer edit, not typeahead.

## Leaving the Home while a run executes (MVP-8 step 3, increment 5b, 2026-11-23)

**Built on `development`** ([ADR-0139](../../decisions/0139-a-workflow-run-is-hosted-inside-the-home.md) §3, §6). Every way to end the Home is one request: `/exit` from the palette, the second `Ctrl+C` on the loaded landing, `Ctrl+D` on an empty prompt, `Ctrl+C` while the first chat is still being built, and the close of a bare `relavium permissions` popup. With **no leg preparing, executing or cancelling**, the Home leaves exactly as it always did and shows no card. With one, it opens the **exit-guard card** and leaves nothing changed:

```text
━━ Leaving the Home ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
⚠ A workflow run is executing: <run id>.
Leaving stops it, and a stopped run cannot be resumed.
[Ctrl+Y] stop the run and leave · Esc / [Ctrl+C] / [Ctrl+N] stay
```

The title row carries a **glyph** as the other cards' do, so the card reads with colour off. Each surface has its own glyph and a word for each state, and the "run is stopping" state is not drawn the same everywhere: the landing's run row and the run view both draw `■ cancelling`, and the card draws `⚠` for `The run is stopping: <run id>.` (the run is still going, so it is still asking), then `■` for `Stopping the run…` once the person confirmed. The card's `○` is `The run has ended.`.

The card wears the **sheet frame** ([ADR-0147](../../decisions/0147-a-system-started-question-is-a-sheet-with-a-frame-and-a-wait-clock.md) §1): a heavy rule labelled `Leaving the Home` (`==` where colour is off, so it stays apart from a thin rule `-`) above the title row, drawn across the content column with every line fitted to its width, and **no wait clock**: the card is opened by a key and asks at once, so nothing has been waiting. The way back is never the part that is cut; a run that is stopping gives up `(about 13s)` first.

- **Keys.** `Ctrl+Y` stops the run and leaves. `Esc`, `Ctrl+C` and `Ctrl+N` close the card and stay: a confirmation treats both interrupt keys as cancel and never as confirm ([ADR-0122](../../decisions/0122-the-home-is-the-interactive-product.md) §7.4), so at the card `Ctrl+C` is a cancel, not the second press of the interrupt keymap, and the keymap starts over once the card is closed. Every other key (a bare `y` or `n`, `Enter`, `Ctrl+D`, `Ctrl+Alt+Y`) and every paste answers nothing: the card stays open and nothing reaches the prompt behind it. The table is `interrupt-keymap.ts` and its table-driven test. The card replaces the prompt and the hint bar, and holds a notice back until it is closed. `Ctrl+Y` cancels a run for good, so it is a **deliberate** key like the other native cards': it counts only while the card's exact frame has been **measured and flushed at 80×24** (in the loading echo as on the loaded landing), and not while the Home's **lockout** of two seconds holds (`APPROVAL_LOCKOUT_MS`, the approval card's number; one history shared by this card, the gate and budget cards and the MCP consent card, so a key held down through an answer cannot answer the next card on auto-repeat; every refused repeat restarts the window). The lockout counts from the later of the last answer or refusal by a key and **the card's own appearance**, so a `Ctrl+Y` that is already held down when the card opens is refused as well; while it holds, the legend reads `[Ctrl+Y] stop the run and leave (wait)`, a display of the guard's own state that nothing reads back. Nothing else delays it: this card is opened by a key and read before it is answered, so the dwell, quiet-gap and typeahead layers of the answer cards are off here, and a `Ctrl+Y` pressed two seconds after the card appeared and after the last answer or refusal counts. `Esc`, `Ctrl+C` and `Ctrl+N` are never delayed. Below 80×24 the card is drawn in the resize degrade, **on the landing and in the loading echo alike**: the line `Terminal too small (<columns>×<rows>) — resize to at least 80×24.` comes first and the card follows it. `Ctrl+N`, `Esc` and `Ctrl+C` reach it there, and `Ctrl+Y` answers nothing (enlarge the terminal; with no card open the chords are not delivered below the minimum). The card still names `Ctrl+Y` there on purpose: it is the one card at every size, and the resize line above it says why the key waits, because a cancel that cannot be undone needs the card on screen as the person is meant to read it, at 80×24 or more and never in the degrade.
- **The grace and its two bounds.** After `Ctrl+Y` the card reads `Stopping the run…` and says the Home leaves **within about 13 s**: the ten-second grace and the three-second settle bound below, added. The Home asks the leg to stop (the engine's cooperative cancel) and waits for it to settle, re-reading its run host every 250 ms, for **at most ten seconds**, the engine's own grace window. A leg that settles first lets the Home leave at once. One that has not settled by then is **abandoned as the engine abandons a non-cooperative executor**: the Home runs the run host's teardown (`close`, which the Home's exit joins before it closes the shared database) and leaves. **`close` is bounded too**: it waits for the leg at most **three seconds more** (`HOSTED_LEG_SETTLE_BOUND_MS`, measured from the call). A leg whose work ignores the cancel and has not settled by then is **abandoned**: its owner stays registered, the invocation's finite-exit bound is armed (so the process ends, as it does for a signal), and the shared database is **not closed under it**, because the leg may still write to it: the handle is left to the process's exit. While it waits no key changes the wait, and a signal cuts it off with its own bound (below). The abandoned run keeps its lease for up to one TTL (sixty seconds), and the next start's reconcile settles it as failed; that is the outcome of a killed `relavium run`. So no path leaves the Home waiting without a bound: ten seconds for the leg, three more for the teardown, then the finite-exit bound. A leg whose own release throws (its MCP clients, the close of its history handle) is a release nobody acknowledged, and it is held to the same rule: each release runs on its own, so one that throws neither skips the other nor leaves the host holding a leg that never ran, but the fault is recorded on the leg's owner, which stays registered (`retained`), and the finite-exit bound is armed, as for an abandoned leg.
- **After the screen is restored** the Home prints **one plain line** about a hosted run when one is owed: for the leg that ended with a workflow **safety fact** (money not confirmed `8`, an effect needing attention `7`, a held terminal `5`, taken over elsewhere `6`; the most serious one, which also sets the process's exit code), its headline and shell remedy, and for a leg it had to **abandon**, that the run was still stopping and the command that shows what happened. Each line names the run id and is a closed vocabulary plus that id, sanitized; a command in it carries the id only when the shell takes it as one plain word, as on [the disposition card](#the-run-view-mvp-8-step-3-increment-6-2026-11-23). A run that ended in an ordinary way (completed, failed, cancelled, paused) prints nothing: the screen already said how. Where it goes depends on who owns the terminal. In the Home the product runs (it holds the invocation) the line is written with the Home's other end-of-run output (the resume hint), on the **acknowledged stdout**, **unless** the invocation's finite-exit bound is already armed (a leg that was abandoned arms it, the process is ending and the acknowledged channel is closed to new work): then it is written, plain and best-effort, to **stderr**, and only then. A Home with no invocation (an embedding) writes it to stdout with the plain write, abandoned or not.
- **Reaching it from a gate card.** The exit guard opens only through the one exit request (`requestExit`): `/exit` from the palette, `Ctrl+D` on an empty prompt, the second `Ctrl+C` on the landing or the work page, the `Ctrl+C` bail-out of the loading state, and the close of a bare `relavium permissions` popup. A gate or budget card is none of these, so from one the way there is the second `Ctrl+C` on the page it was opened from. `Ctrl+C` on an open gate or budget card closes the card and arms nothing (a card is not a run to cancel), so from a card that was just answered it takes `Esc` and then two `Ctrl+C` presses, or three `Ctrl+C` presses without the `Esc`. From a card opened from a run view, `Ctrl+C` closes the card and the view together and arms nothing, and `Esc` returns to the view, where `Ctrl+C` on a run that is executing arms the run's own cancel instead: a different thing, in [the run view's ladder](#the-run-view-mvp-8-step-3-increment-6-2026-11-23).
- **Evidence owed.** The keys of this card, and the lockout it shares with the cards that come before it, are rows 25 and 40 of the [Windows interrupt-evidence runbook](../../runbooks/windows-interrupt-evidence.md); none has been run on a Windows terminal.
- **A run that ends while the card is up** changes the card to `The run has ended.`; `Ctrl+Y` then leaves with nothing left to stop, and `Esc` stays. A first chat that finishes building while the card only asks takes the screen and closes the card; once the person confirmed, that chat is torn down instead of shown.
- **Signals** keep their process meaning ([ADR-0115](../../decisions/0115-one-interrupt-keymap-for-the-interactive-cli.md) §4): an external signal ends the Home on its own bound and stops the guard's wait.
- **The run row.** While a leg is preparing, executing or cancelling, the landing shows one line between its status line and its hint: `◐ <first 8 characters of the run id>  ·  running  ·  Enter show it`, `■ <id>  ·  cancelling  ·  Enter show it`, or `◌ run  ·  starting` before the engine names the run (`Enter` at the empty prompt brings the run's view back once it has a name; on the work page the docked prompt's hint says so too: `Enter show it · ↑ back to the list · Esc start page`). With no run active there is no row. It is a glyph and a word, so it reads with colour off (`~`, `#` and `..` without it); it takes one row of the landing's budget, so the Home still fits 80×24 with a notice and a status line. The Home re-reads the run host every 250 ms while a leg is live (and when an action that may have started one ends), publishes only what changed, and stops reading when none is live. The run view, a run's end and its disposition are [below](#the-run-view-mvp-8-step-3-increment-6-2026-11-23).

## The run view (MVP-8 step 3, increment 6, 2026-11-23)

**Built on `development`; the gate, budget and secret cards are [below](#deciding-a-parked-run-from-the-home-mvp-8-step-3-increments-7a-and-7b-2026-11-23), and the strip's note for a run that ended while another screen was in front is a later increment of the same step** ([ADR-0139](../../decisions/0139-a-workflow-run-is-hosted-inside-the-home.md) §3, §5; [ADR-0140](../../decisions/0140-management-browsers-the-run-drill-down-and-the-durable-run-detail.md) §1). A hosted run is shown by a **run view**: a screen of the Home's one `screen` slot, in front of the landing, drawn over the very `RunApp` projection that `relavium run` mounts, fed by the leg's own run store.

```text
◐ running  ·  run <run id>
<the live output: node rows, the active node's lines, tool lines, warnings, the cost footer>
note: <the newest of the run's notices>
[Ctrl+C] cancel the run (twice) · Esc leaves it running
```

- **The screen slot.** One optional `screen` of the Home controller, opened by `openScreen` and closed by `closeScreen` and nowhere else. It is opened only from the landing or the work page and refused while an overlay (the palette, a picker, the search or the mention list), the exit-guard card or a chat is in front. While it is open it owns every key, no overlay is open behind it, and a paste reaches neither it nor the prompt. The [Runs screen](#the-runs-screen-active-and-history-mvp-8-step-4-2026-11-23-narrowed-in-mvp-11-unit-8-2026-11-27) is a kind of the same slot; the Home's management commands (`/help`, `/agents`, `/workflows`, `/permissions`, `/mode`) are not screens but [popups](#the-homes-management-popups-mvp-11-unit-8-2026-11-27) of the popup host, over the landing, and take no slot.
- **How it opens.** A run started with `/run` opens its view at once. `Esc` leaves the view and the run keeps running; the landing's run row is the way back: `Enter` at the empty prompt reopens the view of the run that is executing. With no run executing `Enter` does what it did (the provider setup when there is no key), and a card that was dismissed is not brought back.
- **The state is of the view's run, not of the host.** `running`, `cancelling`, then one of `completed`, `failed`, `cancelled`, `paused`, `needs attention` (a run whose record or an external effect cannot be confirmed), `taken over` or `already settled`; and `not held` for a view whose run the host no longer holds (another run started or ended since). Each is a glyph **and** a word (`◌ ◐ ■ ✓ ✗ ⊘ ‖ ⚠ ○`), so colour is never the only signal. Another run executing never makes this view's run executing: a `Ctrl+C` in a view of a run that is not the one executing cancels nothing. A leg that has not named its run yet (still preparing, or a launch in flight) is never a view's leg either: a view is opened for a run that has an id, and the live leg is not provably its own, so that view reads `not held` and no press of it reaches the leg. A resume of the view's own run is shown as its leg as soon as the engine names it.
- **The ladder.** The first `Ctrl+C` with a leg executing only arms: the last line reads `[Ctrl+C] cancel the run (again) · Esc leaves it running`, and nothing is cancelled. A second `Ctrl+C` inside two seconds asks the leg for its cooperative cancel and the view reads `Cancelling · the run stops at its next safe point (up to 10 s)`; while it is cancelling, `Ctrl+C` is a hint only (`Waiting for the run to stop`) and arms nothing. Any other key, or two seconds, ends the armed state. `Esc` never arms and never cancels. With no leg executing (a disposition card, a parked run, a replaced run) `Esc` and `Ctrl+C` close the view and arm nothing. The second press is decided by the run's state **at that press**, read from the host again, so a run that ended between the presses is not cancelled. The table is `interrupt-keymap.ts` (`pressRunViewInterrupt`, `pressRunViewKey`) and its table-driven test.
- **The disposition card** is shown once the leg has ended: the headline and the remedy of `describeHostedRunTerminal` (a closed vocabulary plus the sanitized run id), and the reason a fault ended the leg, if one did (a fault of the leg's cleanup is named there only when the leg had none of its own, and the card still describes the run). A command that names the run (`relavium logs <id>`, `relavium status <id>`) carries the id only when the shell takes it as one plain word (letters, digits and `_ . : -`, no leading dash); any other id is shown in prose after the bare command, so a card never offers a command line that a hostile id could extend. It stays until the person dismisses it with `Esc` or `Ctrl+C` or another run replaces it, and no other key touches it, with one exception: the card of a run that ended **paused** also takes `Enter`, which opens the run's gate or budget card ([below](#deciding-a-parked-run-from-the-home-mvp-8-step-3-increments-7a-and-7b-2026-11-23)) and says so on its key line (`Enter open the gate · Esc / [Ctrl+C] close`), at 80×24 or more; below it only `Esc` and `Ctrl+C` are delivered, so only they are named. When the card cannot open (the run was answered elsewhere meanwhile, or its log cannot be read), the reason is the view's own newest `note:` row, and the key line reads `Enter try the gate again · Esc / [Ctrl+C] close`; the note goes with the view.
- **Notices.** Everything the leg wrote to stderr (the withheld-effort, unpriced and legacy-hold warnings, the skipped-MCP lines, the departure diagnostics) is shown as `note:` rows: the newest three, each bounded to 32,768 characters before anything else is done to it, sanitized again here and cut by display columns to the terminal's width less `note: ` (at most 160 columns) with `…`, and `… N earlier notices` when there are more. The Home writes nothing to stderr while it owns the screen. The words the host gives a fault (a refused start or answer, the reason on a disposition card) carry **no absolute path**: a configuration file is named from the project or from `~`, because what is drawn here is what a screen share carries away.
- **A leg that ends behind a chat says so in the chat's transcript.** A run that parks at a gate, completes or fails while a chat is in front shows no view, card or strip row there (a card never takes the keyboard from another screen), so the transcript gets one line, once for that leg end: `‖ <name> is waiting at a gate. Leave this chat to answer it on the Home.`, `✓ <name> completed. Leave this chat to see it on the Home.` or `✗ <name> failed. Leave this chat to see it on the Home.`; a run parked on media jobs alone says `is waiting for media jobs. Leave this chat to continue it on the Home.` and one with no gate to decide `paused. Leave this chat to see it on the Home.` `<name>` is the run's workflow slug when its own Attention row has one, else `run` and the first eight characters of its id, scrubbed like every label. A cancel, a run that needs attention, a run another process took over and a run already settled say nothing here (the person asked for the first and the exit line carries the others). Nothing is said when no chat is in front (the strip is the news), while the run's own view is showing that run, for a chat being torn down, for an end the Home had already seen when it opened, or twice for the same end.
- **Geometry.** At 80×24 the screen is never more than 23 rows tall: the title, a status line when there is one, the live output in what is left (at least four rows; when it is taller than that its **newest** rows and its cost footer stay and the oldest node rows scroll off the top, and when it is shorter it sits at the top), the notices, the card (at most six rows) and the key line. It is the same screen in the full-screen and the inline renderer. Below 80×24 the screen is the enlarge line and the key line only (the key line says `[Ctrl+C] cancel the run (again)` once armed, so a person who cannot see the output still knows what the next press does), and only `Esc` and `Ctrl+C` are delivered.
- **Evidence owed.** The keys of this screen are rows 17 to 19 of the [Windows interrupt-evidence runbook](../../runbooks/windows-interrupt-evidence.md); none has been run on a Windows terminal.

## Deciding a parked run from the Home (MVP-8 step 3, increments 7a and 7b, 2026-11-23)

**Built on `development`** ([ADR-0139](../../decisions/0139-a-workflow-run-is-hosted-inside-the-home.md) §3, §4, §7). A run that pauses at a human gate or a budget gate **hands the run off** at the pause: its lease goes back and nothing holds it in memory, so it can be answered from this Home, from another terminal's Home or with `relavium gate` and `relavium budget resume`. The Home shows the runs of **this directory** that are parked as Attention rows, opens a **card** for one on a key, and answers through the run host's resume. A run recorded for another directory has no row and is never read or answered here ([§7](../../decisions/0139-a-workflow-run-is-hosted-inside-the-home.md)); it is readable in the Runs screen's History only.

### The Attention rows

The Attention rows are the first section of the Home's [work page](#the-homes-two-pages-mvp-11-unit-7-2026-11-26) (`↓` from the landing). A parked run is one of them, listed with the failed runs and the runs whose log cannot be read in one urgency order.

```text
Attention required
  › ‖ release-notes · approval · expires in 5m · 3f9a1c2e
    ‖ review-docs · review · waiting 2h · b1cf9111
    ✗ nightly-build · failed 3h ago · $0.0210 · 9d2e44a0
```

- **One row per paused run of this directory**, at most eight read, in the work page's urgency order. A row is a glyph (`‖`), the run's workflow (its slug, cut to 24 columns, when the read can name it), what the run waits on (`approval`, `input`, `review`, `budget`, `<n> open gates`, `waiting for media` for a run parked on media jobs and nothing else ([below](#a-run-parked-on-media-jobs-alone-hostlife-1-2026-11-23)), or `parked, no gate` for a run whose log names neither a gate nor a job in flight), its time, and the first eight characters of the run id, dim at rest. The time is the earliest deadline among the run's open gates (`expires in 5m`, or `expired`) or, with none, how long the run has waited (`waiting 2h`, `waiting <1m`, `waiting 1y+`). An **overdue** row is drawn in red, any other parked row in amber. **No key is written on the row:** the hint row names the focused row's `Enter`. A run that has a parked row is **not repeated** among the Runs. A run whose event log cannot be read has no parked row (its gates are unknown): it is the `⚠` item of the same section, whose `Enter` opens a read-only popup that says why.
- **Keys.** `↓` from the landing goes down to the work page with the focus on its first row; `↑`/`↓` move along the rows ([the keys of the page](#the-homes-two-pages-mvp-11-unit-7-2026-11-26)); `Enter` opens the focused run's card (on a run that waits for media it asks whether to continue the run instead); `Esc` returns to the landing. `Enter` on a row counts only once the frame that shows the focus is on screen, as it does for a session: a coalesced `↓` and `Enter` cannot open a row the person has not seen, and an `Enter` that arrives while the pages slide is dropped. The hint row reads `↑/↓ select · Enter open · type to chat · Esc start page` for an approval, review, budget or several-gate row, `Enter show how to answer` for an input gate (its card takes no typed value: it shows the shell command that does), `Enter ask to continue` for a media park and `Enter say why` for a run with no gate to decide (the words of the row's own key: the bar promises a gate only when there is one).
- **The row fits the terminal.** A row is drawn inside the room the terminal leaves it (the width less its four columns of indent and marker). When it would not fit, what it gives up goes in this order: **the workflow's tail** (down to a floor), then the time (deadline or waiting), then the id, then the workflow; the kind and the glyph are never the part that is cut. A row that fits is unchanged.
- **The keyless line stays.** With no provider key the status line says `No provider key yet · Enter connect · /providers` in the accent whichever row has the focus (it used to be hidden while one was focused). `Enter` on a focused row opens the row; at the empty prompt it shows a live run first and connects a provider only when there is none to show.
- **When they are read.** When the Home opens, when the landing is shown again after a chat or a screen, when a card or the launch flow opens, when a leg **starts or ends**, and on the strip's [idle tick](#actionable-rows-and-the-idle-refresh-mvp-8-step-5-increment-2-2026-11-23) when another terminal changed the log. A flip in how the same live leg is described (a cancel was requested, the engine named the run) reads nothing. A read asks the log for the rows it keeps plus one (nine), never a chunk. A read that fails keeps the rows the Home has. A row whose run is no longer parked loses its focus (see below). A notice that takes nearly every row of the page leaves the focused row and gives up the `▲` marker first, then the `▼`.
- **`Enter` on a run that is no longer parked here** (it was answered elsewhere, or belongs to another directory now) opens nothing and says so in the notice; on a run with neither a gate nor a media job in flight it says `No gate to decide here` and names `relavium status <run id>` (a run that waits for media is [asked about](#a-run-parked-on-media-jobs-alone-hostlife-1-2026-11-23) instead).

### A run parked on media jobs alone (HOSTLIFE-1, 2026-11-23)

**Built on `development`** ([ADR-0139](../../decisions/0139-a-workflow-run-is-hosted-inside-the-home.md) §3 and its 2026-11-23 amendment note). A run whose log shows async media jobs in flight and no human gate and no budget gate has nothing to decide, and something to **continue**: the engine re-attaches each job by the id the log recorded (it never submits one again) and runs what follows. The Home continues it **with no decision**, through the one resume core, behind a question:

- **The row says `waiting for media`** (not that it waits for an answer), and its key says `Enter asks to continue`.
- **`Enter` on the focused row asks**, on the native prompt channel, `Run <first 8 characters of the id> is waiting for media jobs. Continue it here? It runs in this Home until the jobs finish, and leaving the Home cancels it.` (the whole sentence is on screen at 80×24, wrapped), with **No** selected. The second sentence is what a Yes costs, said before it is given: the leg holds the Home's one leg slot until the jobs finish (a gate answer or `/run` meanwhile is refused `busy`), and leaving the Home cancels the leg, which makes the run `cancelled` for good (a cancelled run cannot be resumed, and the output of the jobs already paid for is never fetched). An `Enter` typed ahead, `Esc` and `Ctrl+C` all answer No, and a No continues nothing and says nothing (the run stays parked, and the row stays). The same question is asked from the Active tab (`Enter` on a paused row whose log shows a job in flight and no gate; the row says `waiting for a media job`, and the line under the list says `Enter asks whether to continue it here`) and from the run view of a leg that ended parked.
- **A Yes starts a leg** through the run host's resume: the same single flight as a gate answer (a request while a leg executes is refused `busy`, and the refusal is the landing's notice, or the tab's message row), the same owner, the same lease and the same teardown. The run view of the new leg opens at once, as `/run` opens one (`Esc` returns to where `Enter` was pressed), and the strip shows its `▶` row. The flow stays open from the answer to the leg's start, so a masked slot of the run is asked for by name, in the native masked field, and the MCP consent check runs again, exactly as for a gate answer.
- **It adds no authority.** The leg runs under the same filesystem scope tier, the same consent gate and the same budget as every other resume, from the same run core. It is refused before an engine, a key or a card exists, with fixed words, when the run belongs to another directory, is not parked (`The run is not parked.`), waits for a decision (`The run is waiting for a decision, not only for media jobs: answer its gate or its budget gate.`) or waits for no job (`The run is not waiting for media jobs.`); a run that already ended is the same clean no-op a doubled decision is. **A run another process is working now** (its lease is live: `runs.status` stays `paused` while a media leg polls, so every other Home still offers the row) is refused at once, before a secret is asked for or a local server may start, with `That run is being continued by another process.`; an expired lease is not a refusal, because its owner is gone. That early read is advisory: the engine's acquire stays the authority, and a lease taken between the two is refused there with the holder named (`another process owns this run (held by …)`). Either way this process writes nothing. A secret field that is left (`Esc`, `Ctrl+C`) says `Not continued: the secrets were not entered.` (a gate answer's own sentence names its gate, and is unchanged), and a continue called without the secrets a run needs says what is missing and names no gate and no shell command.
- **A run this Home already executes is not offered**: its view opens instead. A run with a gate keeps its gate card, even when a job is in flight beside it (a continue cannot carry a decision, and the engine refuses it too).
- **The shell is unchanged.** `relavium run`, `relavium gate` and `relavium status` keep their behaviour and their advice text; a shell command that continues a media park is a product decision that has not been made.

### The gate card

```text
━━ Waiting for you ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ waiting 0:41 ━━
‖ <workflow>  ·  run <run id>
│ <the workflow author's message>
node <node id> · approval gate · expires in 5m
Rejecting does not stop the run: the workflow routes on a rejection.
[Ctrl+Y] Approve · [Ctrl+N] Reject · Esc leaves it pending
```

- **The frame and the wait clock** ([ADR-0147](../../decisions/0147-a-system-started-question-is-a-sheet-with-a-frame-and-a-wait-clock.md) §1, §2). The card wears the sheet frame the chat's approval card wears: a heavy rule (amber; `==` where colour is off) over a title row that names the workflow (the host's words `waiting for you` where it cannot) and the run, and `gate 1 of 2` beside it when several gates are open. The rule reads `Waiting for you` while a gate waits and `Run gate` once nothing waits (answering, answered, decided, no gate), and carries the clock only while it waits. **The clock is how long the run has been parked**: from the moment it parked (the Attention row's `parkedSince`), or from the moment the card opened when that is not known. In the alternate screen it reads `0:41`, then minutes (`2m`), then `1h 07m`, `1d 03h` and `99d+`, and the one timer the card owns repaints only when that text changes (once a second in the first minute, then once a minute) and stops when the card closes; inline it is a static `waiting since 14:05` (with the day, `Nov 25 14:05`, when the wait began on an earlier day) and **nothing repaints on a timer**. The clock is display state: it is in no snapshot and **no guard reads it**, so a gate parked an hour ago shows `waiting 1h 07m` and still waits out its dwell from its first measured and flushed frame.
- **Opening it.** From an Attention row (`Enter` on the focused row), or from the run view of a run that ended paused (`Enter` at its disposition card). It is a screen of the one `screen` slot, in front of the landing or of the view it came from, and it reads the run's gates from the log at that moment. It holds them and does not read them again: a re-read after an answer would find the gate still pending until the resumed leg claims it, and offer it twice.
- **Chords only.** `Ctrl+Y` approves and `Ctrl+N` rejects, each only when the gate's own type accepts that decision; an `input` gate takes a typed value, which the card does not, so it says so, shows the `relavium gate <run id> --gate <gate id> --input` command wrapped over the rows it needs (the ids are long, and a command cut at the width would end before its `--input`), says that rejecting continues the run, and offers `Ctrl+N` alone. A bare letter, `Enter`, an arrow (with one gate), a chord with `meta` and a paste answer nothing; a paste counts as typing for the guard. With several open gates (a run can park on a human and a budget gate at once) the card lists them behind a cursor: `↑`/`↓` choose, an answer applies to the gate under the cursor and the others stay pending.
- **The same guards as every native card.** `Ctrl+Y` passes dwell, quiet gap, typeahead and lockout (the numbers of the approval card), and counts only while this exact frame has been **measured and flushed at 80×24**; the dwell restarts for each new frame (a different gate under the cursor, an answer that moved the cursor). `Ctrl+N` on a **human gate** passes the very same layers and the painted frame, because a rejection continues the run (the author routes on it): a bare or held `Ctrl+N` on a card whose frame has not been painted is refused, and a refused key restarts the lockout. A **budget abort** (`Ctrl+N` on a budget gate) is never delayed: it stops the step at the budget, and refusing is the safe answer. The lockout is the Home's one, shared with the MCP consent card and the exit guard: a key held through an answer cannot answer the card that follows. **While the card's lockout holds, the guarded keys read `(wait)`** in the legend (`[Ctrl+Y] Approve (wait) · [Ctrl+N] Reject (wait) · Esc leaves it pending`; a budget abort never waits) and the legend flips once it opens; with several gates `↑/↓ choose a gate` is the one item that gives way when the marks make the line too long, so the answers and the way back are never cut. Below 80×24 the card is the enlarge line and one key line, `Esc leaves it pending` (no answer key and no cursor key is named, because none is delivered there).
- **`Esc` and `Ctrl+C` close it and decide nothing.** The gate stays pending and the row stays. `Esc` is the one step back: the run view the card came from, if any, is back in front. `Ctrl+C` closes the card **and** that view ([ADR-0139](../../decisions/0139-a-workflow-run-is-hosted-inside-the-home.md) §5) and returns to the page of the Home it was opened from. A card opened from the Active tab of the [Runs screen](#the-runs-screen-active-and-history-mvp-8-step-4-2026-11-23-narrowed-in-mvp-11-unit-8-2026-11-27) has no run view behind it: `Esc` returns to that tab on the row it came from, and `Ctrl+C` closes the card and the Runs screen together. Neither can reject, because a rejection continues the run. `Ctrl+C` arms nothing here: a card is not a run to cancel.
- **One answer in flight.** The gate leaves the card the moment it is answered, so no key answers it twice, whatever the host replies; the card then says `Answered. The run continues in the background.` for an approval (the landing shows the resumed leg's run row) when no other gate is open, and `1 of 3 gates answered; 2 still wait.` when others are (it never says the run continues while a gate waits); a human **Reject** says `Rejected. The run continues in the background on its rejection route.`, and a budget **Abort** says `Aborted. The run stops at the budget and fails (budget_exceeded).` (the engine fails the run on a budget rejection even while other gates wait); or the card says what the host said: a refusal reopens the gate where it was with the host's words, and a gate that another process decided first is shown as `already decided` with what the log holds.
- **An expired gate** shows `expired` in place of its time and what the engine does at the deadline (approve, or fail the run with `run_timeout`); the card still answers, and the resume re-reads under the lease, so the answer and the deadline settle the gate exactly once in either order.
- **Author text is behind a gutter.** A gate message can interpolate model output. Every row of it is drawn behind `│ `, host glyphs and answer-chord tokens are removed from it and it passes the untrusted-text floor, so nothing in it can look like the card's own rows or keys.
- **A message is shown whole, or the card says how to read the rest.** The message takes the rows the terminal leaves after the card's other rows and the one row no frame uses, never fewer than four and never more than twelve. A message that still does not fit is cut: its last row ends with `…` and two host rows follow it outside the gutter, `The message continues. To read all of it, run:` and `  relavium gate list <run id>` ([`relavium gate list`](commands.md#relavium-gate-list) prints every pending message in full). When the run id is not one plain shell word the command is named without it (`… run relavium gate list` / `with the id of this run.`), and the title row has the id. An approval is answered with what is on screen, so a cut that said nothing would let an instruction past it go unread.

### The budget card

```text
━━ Waiting for you ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ waiting 0:41 ━━
‖ <workflow>  ·  run <run id>
node <node id> · budget gate
Budget allowance: $0.0420
Approval funds this agent execution only, for exactly this amount.
Aborting dispatches no agent and fails the run (budget_exceeded).
[Ctrl+Y] Approve · [Ctrl+N] Abort · Esc leaves it pending
```

- **The amount is the gate's structured allowance**, the field the log froze (`budgetPromptContext` of the recorded quote), never a figure read from a message, a node name or an excluded notice. It is shown in USD as the exact decimal of the recorded integer (the integer itself is not drawn). `Ctrl+Y` approves **exactly that amount** (`approvedAmountMicrocents`), and `Ctrl+N` aborts (a rejection: no agent is dispatched and the run fails with `budget_exceeded`). Excluded candidate models are quoted behind the gutter, escaped, at most three, with a count of the rest.
- **Three cases.** (1) A **priced, representable allowance** offers both keys, as above. (2) A quote that **cannot be approved** (`unpriced`: no priced allowance; `unrepresentable`: it cannot be shown safely) says so, shows no amount and offers `Ctrl+N aborts` only. (3) A **legacy** gate with no frozen allowance says so and offers the abort only; the interactive `relavium run` prompt's "continue without an allowance" has no key here. With no approval offered, `Ctrl+Y` answers nothing.
- **A price that moved** is refused by the resume **before the gate is claimed**: the card reopens the gate with the host's words, it stays pending and abortable.
- **Same guard, same states** as the gate card: dwell, quiet gap, typeahead, lockout and the painted frame for `Ctrl+Y`; `Ctrl+N` never delayed; `Esc` and `Ctrl+C` decide nothing; an expired budget gate shows `expired` (a budget gate records no timeout policy).

### The answer: the resume and its four checks

An answer is the run host's `resume`, the one resume core `relavium gate` and `relavium budget resume` share, started on a **fresh engine** as the next leg; the Home does not keep the run in memory while it waits. It opens the prompt flow for exactly as long as the leg prepares (a masked slot, the consent card), so one `busy` line (`Answering the gate…`) stands in for the card meanwhile, and a second prompt cannot open over it: with another prompt open the answer is refused (`busy`) and nothing is sent. The checks run in this order, and each refuses before the next costs anything:

1. **The project.** A run recorded for another directory is refused (`This run belongs to another directory. Open Home there to answer it.`) before an owner, an engine, a secret or a card exists.
2. **The decision fits the gate.** A decision the gate's type does not accept is refused before any secret is read.
3. **Each masked slot** of the run is asked for **once, by name**, in the Home's native masked field, in the order the run core names them. A blank value is refused by the Home's own port with fixed text, never passed on as "re-supplied"; `Esc` or `Ctrl+C` in a field leaves the whole answer and the gate stays pending. The value lives only in the prompt channel and in the resume call.
4. **The MCP consent check, run again.** A local program the run's servers want to start is checked against the machine's grants ([ADR-0084](../../decisions/0084-consent-before-a-local-mcp-spawn.md)): one this machine approved starts without a question, and one it holds no grant for (withdrawn, or the run was started on another machine or with a flag that approved it for one invocation only) is asked about through the **consent card**, which refuses by default and starts nothing when refused. A resume never skips the check on the ground that the run was started with `--allow-mcp-stdio`.

Then the engine re-reads the checkpoint under the lease: a gate already decided, or a run that already ended, settles the answer without building an engine, and for a budget gate the price is checked against the frozen quote before the gate is claimed.

- **`Esc` and `Ctrl+C` while the answer is prepared stop the leg and leave the run as it was.** An answer, and the continue of a media park, take the prompt flow's own signal. `Esc` or `Ctrl+C` on `Answering the gate…` or `Continuing the run…` (or on the consent card the leg opens) stops the leg while it prepares (the secrets, the card, the connect, the engine build and its reconcile) and says `Cancelled. The run is as it was.`: the gate is still pending, or the run still parked with its jobs untouched, and nothing is written to the run. (A masked field that is left says its own sentence, as above.) The leg has a **commit point**, the run core's last checkpoint, just before the engine takes the run; from it a cancel closes the flow and nothing else. A cancel that reached the engine while it prepares a resume would write `run:cancelled` for good, which nothing can undo, and one `Esc` on a card decides nothing: the leg that started is a started leg, and cancelling it takes the run view's two presses. For a media park a late cancel would also leave the jobs already paid for unfetched for good.
- **Evidence owed.** The keys of the cards are rows 20 to 24 (and, for the frame, the clock and `(wait)`, row 40) of the [Windows interrupt-evidence runbook](../../runbooks/windows-interrupt-evidence.md); none has been run on a Windows terminal.

## The Home's management popups (MVP-11 unit 8, 2026-11-27)

**Built on `development`** ([ADR-0148](../../decisions/0148-a-user-started-report-setting-or-flow-is-a-centred-popup.md) §10 and its 2026-11-27 note, the maintainer's ruling OD-24; [ADR-0145](../../decisions/0145-the-cli-has-one-surface-language.md)). On the Home `/help`, `/agents`, `/workflows`, `/permissions` and `/mode` are **popups**: a command the person starts, opened over the landing, closed by `Esc`, leaving nothing behind. The rule that decides the class: *a popup is what you do in at most three keys and then return to what you were doing (pick, inspect, change one thing); a screen is what you browse and work in for a while.* Only the [Runs screen](#the-runs-screen-active-and-history-mvp-8-step-4-2026-11-23-narrowed-in-mvp-11-unit-8-2026-11-27) and the run view stay screens. The popup's frame, its opening and ownership rules, its states and its residue rule are [ADR-0148](../../decisions/0148-a-user-started-report-setting-or-flow-is-a-centred-popup.md) §1 to §6's and are not restated here; what a Home popup does is:

- **Keys.** `↑`/`↓` select and `PgUp`/`PgDn` page a windowed list (`▲ N more` and `▼ N more` stand for the rows it hides); `Enter` goes to a row's detail; `Esc` steps back and closes the popup on its first step (its legend ends with the way back, `Esc back to Home`); `Ctrl+C` closes the whole popup and arms no exit window; neither confirms anything. An action letter (`[r] [x] [p] [d] [c] [h]`) is bracketed in the legend and acts only where the legend names it. The popup's top edge names the command on the left and where it came from on the right (`from Home`).
- **A key typed ahead or held chooses nothing.** A key that arrived before the popup's first frame was seen is dropped, nothing answers for half a second after the popup appeared, and an answer needs a key that arrived after it did.
- **Reads happen after the first frame.** The popup opens at once on a loading state and reads the catalogue, the agents or the permissions in work its owner keeps alive until it settles. A fault is a state in the popup, in words (what failed, then the catalogue's own sentence about why, scrubbed, or `Close this and try again.`), with the next action inside the TUI and never a shell command; an empty list says what is empty and what to do. Below 80×24 a note replaces the popup. In the alternate screen it is a centred box over the dimmed Home (colour on); inline it is a framed block that replaces the body, with rules and no side bars, never taller than `rows − 1` lines; with colour off the glyphs are their ASCII forms.
- **Stored words are scrubbed as the Home's own rows are.** A workflow's, an agent's or a directory's name, a description, a node id, a file's place and a remembered command pass the Home's row scrub (control sequences, the `▲ N more` markers and bracketed key names such as `[Enter]` are made plain), so a name a repository wrote cannot forge a row or a key hint.
- **Nothing is written into the conversation or the Home's notice.** What a popup did is one transient notification (in the popup's legend row while it is open, on the hint row after it closes). A popup's newer word replaces its own older one once the older one has been drawn (`Nothing was written.` then `Pinned x.` shows the second at once); the Home's and the host's words queue in order and are never replaced, so a notice that a draft looked like an API key is read for its full three seconds before the next word. What a `/workflows` flow said when it hands the popup back (a refusal, a No, an `Esc`) is the reopened popup's own first word. While a popup is open the strip does not refresh, the Active tab does not poll, and `PgUp`/`PgDn` do not page the Home's notice.

## `/permissions` on the bare Home (MVP-4 step 7, 2026-11-21; a popup since MVP-11 unit 8, 2026-11-27)

The landing palette offers `/permissions` (a line that reaches the Home as a paste, or typed with a leading space, does the same, since a `/` at an empty prompt opens the palette). It takes no argument (`/permissions accepts no arguments.`), and a Home with no permissions port says `Remembered commands are not available here.`. It opens the [popup](#the-homes-management-popups-mvp-11-unit-8-2026-11-27) a chat's `/permissions` opens, in its Home form: **This project · remembered (n)**, the commands this project remembers (a program's name and its argument count, and the date), over a store opened afresh on every read; **This repository · allowlist, read-only**, the repository's `[chat].allowed_commands` (at most four entries, the last a count of the rest, under the note that a listed command still asks in a chat); and, above them, the one note that only auto mode runs a remembered command unasked. There is no *This session* section and no mode: the Home has no chat. With nothing remembered the popup says how a command becomes remembered (`Ctrl+O` then `Enter` on a command card in a chat). Its legend reads `↑/↓ select · [d] / Del withdraw (then Enter) · Esc back to Home`.

`[d]` (or `Delete` or `Backspace`) arms the withdrawal of the highlighted row. The popup's second step names the command and what withdrawing it changes, and **only `Enter` answers it**, not before its frame has been on screen for 0.8 s (until then its legend reads `Enter withdraw (wait) · Esc keep`) and not after 10 s; `Esc` keeps the row. The guard, the rows and every sentence are the chat popup's and are owned by [command-permissions.md](command-permissions.md#in-the-chat-permissions-a-popup); the Home adds nothing and removes nothing. Withdrawing only ever makes the chat ask more.

A bare `relavium permissions` on a terminal (the gate above) starts this Home with the popup already open and without the first-run provider setup, and **the popup is the run's whole job**: when it closes, however it closes (`Esc` or `Ctrl+C`), the command ends with exit `0`. If the popup cannot open the Home stays open with `Remembered commands are not available here.` in its notice. It is the whole Home, so it opens the history database and inherits the Home's start-up refusals. Anywhere else (a pipe, `--json`, CI) the command group is unchanged.

## `/workflows`: the workflows popup (MVP-11 unit 8, 2026-11-27)

**Built on `development`** ([ADR-0148](../../decisions/0148-a-user-started-report-setting-or-flow-is-a-centred-popup.md) §10 and its 2026-11-27 notes; [ADR-0140](../../decisions/0140-management-browsers-the-run-drill-down-and-the-durable-run-detail.md) §1). A typed or palette `/workflows` at the landing opens a two-step [popup](#the-homes-management-popups-mvp-11-unit-8-2026-11-27) and starts no chat; with arguments it says `/workflows accepts no arguments.`, and a Home with no catalog says `The project’s workflows are not available here.` It replaces the Defined tab of the old tab host; in a chat `/workflows` is the chat's own.

- **The catalogue** (step 1). `This project · N workflows` and one row per workflow: its name, its node count, how its last run stands in this directory (a glyph and a word: `✓ done 3h ago`, `‖ waiting 5m`, `✗ failed 2h ago`, `◐ running`) and `pinned` as a word, pinned workflows first. A file that does not parse stays a row, `✗ invalid`, with its reason under the list while it is highlighted; a pin whose workflow left the catalogue is `? not in catalog` and a workflow pin of another project is `? other project`, after this project's pins: neither can be run or exported, and either can be unpinned (the store caps pins in total, fifty, across every project and both kinds, so a pin the popup did not list would hold a slot with no way to remove it). The highlighted row's file is named under the list. Legend: `↑/↓ select · Enter details · [r] run · [h] runs · Esc back to Home`.
- **The detail** (step 2, `Enter`). The name and, as facts, the node count and `pinned`; the description (at most three rows); **Inputs** (name, type, `required`); **Nodes**, the chain of node ids in the order a run reaches them (a human gate says what it is and how long it waits; a long chain ends `… N more`); **File**; and **Last runs**, the workflow's three newest runs in this directory (how each stands, its age and its short id) or `No run of this workflow in this directory yet.`. What the arrows do depends on whether the page fits. **When it fits**, nothing is highlighted on opening (so that a held or doubled `Enter` that opened the detail answers nothing), `↑`/`↓` move only between the last runs, `↓` lands on the first one at once, `Home` and `End` go to the first and the last, and with no run nothing moves. **When it overflows**, `↑`/`↓` walk every line with a drawn caret, `PgUp`/`PgDn`/`Home`/`End` page and jump, and the whole page stays reachable. The legend names what works and keeps the action letters: `↑/↓ select · [r] run · [x] export · [p] pin · Esc back` on opening, `Enter open run · …` with a run highlighted, `↑/↓ scroll · …` on an overflowing page (`[Ctrl+C] close` is the first item to give way, never a letter that acts). `Enter` on a last run closes the popup and opens that run on the [Runs screen] (a waiting or running run on the Active tab with the cursor on it, a finished run's detail on History)(#the-runs-screen-active-and-history-mvp-8-step-4-2026-11-23-narrowed-in-mvp-11-unit-8-2026-11-27). The **Nodes** line draws `→` only along an edge and `·` before a node that no edge joins to the one before it (`start → check → hi · lo → out`). A step reached by `Enter` settles on its own frame, so a held or doubled `Enter` goes no further than one step.
- **`[r]` runs it.** The popup closes and the [`/run` flow](#running-a-workflow-run-mvp-8-step-3-increment-5a-2026-11-23) starts at that workflow with its picker skipped once; the form, the `Ctrl+Y` confirmation and the single start are the flow's own, and a leg that is already live refuses it before anything is asked, as `/run` does. When the flow ends without a run (`Esc` at its first step, a No, a refusal) **the popup comes back on the step `[r]` was pressed on**, the catalogue's row or the detail; a run that started closes everything (and opens its view while it executes); `Ctrl+C` in the flow closes everything. The two popups are not stacked: the flow is a native-channel prompt, which the popup host cannot hold under another popup, so the person sees one popup replaced by another and the first one back.
- **`[x]` exports it** the same way: the export confirmation (destination and byte count; only `Ctrl+Y` writes the file, `Ctrl+N` or `Esc` writes nothing), then the popup comes back. **`[p]` pins or unpins** the workflow under its project root and slug in place, reads the rows again with the highlight following the workflow and says what happened in one notification (a pin refused at the cap says `Cannot pin: 50 pins is the limit. Unpin one.` when the store's own words do not fit). **`[h]`** closes the popup and opens the Runs screen on History.
- **No new authority.** `[r]` and `[x]` start flows that exist and `[p]` writes a mark; nothing here starts a run or writes a file. A request carries the slug and the catalogue path the read holds for the row's entry, never a label, and only a workflow that parsed has one; a row that cannot be run, exported or pinned says what it cannot do and why (`Cannot run X: it is not in the catalog any more.`).
- **Evidence owed.** The keys are row 42 of the [Windows interrupt-evidence runbook](../../runbooks/windows-interrupt-evidence.md); none has been run on a Windows terminal.

## `/agents`: the agents popup (MVP-8 step 5, 2026-11-23; a popup since MVP-11 unit 8, 2026-11-27)

**Built on `development`** ([ADR-0148](../../decisions/0148-a-user-started-report-setting-or-flow-is-a-centred-popup.md) §10 and its 2026-11-27 notes; [ADR-0140](../../decisions/0140-management-browsers-the-run-drill-down-and-the-durable-run-detail.md) §3). A typed or palette `/agents` at the landing opens a two-step [popup](#the-homes-management-popups-mvp-11-unit-8-2026-11-27) and starts no chat; `/agents` with arguments says `/agents accepts no arguments.` and opens nothing, and a Home with no agent catalog says `The project’s agents are not available here.` It is the Home's own command: with a chat in front it is not routed (it is a near miss of the chat's own [`/agent`](#agent-the-bound-agents-popup-in-a-chat-mvp-8-step-5-2026-11-23-a-popup-since-mvp-11-unit-8-2026-11-27), and a chat answers every near miss locally, so the Home says `Unknown command. Did you mean /agent?`, which never runs the command it names), and it is in no chat palette. It replaces the agents strip of the tab host; the strip's Sessions tab went with it, a saved conversation being `/resume`'s.

- **The list** (step 1). `This project · N agents` and the project's agent files (`.relavium/agents`, the catalogue `relavium list --agents` and `chat --agent` read), one row per file, in the catalogue's order (by slug): the agent's id and name and `✓ ready` or `✗ invalid`. The highlighted row's line under the list is its file or, for an invalid one, the catalogue's reason (`Cannot open: …`). Legend: `↑/↓ select · Enter details · Esc back to Home`. Empty: `No agents in this project.` and `Add one under .relavium/agents (see /init).`; unreadable: `The agents of this project could not be listed.`, then the catalogue's own sentence about why (scrubbed) or `Close this and try again.`
- **The detail** (step 2, `Enter` on a ready agent; on an invalid one `Enter` opens nothing and says why in a notification). Read-only, and it shows only the model, the provider, the temperature and the reasoning effort (`not set` when the definition has none), the tool grant as the definition declares it (the names, at most three rows, ended with `…` when cut; `none declared` for none), the first 240 characters of the system prompt (scrubbed whole before it is cut, at most four rows, cut at a word and ended with `…`) and a line that points to `/resume` for the agent's conversations. It has one action, `[c]`. Legend: `[c] chat · [Ctrl+C] close · Esc back`.
- **Chat with an agent: `[c]` on its detail.** `[c]` starts a chat bound to that agent. The popup closes first and the build begins, so the chat opens where the Home was, idle (there is no first message, and the loading line echoes none; nothing is sent until the first message). An invalid agent has no detail and so no `[c]`; `Ctrl+C` closes the popup and starts nothing. **The Home adds no authority:** it binds through `relavium chat --agent`'s own session build. The file the detail showed (named by the catalog's own path of it, never a word a person typed and never the row's label) is read **once**, through the catalog's hardened single-file read (an admitted project artifact inside the catalog root, a regular file under the size ceiling, opened with no final-link following, no blocking and an exact device and inode check), so a file swapped for a link out of the project or for a FIFO is refused, as it is in the list; `chat --agent <path>` itself reads a path it was given with a plain stat and read, and is unchanged. The definition that read produced is what is bound, and the file is not read again. If it is not exactly the definition the detail was drawn from (a deep comparison of the parsed definitions: a tool, a prompt, a model, a server or a name edited, with the same id and still valid), nothing starts. The tool grant is exactly the definition's `tools` (narrowed, as for `--agent`, to the tools the chat host wires), every tool call still asks under the chat's mode ([ADR-0057](../../decisions/0057-cli-chat-modes-and-per-tool-approval.md)), the model and provider are the agent's own and not `[chat].default_model`, and a stdio MCP server it declares goes through the same per-server consent as every path ([ADR-0084](../../decisions/0084-consent-before-a-local-mcp-spawn.md)), the card naming the file, with nothing spawned before it is granted. `/clear` in that chat rebinds the same agent without reading the file again. An agent that cannot be started leaves the Home on the landing with one fixed sentence, and the loading state is cleared and no chat starts, and nothing of the file or of the error is shown: `The agent changed since it was listed. Open the list again.` when the file is no longer the definition the detail showed, otherwise `The agent could not be started: <reason>.`, where the reason is one of `its definition is not valid`, `its file is missing or cannot be read` (gone, or refused by the hardened read), `its provider has no usable key (see /providers)` or `its session could not be built` (a server it declares was not approved or did not start).

## `/mode` on the bare Home (MVP-11 unit 8, 2026-11-27)

**Built on `development`** ([ADR-0148](../../decisions/0148-a-user-started-report-setting-or-flow-is-a-centred-popup.md) §3 and its 2026-11-27 notes, the maintainer's ruling OD-25). A palette `/mode` at the landing opens a one-step [popup](#the-homes-management-popups-mvp-11-unit-8-2026-11-27); `/mode` typed with an argument says `No conversation is active. Use /mode to set the startup default.` and changes nothing, and a Home with no startup-mode port says `Startup mode settings are unavailable here.`. It is the chat's list ([chat-session.md](chat-session.md#the-mode-popup-mvp-11-unit-8-2026-11-27)) without the state word `this chat`: there is no conversation, so the one choice is the startup default for new chats. The principle is that **a popup never asks for a decision that changes nothing**.

- **The list** opens on the saved startup default, so a bare `Enter` keeps it: the four modes, each with its effect in a few words and the state word `startup` on the saved default. The highlighted mode's whole effect is stated under the list before any key is pressed (amber for `accept-edits` and `auto`, which approve without a card, and led by `! ` where colour is off). Legend: `↑/↓ select · Enter set as startup default · Esc close`, and `↑/↓ select · Enter keep · Esc close` on the saved default.
- **`Enter` on the saved default** closes the popup with one notification (`Startup default is already ask`) and no second screen.
- **`Enter` on another mode** opens the one confirmation of the persistent write, the same component the chat's `[s]` opens and worded alike ([chat-session.md](chat-session.md#the-mode-popup-mvp-11-unit-8-2026-11-27) owns its content: what is written, the file, the rewrite or the creation, `auto`'s risk sentence and any override the card names): the startup-default writer's own flow framed as `Mode · Confirm · Done`, with the writer, its disclosure, `auto`'s extra admission and the `startup-writer-*` controls unchanged. It is answered by `Ctrl+Y` and by nothing else (`Ctrl+N`, `Ctrl+C` and every other key save nothing, and a held key never confirms), and `Esc` steps back to the list on the saved default, never on the mode that was being saved. A write ends in a persistent *Done* step that names the file; a declined or refused save is one notification. There is no `[s]` on the Home: its `Enter` is the way in to the write.

## The Runs screen: Active and History (MVP-8 step 4, 2026-11-23; narrowed in MVP-11 unit 8, 2026-11-27)

**Built on `development`** ([ADR-0140](../../decisions/0140-management-browsers-the-run-drill-down-and-the-durable-run-detail.md) §1, §2, §4, §5; [ADR-0148](../../decisions/0148-a-user-started-report-setting-or-flow-is-a-centred-popup.md) §10 and its 2026-11-27 note). The Runs screen is the Home's `tab-host` screen (the code keeps that name): one screen slot that replaces the strip and the prompt while it is open, and is entered only from the landing (a chat or a card in front keeps its own keys). It is the one place the Home keeps for browsing runs and working in them for a while. It was a tab host of four tabs (Defined, Active, History, Permissions) with a second strip for `/agents`; the catalogue, the agents and the permissions are [popups](#the-homes-management-popups-mvp-11-unit-8-2026-11-27) now, and its tabs are **Active** and **History**. There is **no `/runs` command**: it opens on History from `[h]` in the `/workflows` popup, on a run's detail from `Enter` on a run row of the work page (the Home's second page, `↓` from the landing) and from `Enter` on a last run in the `/workflows` detail, and it comes back with `Esc` from a run view or a gate card opened from Active. Each tab is read again every time it is entered. While the screen is open each tab remembers its cursor, History also its scope, its filter and the run its cursor was on, and Active the run its cursor was on and its scope (not a run's detail or a node page, which a tab left behind does not keep); this is every tab's, whichever tab is in front, so moving to another tab and back (or to a run view and back with `Esc`) finds each tab as it was left. The History tab remembers no page: it reads its first page again when it is entered, with the cursor on the same run when that run is on it. The memory goes with the screen, so a screen opened again starts every tab at its top, and nothing is kept on disk.

- **This directory by default.** Active and History both list this directory's runs; `[a] all` lists every project's, read-only (a run of another project can be opened here and is never actionable), and the key then reads `[a] here`. The scope is each tab's own.
- **Keys.** `←`/`→` move between the two tabs and stop at the ends; `Tab` and `Shift+Tab` go around. `↑`/`↓` move over rows and stop at the ends on Active, and on the **History** list `↓` on the last row of a page reads the next page and `↑` on the first row reads the previous one (the History bullet below). `PgUp`, `PgDn`, `Home` and `End` page and jump on **History** (the list, a run's detail and the node page); Active answers to `↑`/`↓` only. `Enter` opens a run's detail or a node on History and a run's view or gate card on Active. `Esc` goes back **one level** where there is one (the node page to the run's detail, the detail to the list) and closes the screen at a tab's list, back to the Home. `Backspace` goes back one level on History's detail and node page and does nothing elsewhere. `Ctrl+C` closes the screen from any tab and any depth and **never arms or cancels from the Runs screen itself**; a run view reached from the Active tab keeps its own two-press ladder ([above](#the-run-view-mvp-8-step-3-increment-6-2026-11-23)). A bare letter is an action only where no text field is open (`a` all or here on either tab, `p` pin, `f` filter and `n` first failed on History, `r` run again on the detail of a run of this directory); nothing needs a mouse, and a paste is dropped. The legend under the screen names the keys that fit its 78 columns, the way out last: `Esc / [Ctrl+C] back to Home` at a tab's list, `Esc back` on a detail (`←/→ tab · ↑/↓ select · Enter open · [a] all · Esc / [Ctrl+C] back to Home` on Active at 80 columns). What a legend leaves out, it leaves out for room: `Shift+Tab` everywhere; `PgUp`, `PgDn`, `Home` and `End` on History; `Backspace` on History's detail and node page (it goes back, as `Esc` does). A bare letter acts with Caps Lock on as well (`P` is `p`).
- **The 23-row budget.** The host draws at most 23 rows and one row stays spare in a terminal of exactly 24 lines, so the inline renderer never reaches the bottom edge. The tab strip and its rule take two rows and the legend one, so the body is **20 rows** at 80×24: on a list, the rows, a `▲ N more` or `▼ N more` marker standing for the rows it hides, and the message row, which keeps its line whether or not it has anything to say. A label is cut with `…` before a column is dropped. Below **80×24** the screen is two lines, the hint `Enlarge the terminal.` and a legend that names the level `Esc` goes to (`Esc back to the run` on a node page, `Esc back to the list` on a run's detail, `Esc / [Ctrl+C] back to Home` at a tab's list), and only `Esc` and `Ctrl+C` are delivered: `Esc` there does what it does at full size (it steps back one level from a node page or a run's detail, and closes the screen only from a tab's list), so a screen opened on a node page is not closed by it, and `Ctrl+C` closes the screen. Every state has a glyph **and** a word (colour only repeats it), every string read from the history file passes the sanitize floor, and the screen reads the same in the inline and the full-screen renderer and with colour off.
- **Active.** This directory's runs that are not finished (`[a] all` lists every project's, read-only, and the key then reads `[a] here`; a run another directory started used to read `another project` here and is no longer listed by default), in four groups that never mix: running (the leg this Home hosts is one of them), paused, stalled and held, each row with a glyph and a word. `Enter` on the hosted leg reopens its view; `Enter` on a run paused at a gate in this project opens its gate card (`Esc` on it returns to the tab on the same row; `Ctrl+C` closes the card and the Runs screen together, back to the page of the Home they were opened from); `Enter` on a run paused on media jobs alone in this project asks whether to continue it ([above](#a-run-parked-on-media-jobs-alone-hostlife-1-2026-11-23): a No changes nothing, a Yes shows the new leg's view, and `Esc` there returns to the tab on the same row); every other row is read-only, and `Enter` says why (there is no cross-process cancel). **The cursor follows the run by its id, not its row number.** A run that moves up or down the list keeps the cursor; a run that **left** the list does not hand the cursor to the row now at its number: no row is marked, the message row says `The run you had selected left the list. ↑/↓ select another.`, and `Enter` says `No run is selected. ↑/↓ select one.` and opens nothing until `↑` or `↓` picks a row, so an `Enter` aimed at a run that is gone never opens the card of its neighbour. The tab is a read-only poll while it is in front (it pauses while the exit question, a native question or form, a popup, or a terminal below 80×24 holds the screen), and one read of it is **one snapshot of the database** (the three status pages, the leases and the gate reads in one read transaction), so a run another process moves between two statements is never listed twice, nor missing for a tick. The rows are as of each node boundary: streamed output is never stored, and the last row says so. A run whose lease has been missing for more than one lease TTL is `stalled`; the poll never reconciles.
- **History.** Finished runs, newest first: **this project's** by default, `a` to widen to every project and back, `f` to cycle the status filter, twenty rows a page (at most three pages kept in memory, older ones read again). A pinned section sits above the page. Each row has the run's glyph and word, its short id, workflow, age and a cost that is qualified like every other cost (`…` until read, `not final` for a run that has not ended, `unreadable` for a run whose log cannot be read, `not read` for a cost whose read failed just now, which the next key reads again; never hidden). A run whose log cannot be read **keeps its own glyph and status word** and says `unreadable` only in the cost slot, where the figure it replaces would be (the line under the list adds `its event log could not be read (it was <status>)`). `↓` on the last row of a page reads the next page (the cursor lands on its first row) and `↑` on the first row reads the previous one (the cursor lands on its last row), so a long list is walked with the arrow keys alone; `PgUp`, `PgDn`, `Home` and `End` stay on the page. A page can hold fewer than twenty finished runs, or none, and still not be the last (the store is read 200 raw rows at a time, and the active runs among them belong to the Active tab), so the list never promises a `▼ more` for rows it has not read: a page with no finished run but a next page says `No finished run on this page. ↓ reads the next page.`, and the line under any page with more behind it says `Newest first. Enter opens a run. ↓ at the end reads the next page.` `p` pins or unpins the run under its full run id (a fifty-first pin is refused with a sentence that names the stored total and how many of them are workflows, as the `/workflows` popup's does), and `Enter` opens the run's detail.
- **The run detail.** The header (status glyph and word, workflow, short id, `★ pinned`, start, duration, tokens and the qualified cost, the run's error), then the **node table** and the run's events. A run whose end is held in the terminal outbox says `held`, never `in progress`. The table lists the nodes that ran **in the order they ran**, then the nodes of the run's frozen workflow snapshot that have no record at all, in the order the workflow authored them: such a node is `○ pending` and says `not yet run` while the run has not ended and `did not run` once it has, so a failure never hides the part of the workflow it kept from running. Each row has the last attempt's status, the attempt count, duration, tokens and cost, with a skipped node's reason; a figure with nothing to show says why in [the words below](#words-for-what-is-absent). `↑`/`↓`, `PgUp`, `PgDn`, `Home` and `End` scroll, **`Enter` opens the node on the selected row**, **`n` puts the cursor on the first node whose last attempt failed** (a node that failed and was retried to success does not count; with none it says `No node of this run ended failed.`), **`p` pins or unpins the run** by the same path as on its row (and the list behind is read again), and `Esc` or `Backspace` return to the list on the run it came from. Whether the run is pinned (the header's `★ pinned`, and which way `p` toggles) is asked of the pin store by the run's full id when the detail opens and kept current by `p`, never read off the list: a run of another project is not on this project's page, so the page cannot say, and it is shown pinned (and `p` can unpin it) all the same. A run of another project can be opened here and is never actionable. **`r` runs it again**, on the detail of a finished run started in this directory: the legend names `[r] run again` only where the press would pass (the workflow is in this project's catalog and parses), and `r` opens the `/run` form on that workflow with its inputs asked again (a run's inputs are not shown or reused, [ADR-0113](../../decisions/0113-secret-derived-context-keeps-provenance-at-public-sinks.md)), so nothing starts without the form's own `Ctrl+Y`. A refusal says why in a fixed sentence (`That run was started in another directory.`, `This workflow is not defined in this project.`, `The file of this workflow could not be read.`); a workflow whose node count changed since the run still opens and says `This workflow changed since that run.`. Where `[r] run again` is offered, the detail's legend at 80 columns drops `↑/↓ scroll` (a failed run) or `[n] first failed` (a completed run), and the line under the list names `Enter`. A log longer than twenty pages of a thousand events is read as far as that and says so; a row written by a newer binary is skipped and counted once.
- **The node page.** One node of one run, opened from the run detail; `Esc` returns to the detail on the row it left. It shows the node's **order and type from the run's frozen workflow snapshot** (`Order in the workflow: 2 of 5  ·  type agent`, two spaces each side of the dot; with no readable snapshot it says `Order in the workflow: unavailable` and shows the type the run recorded), what the workflow authored (agent and model) beside the model(s) the node **actually ran on** (from its settled model calls), its tokens, cost and time, every **attempt** (one row each: the last row recorded for an attempt number, so a re-dispatched attempt is listed once), the **tool activity** of the inspected attempt, its **error**, its **output**, and the node's own events. A node's **input is never shown**: no value of it is recorded, and the rendered input can be secret-derived. The page inspects the node's **last** attempt; **`n` shows the first attempt that failed**, but only for a node whose last attempt failed: a node that was retried and then succeeded has no failed attempt to show, and `n` says so. `↑`/`↓`, `PgUp`, `PgDn`, `Home` and `End` scroll.
  - **The output goes through the one masking seam** (`render/output-masking.ts`) that the final summary of `relavium run` and `logs` also masks through, so a value one of them masks cannot reach the terminal through the other. A value is masked **whole** and only then cut: a string leaf, an object key and the whole emitted text each pass the shared secret scrubber on their own, a member whose **name** labels a credential has its value masked whole (a name the scrubber's own header and query rules read as a label, or one of the exact names [`relavium run`](commands.md#relavium-run) lists, which owns the list and how a name is compared; a boolean or `null` under one of those exact names stays, so the engine's masked-input marker `{ secret: true, ref }` stays readable), and terminal controls (escapes and the bidirectional controls) are stripped. The page shows at most **40 lines and 4,000 code points** of an output, says `masked` and `shortened` on a line of its own under the heading when either happened (and masks the value of an output whose node id labels a credential whole, as the summary does for an output of that name), and never reads a stored document above **1 MiB**: it says its size in bytes and shows no text of it. The error goes through the same scrubber and the same strip; a long line is wrapped, not cut.
  - **The tool activity is content-free.** One row per call: the tool's id (scrubbed) and how the call ended ([the tool outcomes below](#tool-outcomes)), at most fifty calls, with a `… N more, not stored` row for the rest. No argument and no result text is kept, so none is shown. The trace belongs to the attempt the node's end event closed; any other attempt says `not recorded for this attempt`.
  - **A node with no attempt row** (skipped, or not reached) is a short page: its place and type, `skipped: branch not taken` (or `upstream unreachable`) or the sentence of its state, and the same sentence for each figure. A node whose record cannot be read says `unavailable` and guesses nothing.
- **Nothing here changes a run.** The Runs screen cancels, retries, edits and deletes nothing, and a pin is only a mark: it never changes a run or a workflow. Pins are global to the home database, survive restarts, and are capped at fifty.
- **Evidence owed.** The keys of the Runs screen, the run detail and the node page are rows 27 to 30 and 45 of the [Windows interrupt-evidence runbook](../../runbooks/windows-interrupt-evidence.md); none has been run on a Windows terminal.

## `/import` and `/pricing`: the Home's forms for two shell commands (MVP-8 step 5, 2026-11-23)

**Built on `development`** ([ADR-0140](../../decisions/0140-management-browsers-the-run-drill-down-and-the-durable-run-detail.md) §9). Each is a **Home command**: it is in the landing palette and on the `/help` popup, a typed or pasted line at the landing opens it, and with a chat in front the line is the chat's, so neither opens a card there (`/pricing` reaches the chat's dispatch as an unknown slash; `/import` is a near miss of the chat's `/export`, so the Home says `Unknown command. Did you mean /export?`, which never runs the command it names). Neither takes an argument (`/import accepts no arguments. It asks for the path.`, `/pricing accepts no arguments.`), neither is in a chat palette, and a Home started without the ports says `Import is unavailable in this session.` or `Model pricing is not available here.`. Both run as framed popups on the Home's native prompt channel (since MVP-11 unit 6: a step rail, the confirmation answered by `Ctrl+Y`, and a persistent Done step that says what was written or that nothing was, closed by `Enter` or `Esc`), so the keyboard belongs to the form while it is open and the Home shows one notification when it closes. The shell commands, [`relavium import`](commands.md#relavium-import--relavium-export) and [`relavium models pricing`](commands.md#relavium-models), are unchanged and remain the way to script them: each form runs the command's own prepare step (which writes nothing) and then its own commit.

- **`/import`** asks for the path of a workflow or agent YAML (one text field, at most 1,024 characters, a leading `~` is your home; it is a path prompt, not a file browser). It then shows a card of what the import would write: the kind and id, where the file comes from and where the copy would go in this project, its size, up to two notices about literals the file holds, and that the copy is canonical YAML (comments dropped, values kept as written, the file you named unchanged). **Only `Ctrl+Y` writes the file.** `Ctrl+N`, `Esc`, `Ctrl+C` and every other key write nothing, and the Home says `Nothing was written.`. **It never overwrites**: an id the project already has, or a destination that is taken, is a refusal shown before the card asks (`Not imported. …`), and its words name `relavium import --force`, the shell command that replaces a file.
- **`/pricing`** (the palette describes it as `models pricing`) asks whether to **set a price** or **clear the override**, then for which model: the merged catalog `/models` lists, each with where its price comes from, or **Another model…**, which asks for an id and one of the registered providers. A set asks for each price the shell's field table has (input and output, cached input and the media rates; an empty answer leaves a price unset, and input and output are given together or not at all, as the shell requires). A card shows exactly what will be recorded and that the override belongs to this machine's operator and outranks the catalog's price. **Only `Ctrl+Y` records it.** `Ctrl+N`, `Esc` at the card and every other key write nothing; `Esc` at an earlier question steps back to the one before it, and at the first it leaves the form. Clearing a model the operator has no price for is said, not asked. The card and the sentence after a write print the stored value. A model id that is empty, holds an invisible or formatting character, or has a space at either end is refused before anything is asked (the field table's rule, which the shell applies to a set too; a clear is never refused by the shell, but the form also refuses an id its card cannot show whole, one too long or one the sanitizer would change). The form reads the database catalog before it decides a plan, as the shell does, so a model only a refresh has seen is anchored to its provider and priced as everywhere else.

## Typed slash words and `/help` at the landing (MVP-8 step 5, 2026-11-23)

**Built on `development`** ([ADR-0140](../../decisions/0140-management-browsers-the-run-drill-down-and-the-durable-run-detail.md) §3). A line that starts with `/`, typed or pasted at the landing, is a command line: it is answered there and **never starts a chat**, and nothing is sent to the model. A message cannot begin with `/`: a chat reads every line that starts with a slash as a slash command (one it does not know is answered `unknown command`, never sent to the model), so a chat started for such a line could only answer that. The first word decides the answer, whatever follows it (`/tmp has junk` and `/cost is high` are answered by `/tmp` and by `/cost`). (A `/` typed at an empty prompt opens the palette, so a line typed key by key reaches this answer through the palette: `Enter` on a query that matches no command answers the line exactly as the same line pasted is answered, by the same code, so a Home command typed with arguments (`/run extra`) says `/run accepts no arguments. Use its picker to choose a workflow.` here as it does for a paste, and is not reported as unknown. A query that matches a command still runs that command.)

| The word | The landing answers |
|---|---|
| `/help` | Opens the **help popup**. With anything after it: `/help accepts no arguments.` |
| A word the Home owns and that has no screen of its own (`/exit`, `/doctor`, `/clear`, `/models`) | Runs as the palette runs it, with no arguments. With anything after it: `<word> accepts no arguments here. Start a chat to use them.` |
| `/mode`, `/resume`, `/permissions`, `/workflows`, `/agents`, `/run`, `/init`, `/providers`, `/import`, `/pricing` | Their own popups and cards (`/workflows`, `/agents`, `/permissions` and `/mode` are [popups](#the-homes-management-popups-mvp-11-unit-8-2026-11-27): `/agents` with arguments says `/agents accepts no arguments.`, and `/mode` with one says `No conversation is active. Use /mode to set the startup default.`; [`/import` and `/pricing`](#import-and-pricing-the-homes-forms-for-two-shell-commands-mvp-8-step-5-2026-11-23) say `/import accepts no arguments. It asks for the path.` and `/pricing accepts no arguments.`). |
| Any other word of the registry, alone or with anything after it (`/agent`, `/cost`, `/export`, `/cancel`, `/copy`, `/details`, `/thinking`, `/compact`, `/scrollback`, `/edit`, `/effort`, `/trim`) | The notice `<word> works in a chat. Start one, then type it. /help lists the commands.` |
| A near miss of a Home word, with or without text after it | `Unknown command. Did you mean /x?` (`/help` is one of the words it can suggest; the suggestion never runs the command it names). |
| Any other lower-case word (`/` and lower-case letters and hyphens), with or without text after it (`/tmp has junk`) | `Unknown command: <word>. /help lists the commands.` The notice names the word and not the text after it. |
| Any other line that starts with `/` (a path such as `/Users/x/file.txt`, a word with an upper-case letter such as `/Zzzz`) | `Unknown command: <line>. /help lists the commands.` The line is shown as the chat shows an unknown command: every character outside printable ASCII is `?`, and at most 64 characters are kept. |

A line that starts with a slash is never a first message: `/Users/x/file.txt`, `/etc/passwd`, `/tmp has junk` and `/cost is high` are each answered and none starts a chat. To send text that begins with a path, begin the message with a word (`Please clean /tmp`). A line that does not start with a slash is a message, whatever it holds. With a chat in front nothing changes: the chat's own dispatch answers its commands and its unknown words, and the help sheet does not open.

**The palette is bounded by the terminal.** The `/` palette lists every command of the bare Home (fifteen: Work, Set up, Check and End, as [the landing's section](#the-homes-two-pages-mvp-11-unit-7-2026-11-26) lists them), which is more rows than a terminal of 24 rows can hold with the prompt. On the landing it is drawn **below** the prompt row (the prompt row holds the typed query, then the list, then a legend row), so nothing above the prompt moves when it opens; on the work page it is drawn above the docked prompt (the list, the prompt row with the query, the rule, the legend on the hint row). It takes at most half the terminal (12 rows at 80×24: a window of eight entries and a marker) and never more than `rows − 1` lines, and never fewer than a window of one highlighted entry between two markers; when the matching entries do not all fit, a window of them is drawn with `▲ N more` / `▼ N more` for the entries it hides (the entry a marker stands on counted), the highlighted entry is always in the window, and `↑`/`↓`, `Enter`, `Esc` and `Ctrl+C` do what they did. The window is the one the Runs screen, the popups' lists and the native select use (`windowBody`); a chat's palette is the same view and, with more rows than entries, draws as it did.

**The help popup** (MVP-11 unit 8, [ADR-0148](../../decisions/0148-a-user-started-report-setting-or-flow-is-a-centred-popup.md) §10 and its 2026-11-27 note) is the Home's `/help`: one read-only [popup](#the-homes-management-popups-mvp-11-unit-8-2026-11-27) that fits one page at 80×24 with no scroll, with `[c] copy` and `Esc back to Home`. **Keys** lists the landing's own keys, each in a few words (`Enter` start a chat with what you typed, or open the row; `Ctrl+J` add a line to what you are typing; `/` the commands, from an empty prompt; `↓` down to the work page; `Esc` back up to the start page; `Ctrl+D` exit from an empty prompt, and `Ctrl+C` twice to exit, both asking first while a run executes). **Commands** is the Home's palette rows, grouped as the palette groups them (Work, Set up, Check, End) and listed by name alone; the descriptions are in the palette (`/`). Chat-only commands are not listed. The keys are one table that a test presses on a mounted landing, and the commands are the registry's Home placements, so the popup cannot name a command or a key that does not work. It replaces the help sheet, a screen that cut rows at 80 columns.

## Words for what is absent

A page of the Runs screen never draws `0`, a blank or a bare dash where it means "nothing was recorded", and never says two different things with one word: each way a figure, a trace, an output or an error's message can be missing has **one fixed sentence** (the table below has fifteen), and the sentence says what is known and no cause beyond it. The words live in one module of the CLI (`apps/cli/src/render/absence.ts`); the run detail's model, the node page's model and the Runs screen's lines import them and write none of their own, and a test (`apps/cli/src/render/absence.test.ts`) reads this section and compares it with that module in both directions.

| Sentence | Where it is drawn | What it says |
| --- | --- | --- |
| `not recorded` | A node's tokens, cost, error or output | The node finished (completed or failed) and the figure was never written: an older log, or no settled model call and no step figure. Never used for a node that did not run, did not finish or is still going. |
| `did not run` | The figures of a skipped node, and of a node a finished run never reached | Nothing ran, so there is nothing to record. |
| `did not finish` | The figures of a node whose last attempt has no end event in a run that has ended | The node was left running when the run ended (a decided gate, a failure that stopped it). |
| `in progress` | The figures of a node that is running in a run that has not ended | The figure does not exist yet. |
| `not yet run` | A node of the frozen workflow that has no record at all, in a run that has not ended | Its turn has not come. |
| `not recorded (older log)` | The tool activity of a node whose end event has no trace field | The log was written before the trace existed. It does **not** say the node made no call. |
| `not recorded for this attempt` | The tool activity of an attempt other than the one the node's end event closed | The trace belongs to another attempt. |
| `no result recorded` | One call of a tool trace | The node ended before the call was answered, or the tool threw (the node's own error says why it failed). A refusal is a recorded result and is not described this way. |
| `no tool calls` | The tool activity of a node whose trace was recorded and is empty | The node made no tool call. |
| `no output` | The output of an attempt that failed | The attempt produced no output. |
| `(empty)` | The output of an attempt that recorded an output and it is the empty string | The output exists and says nothing; this is not `no output`. |
| `skipped` | The status word of a node the run passed over, followed by its reason | `branch not taken` or `upstream unreachable`; every figure of the node says `did not run`. |
| `unavailable` | A node page whose record could not be read, and the node's order when the snapshot could not be | The attempt row is gone, the run is gone, or its log is damaged; nothing is guessed in its place. |
| `no message recorded` | The error line of a run's detail | The run's stored error carries a code and no message. |
| `no node was recorded` | A run's node table | The run has no attempt row and its frozen workflow (when it could be read) names no node. |

### Tool outcomes

The four ways one call of a tool trace ends. `<duration>` stands for the call's measured duration (`12ms`, `1.4s`).

| Words | What it says |
| --- | --- |
| `ok` | The call ran and was answered, and no duration was measured. |
| `ok in <duration>` | The call ran and was answered. |
| `refused` | A recorded result with no duration: the tool never ran (a denied call, a refusal before dispatch). |
| `failed after <duration>` | The call ran and failed. |

## The Home's two pages (MVP-11 unit 7, 2026-11-26)

**Built on `development`** ([ADR-0146](../../decisions/0146-the-home-and-the-chat-share-one-calm-layout-and-the-first-run-has-no-dead-end.md) §1 to §3 as the maintainer's rulings of 2026-11-26 shaped them, [ADR-0140](../../decisions/0140-management-browsers-the-run-drill-down-and-the-durable-run-detail.md) §6; the decisions and what is still open are in the [log's unit 7](../../roadmap/phases/mvp-11/implementation-log.md#unit-7--the-home-and-the-chats-presentation-2026-11-26)). The Home is two pages. **Page 1, the landing**, is always the calm one, whatever the Home holds. **Page 2, the work page**, is what `↓` goes down to. The pages share one draft (both prompts draw the same editor, so a message typed on one is on the other when the person goes back) and one status line.

The work page's rows are a bounded, indexed aggregation over the durable `history.db` ([ADR-0050](../../decisions/0050-cli-history-db-at-rest-posture.md)), re-read on every return-to-Home and on an [idle tick](#actionable-rows-and-the-idle-refresh-mvp-8-step-5-increment-2-2026-11-23) that reads only when the log changed, never a live subscription (the code calls the list the *strip*). Under [ADR-0122](../../decisions/0122-the-home-is-the-interactive-product.md) its sessions, parked runs, failed runs and recent runs are keyboard-openable; the other rows remain displays. It never mutates anything on its own (the no-IDE-shell principle of [ADR-0007](../../decisions/0007-desktop-is-not-an-ide.md) applied to the CLI by analogy: management + chat only, no file tree, editor, or embedded terminal).

Before its first read the Home **reconciles** (2.6.G liveness): a run a dead process left `running` is settled and shows under *Attention required*, and a terminal held in the outbox is written. What is settled, how, and which runs are left alone are the rules `run` and `gate` follow, stated once with [exit code `5`](commands.md#exit-codes). The Home waits for this after the signal and exit nets are registered and before it mounts, so a crashed run whose lease has expired is settled before the first frame. A dead process's lease stays live for up to a minute after it died, and until it expires the run still shows as `running`; a later open settles it. Reconciling is best-effort and never keeps the Home from opening.

### Page 1: the landing

```text
      R  E  L  A  V  I  U  M                          ← the wordmark (bold, accent)

      ◉╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌○╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌○   ← the rail (68 columns at 80)
      Start as an agent        Ship the workflow             Own every run
      talk to an agent          save it as YAML             every run kept

      › summarize the files in this folder                ← the prompt and its dim example (never sent)
      ────────────────────────────────────────────────────────────────────
      anthropic · claude-haiku-5-5 · ask mode   ~/acme-web                ← one status line
      ◐ 3f9a1c2e  ·  running  ·  Enter show it                            ← only while a hosted run executes

      [/] commands · ↓ release-notes needs approval · expires in 5m · [Ctrl+C] exit (twice)
```

- **The head.** With `[preferences].show_banner` `true` or absent the landing draws the **block**: the wordmark, a blank row, the rail (three nodes, the first filled) with its three labels and dim notes. With `false` it draws the one-line spaced wordmark instead, **whatever the Home holds** (page 1 is the landing in both states of the Home). It is left-hung at a margin of 6 columns (8 from 100 columns), and the rail is the terminal less two margins, at most 96. In the alternate screen the block sits above the middle (a top gap of 3 rows at 24, 6 at 30); inline there is no vertical gap, so nothing blank is pushed into the scrollback. Without colour the glyphs are their ASCII forms (`@`, `o`, `.`, `>`) and the example reads `e.g. summarize the files in this folder`.
- **The prompt block.** The prompt (`›`, `>` without colour; the cursor on the example's first letter), a thin rule the rail's width, the status line, the run row while a hosted run executes, a blank row and the hint. `Tab` fills the example in, and only where it is on screen (an empty prompt on the landing). A draft longer than the room is drawn as a window around the cursor with a `▲`/`▼ N more` marker. `Enter` on an empty prompt shows the live run when it can be shown, connects a provider when there is no key, and otherwise answers with one notification, `Type a message to chat · [/] commands`. A `/` at an empty prompt opens the palette **below** the prompt row, so page 1 never moves. A notice stands in the blank rows directly over the prompt (a short one moves nothing) and pages with `PgUp`/`PgDn` when it is longer.
- **The status line** is `<provider> · <model> · <mode> mode`, with ` · effort <tier>` when one is set, then three spaces and the directory (project-relative or from `~`): the defaults of the next chat, in the words a chat's own line uses (there is no `next chat:` label). The facts are read once and at the events that can change them (a provider or preference change, a chat ending), never while drawing, so a key or config changed in another terminal leaves the line stale until the next refresh, and a read that fails blanks the row. When it does not fit, the directory is cut first (its leading names become `…`), then the model in its middle, then the provider; the mode and the effort never. With no provider key it is `No provider key yet · Enter connect · /providers`, in the accent.
- **The hint is page 1's one pointer to the work page.** With nothing to continue it reads `[/] commands · type a message to chat · Tab fill the example · [Ctrl+C] exit (twice)`. With something to continue its `↓` item says what needs the person: the most urgent item of *Attention required*, named (`↓ release-notes needs approval · expires in 5m`, `↓ wf-f1 failed 1h ago`, `↓ a run cannot be read`; a run the read cannot name is `run <8 characters>`), then `+2 more need you`, then the counts of sessions and runs; with nothing urgent it counts (`↓ 1 session`, `↓ 2 sessions · 3 runs`). A narrow terminal makes it give up, in order: the counts, `+2 more need you` (then `+2 more`), the others, the long deadline for its compact form (`5m left`) and the name's tail; `expired` is never given up, and when even that does not fit the hint says the count (`↓ 3 need you`). When eight or more paused runs wait (the Home reads eight), it leads with the count of all of them (`↓ 16 need you · …`), because an unread one may be more urgent. A draft gives way to the `↓` cue last: `Enter start the chat · ↓ 3 need you · [Ctrl+C] exit (twice)`. With no provider key it leads with `Enter connect a provider`. The first `Ctrl+C` arms and the hint reads `[Ctrl+C] exit (again)`.

### Page 2: the work page

`↓` from the landing goes down to the work page when there is something to continue and the cursor is on the draft's last line (a multi-line draft moves its cursor first): to the first row, or, when no row can be focused, to the docked prompt. In the alternate screen the two pages are one document two screens tall and the window slides, four steps about 40 ms apart (the arrival comes 120 ms after the key); inline the pages swap. Keys that arrive during the slide wait for the arrival's measured frame, for 250 ms at most, and an `Enter` or an answer chord among them is dropped; `Ctrl+C` ends the slide at once. With nothing to continue there is no work page. The page is exactly `rows − 1` rows tall, top to bottom: the way back (`↑ start page`, dim) and, from 26 terminal rows, a blank row; the sections; a notice with a blank row above it; and the **docked prompt** (a blank row, the prompt reading `type a message, or / for commands`, the thin rule, the status line and the hint: five rows at rest).

```text
↑ start page

Attention required
  › ‖ release-notes · approval · expires in 5m · 3f9a1c2e
    ✗ nightly-build · failed 3h ago · $0.0210 · 9d2e44a0
Continue
  Sessions
    Plan the launch · planner · 5m ago · $1.2000
    chatter · 12m ago · free
  Runs
    deploy · completed · 2h ago · free · 5ac01b7e
  Agents
    coder · 3d ago

› type a message, or / for commands
────────────────────────────────────────────────────────────────────
anthropic · claude-haiku-5-5 · ask mode   ~/acme-web
↑/↓ select · Enter open · type to chat · Esc start page
```

- **This directory only.** The page lists the runs recorded for the Home's project root (the canonical path of the directory, compared as one value: `--cwd` is made absolute at the argv boundary), the sessions of its working directory, and the agents they ran. The work of other directories is not here: it is the session popup's `Tab` and the Runs screen's `[a] all`. So a Home opened in a subdirectory of a project, or in a directory that holds no work of its own, shows nothing of the project's. The counts are the store's **true totals**, not the rows loaded, and each run is counted once: a paused run is Attention; a failed run **created** within the last 7 days is Attention; a run whose log cannot be read is one Attention item; every other run is a Run.
- **Attention required**, in **one urgency order** that the rows, the keys and page 1's hint all read: (1) parked runs whose deadline has passed, the longest overdue first, then those whose deadline is still ahead, the soonest first; (2) parked runs with no deadline, newest first; (3) failed runs of the window, newest first; (4) runs whose log cannot be read, newest first. **Continue** lists *Sessions* (newest first), *Runs* (this directory's recent runs that are not under Attention) and *Agents* (recently used; display only, never focusable).
- **Rows** are one line each, every stored field scrubbed before the row is cut to its width: a parked run `‖ workflow · kind · time · id` ([above](#the-attention-rows)); a failed run `✗ workflow · failed 2h ago · cost · id`; a run whose log cannot be read `⚠ workflow · cannot be read · id`; a session `title · agent · age · cost` (the built-in chat agent is not named; an untitled session shows its agent once, as its name); a run `workflow · status · age · cost · id`; an agent `agent · age`. `id` is the first eight characters of the run id, dim at rest. A narrow run row gives up the workflow's tail, then the cost, then the age (or the deadline), then the id; a session row gives up the cost, the age, the title's tail and then the agent; the status or kind word is never the part that is cut. No row writes a key: the hint row names the focused row's `Enter`.
- **The look of the selection.** The focused row is marked `›`. A plain row (a session, a run) is drawn bold and inverse; an Attention row keeps its tint (amber for a parked run, red once it is overdue and for a failed run, amber for an unreadable one) and is drawn `›` + bold + its tint, with no inverse.
- **How many rows each section shows.** At 80×24 the list has 17 rows and shows Attention 4, Sessions 3 and Runs 3, with their markers; Agents take what is left. A section with more than its cap ends with a dim `▼ N more` and, scrolled to the focus, begins with `▲ N more`; N is the section's true total less what is shown, and a marker that would hide exactly one row draws that row instead. Where `↓` cannot reach the rest (they were not loaded) the marker says where they are: `▼ 5 more · /workflows` for runs, `· /resume` for sessions, `· /agents` for agents. On a taller page, or where the other sections are short, the caps open (Attention up to eight). When rows run short whitespace gives way before words and words before rows (the blank under `↑ start page` goes below 26 terminal rows, the blank under Attention goes when it would cost a row), then the rows go in a fixed priority (the focused row; every section's marker; each section's first row; the focused section's window; the caps; the agents last), and the list keeps at least 10 rows beside a long draft or an open palette, the lowest sections going first. The rows each section takes depend on which section holds the focus, never on the focused row's index, so walking `↓` inside one section does not move the sections below the cursor.
- **Keys.** `↑`/`↓` move along the rows (past the first row `↑` goes up to the landing; past the last, `↓` goes to the docked prompt); `Enter` opens the focused row (the [table below](#actionable-rows-and-the-idle-refresh-mvp-8-step-5-increment-2-2026-11-23)); `Esc` goes back up to the landing, the draft kept; a key that types, or a paste, while a row is focused moves to the docked prompt and is typed there. From the docked prompt `↑` on the draft's first line returns to the last row, and `Esc` goes up. A screen or a card opened from a row (a run's detail, a gate card) returns to the work page with the focus on that row, or, when it left the list (a gate answered), on the row now standing where it stood. The hint reads `↑/↓ select · Enter open · type to chat · Esc start page` on a row (`↑/↓ select session · Enter resume · …` on a session; the `Enter` verbs are in [the Attention rows](#the-attention-rows) and the table), and on the docked prompt `[/] commands · ↑ back to the list · Esc start page` (`Enter start the chat · ↑ back to the list · [Ctrl+J] newline · Esc start page` with a draft, `Enter show it · …` with a live run, `Enter connect a provider · …` with no key). The first `Ctrl+C` arms (`[Ctrl+C] exit (again)`).
- **The palette and the `@` picker** open above the docked prompt on this page (the list, the prompt with the typed query, the rule, the legend on the hint row). The palette is the registry's fifteen Home commands in four groups, Work (`/resume`, `/run`, `/workflows`, `/agents`), Set up (`/providers`, `/models`, `/mode`, `/permissions`, `/pricing`, `/init`, `/import`), Check (`/doctor`, `/help`) and End (`/clear`, `/exit`), at most half the terminal tall (12 rows at 80×24, a window of eight entries and a marker). `@` picks a file on either page (the Home draws no chip bar: a file stays only while its `@path` marker is a token of the draft, and an `Enter` that would send is ignored for 2 s after a pick unless another key came first).
- **Evidence owed.** The slide's synchronized-update support, held keys, the card lockouts, `r` and the `@` picker on a real Windows terminal: none has been run, and the [Windows runbook](../../runbooks/windows-interrupt-evidence.md) carries them as rows 57 (the slide), 58 (`r`) and 59 (the `@` picker), written on 2026-11-28 from this reference and not observed (its rows 1 to 5, 17 to 25 and 32 were reworded to the pages' words the same day).

### Actionable rows and the idle refresh (MVP-8 step 5, increment 2, 2026-11-23)

([ADR-0140](../../decisions/0140-management-browsers-the-run-drill-down-and-the-durable-run-detail.md) §6, MVP-11 unit 7.) The work page's rows are **one list in the order the page draws them**: the Attention items in their urgency order, then the sessions, then the recent runs (an agent is never in it). `↑`/`↓` move along it and `Enter` does what the row's kind says; a key that types goes to the docked prompt. The focused row is marked `›` and is always one of the rows drawn at 80×24.

| Row | `Enter` |
| --- | --- |
| A parked run of this directory (`‖`) | its [gate or budget card](#the-gate-card); a run with no gate to decide says why |
| A failed run (`✗`) or a recent run in *Continue → Runs* | its **detail in History** (the Runs screen opens on History at that run; `Esc` steps back to the list, then to the work page). No run is written, resumed or cancelled from the strip: `p` on the detail only marks a finished run (a pin). A run of another directory opens too |
| The run this Home hosts, when it is one of those rows | the [run view](#the-run-view-mvp-8-step-3-increment-6-2026-11-23), as the run row does |
| A session | the resume, as before; a resume the person cancels (the retry question, `Esc` while it restores) ends on the landing with the notice `Resume cancelled.` |
| A run whose event log cannot be read (`⚠`) | a **read-only popup**, `Run <8 characters> cannot be read`: which run it is (id, workflow, status) and why, from a closed set (a log row written by a newer version, `Update Relavium and it reads`; a damaged row, `Other runs are not affected`; or `could not be read just now, try again`), then `Nothing was changed or started.`; it names no path, error text or shell command, has no key of its own but `[c] copy`, and `Esc` or `Ctrl+C` closes it |
| A gate of a run that is not parked here; an agent | nothing: they stay display rows, and `↑`/`↓` skip them |

- **The focus is the row's identity, not its index.** A run row is named by the run id and a session row by the session id, so a read that puts a row above the focused one moves the row and keeps the focus on it. When the focused row is gone (the run was answered, a session ended) the **focus is dropped**, back at the prompt: a refresh never moves it onto another row, which could be a different kind of row. `Enter` on a row counts only once the frame that shows the focus is on screen, and on a row whose record has gone since it was read (a session that was removed, a run no longer in the history, a run no longer parked here) it opens nothing and says so. When a read of what **another terminal** changed takes the focused row off the strip, the **first `Enter` after it is ignored once, with no notice** (it was meant for the row that went, and must not reach the empty prompt's own `Enter`: the run view, or provider setup when no provider is set up). Only that read sets it, and only with the landing in front: not when the row left because this Home started a leg on that run (the person answered its gate, so they know it has gone), and not behind a screen, a card or a chat. Any other key, a paste, and any screen or card that opens or closes end it, and the next `Enter` is the prompt's own.
- **The idle tick.** Every 5 seconds the Home asks the database's change token (`PRAGMA data_version`, the in-process generation and the hosted run, the Active tab's own probe) and re-reads the strip **only if it moved**; an unchanged token reads nothing, and a read that matches what the strip shows changes nothing on screen. The tick is **paused, not stopped**, while a screen, a card (the gate and budget cards, the exit question, a native form), an overlay (palette, search, mention) or a popup is in front, while a chat or its build is, and while the terminal is below 80×24; the landing coming back from a screen reads once at once. A failed read (the strip's rows, or the parked runs' read: either one fails the whole read) keeps the rows the strip has, is never counted as read, and is tried again **after twice the wait each time**: 5, 10, 20, 40, then 60 seconds at most. A read that works, or a change token that has moved since the last attempt, starts the wait over at 5 seconds. The strip's relative words (`5m ago`, `expires in 5m`) are worded when the landing is painted, from the clock then, so a landing nothing repaints keeps the words of its last paint until the next key, read or resize repaints it. The tick is a timer like the run watch: closing the Home, or a signal, cancels it.
- **A run of another directory has no row** on the Home, not under Attention and not among the Runs (the `other project` mark it once had is gone): it is read in the Runs screen's History with `[a] all`, where it opens a detail and never a card or a resume. Only this directory's parked runs have an Attention row and a card.

A **session title** is derived from the first user message (~40 chars, truncated by code point so an emoji never splits) so the *Sessions* list is readable; an LLM-summarised title is a later phase.

## The mode machine (Home ↔ chat in one ink tree)

The Home and the chat render as **one ink tree with conditional rendering** — a single `useInput` owner — never two mounted apps, so the raw-mode owner never conflicts. The session state machine lives in a plain external store (`home-controller.ts`, unit-tested without ink); the ink component is a thin view that subscribes to it and forwards every key.

| Mode | What renders | Transition |
| --- | --- | --- |
| `home` | the landing (page 1) or the work page (page 2), each with a live prompt | a non-empty submit → `loading`; `Ctrl+C` twice → clean exit (`0`), unless a hosted run's leg is live (preparing, executing or cancelling), when the exit-guard card opens instead (see [Leaving the Home while a run executes](#leaving-the-home-while-a-run-executes-mvp-8-step-3-increment-5b-2026-11-23)) |
| `loading` | the pending message echoed under `Starting chat…` | the deferred `buildChatSession` resolves → `chat`; it rejects → back to `home` with a banner |
| `chat` | the live chat region ([chat-session.md](chat-session.md)) | the chat ends (`/exit`, `/cancel`, or a second `Ctrl+C` inside the arming window) → back to a freshly-read `home` |

The chat session is built **after** the ink mount (an explicit loading state), so the landing shows instantly and a slow or failed build degrades to the loading state / a Home banner rather than blocking the entry. A built chat reuses the **built-in default chat agent** over `[chat].default_model` (the mode-gated editing/search grant plus `run_command`, which asks on a card in every mode except `auto`, where a command the person remembered or approved for the session runs unasked and anything else, a command on the repository's allowlist included, still asks — see [chat-session.md](chat-session.md)); the Home does not bind a custom agent (`relavium chat --agent <ref>` is the path for that).

Resume, model reseat and `/clear` retain the exact bound agent grant. `/clear`
uses that session's private fresh-builder closure, including an authored agent
named `relavium-chat` or an older read-only snapshot. It never identifies the
built-in agent by id. Each replacement resolves the current configured start
at its bound workspace and owns fresh approvals, read evidence and previews.

| **`@`** (2.5.D; on the Home since MVP-11 unit 7) | at a word boundary, open the chat's own file picker on either page (`mention-home.tsx`); the Home draws **no chip bar**, so a picked file stays only while its `@path` marker is a token of the draft | at a word boundary, open dir-navigable **file completion** → insert a `@path` marker + queue a **chip** that expands to UNTRUSTED context at submit ([ADR-0061](../../decisions/0061-cli-input-layer-file-injection-and-shell-escape.md)) | — |
| **`!`** (2.5.D) | append | a leading `!` runs a **shell command** through the same command card as the model's `run_command` (only a remembered grant that no file write has outdated, or an exact command approved for the session, runs unasked, and only in `auto`; the `[chat].allowed_commands` allowlist pre-approves nothing and only labels the card; [ADR-0118](../../decisions/0118-a-command-outside-the-allowlist-asks-instead-of-failing.md)) → `spawn` (`shell:false`); output shown read-only + queued as a **chip** carrying UNTRUSTED context to the next message ([ADR-0061](../../decisions/0061-cli-input-layer-file-injection-and-shell-escape.md)) | — |
| **`Esc`** (2.5.D) | — | at an **idle** prompt with pending `@`/`!` chips, **discard them** (else mid-turn abort) | — |
| **Ctrl+C** ([interrupt keymap](chat-session.md#the-interrupt-keymap--mvp-4-adr-0115)) | **arms** (the hint reads `[Ctrl+C] exit (again)`, any draft stays while it is armed); a **second** press inside 2 s → **clean exit (`0`)**, unless a hosted run's leg is live (preparing, executing or cancelling), when the exit-guard card opens instead (see [Leaving the Home while a run executes](#leaving-the-home-while-a-run-executes-mvp-8-step-3-increment-5b-2026-11-23)); a draft in the Home prompt is lost with the process | **interrupts** the running turn (the abort `Esc` performs) and arms; at an idle empty prompt it arms; with a draft the first press **clears the draft** and arms nothing, the next press (now an empty prompt) arms, and a press inside 2 s after that → **`/cancel`**, end the chat, return to Home: **three presses from a draft**, two from an empty prompt | **bail out** (exit at once: nothing is loaded and nothing can be lost), unless a hosted run's leg is live (preparing, executing or cancelling), when the exit-guard card opens instead (see [Leaving the Home while a run executes](#leaving-the-home-while-a-run-executes-mvp-8-step-3-increment-5b-2026-11-23)) |
| **Ctrl-D** (EOF) | **clean exit (`0`)** on an **empty** prompt (a non-empty buffer keeps it — no data loss), unless a hosted run's leg is live (preparing, executing or cancelling), when the exit-guard card opens instead (see [Leaving the Home while a run executes](#leaving-the-home-while-a-run-executes-mvp-8-step-3-increment-5b-2026-11-23)) | — | **clean exit (`0`)** (the prompt is empty while building, so EOF bails the build like Ctrl-C), unless a hosted run's leg is live (preparing, executing or cancelling), when the exit-guard card opens instead (see [Leaving the Home while a run executes](#leaving-the-home-while-a-run-executes-mvp-8-step-3-increment-5b-2026-11-23)) |

`Ctrl+C` is **always** an escape — it is honored even in the `loading` state (so a hung build is never an unkillable wedge), and leaving the loaded Home takes two presses, and leaving a chat takes two from an empty prompt and three from a draft, so one stray key cannot do it (`Ctrl+D` on an empty prompt still exits the Home at once when no hosted run's leg is live). The Home keeps its draft through the first press and loses it when the second exits ([ADR-0115](../../decisions/0115-one-interrupt-keymap-for-the-interactive-cli.md), amended 2026-11-21). The reseat-less **mode keymap** (`Shift+Tab` + `/mode`) and the fail-closed **per-tool approval** landed in **2.5.E** ([ADR-0057](../../decisions/0057-cli-chat-modes-and-per-tool-approval.md); wired into the Home via the same `home-controller.ts` key routing — see [chat-session.md](chat-session.md)); the interactive `/` command palette landed in **2.5.C**. The **input ergonomics** (`Ctrl+J` multiline, `↑/↓` history + `Ctrl+R` search, readline motions) and the two data-moving affordances (`@`-mention file injection, `!`-shell command escape) landed in **2.5.D** ([ADR-0061](../../decisions/0061-cli-input-layer-file-injection-and-shell-escape.md)) — the `@`/`!` semantics are the SAME as the standalone chat (see [chat-session.md](chat-session.md#input-ergonomics-25d-adr-0061)).

The **footer hint-bar** in 2.5.B was the single fixed line; the context-aware hint-bar (the two or three most-relevant keys per context) landed in **2.5.C**, and the always-visible **active-mode footer indicator** (`formatSessionFooterWithMode`) arrived with **2.5.E** (ADR-0057) — together they extend that fixed footer.

## Bracketed paste (ink 7 native `usePaste`)

The Home receives a bracketed paste on **ink 7's native `usePaste` channel** (separate from `useInput`; adopted in 2.6.F, [ADR-0068](../../decisions/0068-full-screen-tui-renderer-ink7-harness.md)): ink enables/disables bracketed-paste mode (`ESC[?2004h`/`l`) automatically on mount/unmount and delivers the **whole paste as one event** (the `ESC[200~ … ESC[201~` markers stripped, and split stdin chunks reassembled). It is routed to `HomeController.handlePaste`, which appends the block **verbatim** — embedded newlines kept, CRLF/CR → LF — so a pasted multi-line block never submits early. A defensive `ESC[?2004l` is also written on the signal/exit teardown as belt-and-suspenders over ink's own unmount cleanup. Gate:

- **A paste appends ONLY when the main prompt is the active editable target** — dropped while a session **builds** (`loading`), a chat turn **streams** (`running`), a `!`-shell / submit is in flight, or any keyboard-owning overlay/submode is open (the `/` palette, `Ctrl+R` reverse-search, `@`-mention, the `[c]` reason capture and every popup: `/models`, `/effort`, `/permissions`, `/agent` and the rest). The gate is the shared `pasteIsEditable` predicate, so the Home and the standalone [chat](chat-session.md) can never diverge (a type-ahead queue while a turn runs is deferred — see the phase deferred list).
- **Security ([ADR-0057](../../decisions/0057-cli-chat-modes-and-per-tool-approval.md)):** a paste is dropped while a per-tool **approval is pending**, so a pasted approval token (`y` / `a` / `n` / … or a control byte) can **never** answer the fail-closed approval floor — paste arrives on the `usePaste` channel and is never routed to the approval key reducer.

## Render mode (inline / alt-screen)

A **branded block** (the wordmark, the rail and its three labels: [the landing](#page-1-the-landing)) heads the landing, and `[preferences].show_banner` decides whether it is drawn: `true` or **absent** draws the block, `false` draws the one-line spaced wordmark instead. This holds in both states of the Home, because page 1 is the landing whether or not there is anything to continue (before MVP-11 unit 7 an absent value showed the plaque only while the Home was empty). It degrades to plain ASCII under `NO_COLOR` / `--no-color`. It is cosmetic and gates no feature.

The Home renders in one of two modes ([ADR-0068](../../decisions/0068-full-screen-tui-renderer-ink7-harness.md) §e): since Step 4b-3 the **default on a TTY is the full-screen alternate-screen renderer**, with the **inline** renderer (native scrollback, the screen-reader-friendly fallback) as the opt-out — **`--no-alt-screen`** ([commands.md](commands.md#global-options)) for one invocation, or **`[preferences].alt_screen = false`** ([config-spec.md](../contracts/config-spec.md)) durably. A non-TTY / `--json` / CI path is **always** inline (byte-identical). The alt screen renders the transcript through a resize-tracked **viewport** with **scroll-back + auto-follow** — **PgUp/PgDn** page, **Ctrl+Home/Ctrl+End** jump to top/tail, an upward scroll pauses the tail-follow and reaching the bottom resumes it (the scroll keymap is gated behind any keyboard-owning overlay) — and a per-entry wrap cache (keyed on the immutable transcript entry) keeps even a very large transcript cheap (Step 4b-3). The in-Home chat also carries the mouse **selection + copy-on-select** and the **`/scrollback`**, **`/edit`** and **`/copy`** copy-and-search hatches — the same code as `relavium chat` ([chat-session.md](chat-session.md)); the hatches are chat-only, so they never appear in the bare Home's palette. **Mouse reporting is armed only while the chat owns the screen**: the Home landing has no viewport to wheel-scroll and no in-app selection, so it keeps the emulator's own click-drag selection instead. The full-screen mode is inherently inaccessible to screen readers — see [accessibility.md](accessibility.md) for the trade-off and the inline-renderer escape hatch.

Both inline and full-screen interactive modes use the CLI's resolved output policy when mounting Ink.
An inline reseat keeps the existing terminal scrollback and displays the new store's entries once;
the root input owner stays mounted. The resume/reseat notice and retention ordering is defined in
[effect-journal.md](../shared-core/effect-journal.md#8-needs_attention).

## Minimum terminal size

Below **80×24** the landing shows `Terminal too small (WxH) — resize to at least 80×24.`
and a `[Ctrl+C] exit (twice)` hint. It suspends the work page, the prompts and the overlays,
and refuses hidden typing, paste, row and palette activation using the live terminal
geometry. Esc and Ctrl+C/Ctrl-D cancellation remain available (`Ctrl+C` arms, then exits, as on the loaded Home). A resize restores the
existing input and selection. The resize is observed on stdout's cross-platform `resize`
event (backed by SIGWINCH on POSIX).

**MVP-3 Step 2 accepted on development (2026-11-12):** the same minimum and measured input
custody also apply inside the Home chat and standalone chat. Prepared-write
approval and `/details` share the
[chat interaction contract](chat-session.md#proposed-mvp-3-interaction-contract)
in both renderers; the full view and `/details` are one readable inspection screen
([ADR-0134](../../decisions/0134-the-full-view-and-the-tool-details-are-one-readable-inspection-screen.md),
[chat-session.md](chat-session.md#the-full-view-and-the-tool-details)). Tool details are chat-only; opening them executes no tool
and does not activate the work page's rows. Their bounded private previews
expire on teardown and are absent from restored history and transcript hatches.

At or above the minimum, the work page's list uses the rows left after the docked prompt, the status line and the notice (the allocation is [above](#page-2-the-work-page)). The focused row stays visible.
Row labels truncate at the terminal edge; diagnostic notices and recovery instructions
wrap without dropping their source. Long notices show a range and **PgUp/PgDn** affordance
in both renderers. A notice is bounded to **32,768 characters** before it is sanitized, wrapped and paged, and the cut is shown by `…` at the end of its last page, so a notice reads as longer rather than as complete and its layout, which is rebuilt on every frame, costs the same whatever it was handed (the run view's notice rows apply the same bound). A new report or resize returns to its first page. Notice paging does
not submit input or change the row focus, and yields to a keyboard-owning overlay.

## Signal lifecycle & exit codes

The invocation-backed Home shares **one signal lifecycle (SIGINT/SIGTERM/SIGHUP/SIGQUIT)** across the Home, pending/replaced chat hosts and MCP teardown. Its actual owners follow the [canonical invocation ordering](commands.md#invocation-owners-and-fatal-ordering); the synchronous native exit reap is a last-resort request, not a cleanup acknowledgement:

| Outcome | How | Exit code |
| --- | --- | --- |
| **Clean Home exit** | a second `Ctrl+C` inside the arming window / `Ctrl+D` or EOF on an empty prompt in `home` mode; or, for a bare `relavium permissions`, closing the `/permissions` popup it opened (`Esc` or `Ctrl+C`); with a hosted run's leg live the exit-guard card opens first ([Leaving the Home while a run executes](#leaving-the-home-while-a-run-executes-mvp-8-step-3-increment-5b-2026-11-23)) | `0`, unless a hosted run's safety fact is the outcome (next row) |
| **A hosted run's safety fact** | the Home leaves, by any of the ways above or by a signal, after a leg it hosted ended with a workflow safety fact; the most serious one sets the code, and it outranks an infrastructure fault or a signal's code ([the line printed after the screen is restored](#leaving-the-home-while-a-run-executes-mvp-8-step-3-increment-5b-2026-11-23)) | `8` money not confirmed, `7` an effect needing attention, `5` a held terminal, `6` taken over elsewhere ([canonical table](commands.md#exit-codes)) |
| **Signal-driven, without a stronger infrastructure fault or a hosted run's safety fact** | an external SIGINT / SIGTERM / SIGHUP / SIGQUIT (`kill -INT`, closing the terminal window, a parent's signal) | `128 + signo` — **`130`** (SIGINT) / **`143`** (SIGTERM) / **`129`** (SIGHUP) / **`131`** (SIGQUIT); infrastructure faults follow the [canonical precedence](commands.md#failure-classification-and-remedies) |

An external signal stops admission and requests terminal restoration and cleanup of every actual host, including an in-flight build. Repeated signals share the original finite deadline and cannot restart cleanup or force an immediate second-signal exit. The physical exit backstop bounds the invocation; it does not certify terminal, MCP or database release. The shared database closes only after actual host/work settlement, and failed or held cleanup retains its owners and signal custody. Infrastructure faults may strengthen the final disposition; read the [canonical remedies](commands.md#failure-classification-and-remedies) before repeating uncertain work. The ownerless library compatibility path is not this product invocation lifecycle.

A keyboard Ctrl+C does **not** normally reach the process as SIGINT (raw mode), so the controller handles it through the one interrupt keymap (Home: arm, then `0`; chat: interrupt and arm, then `/cancel`). There is **one exception**: while a `/scrollback` or `/edit` suspension owns the terminal, ink has turned raw mode off and the kernel delivers a real SIGINT. That signal belongs to the hatch — the Home's handler drops it (`suspendPort.isSuspended()`), the hatch's own listener resumes the renderer, and the session survives. An external SIGTERM/SIGHUP/SIGQUIT still tears down, suspended or not.

A chat launched from the Home has its **own** exit code `4` ([chat-session.md](chat-session.md)) — but inside the Home that `4` is **consumed by the mode loop** (a chat ending returns to Home), **never leaked**. The Home's own exit code is `0` on a clean exit with no hosted run's leg live; a hosted run's safety fact makes it `5`, `6`, `7` or `8` (the most serious: `8`, then `7`, `5`, `6`), and with a leg live the exit-guard card opens first. See the canonical [Exit codes](commands.md#exit-codes) table.
