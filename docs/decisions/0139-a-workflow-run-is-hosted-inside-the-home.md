## Context

The Home is the interactive product ([ADR-0122](0122-the-home-is-the-interactive-product.md)). A person who opens it must be able to run a workflow, watch it, and answer the human gates and budget gates it raises, without leaving for a shell. ADR-0122 §2 fixes the shape (an in-TUI form **re-hosts the same core** the subcommand calls; it never spawns `relavium <cmd>`) and §10 reserved the hard part: the Home process would then host a run's lease, signals, consent prompts and exit dispositions, and nothing in the documents says how.

The code and documents were read on 2026-11-22 (five reconnaissance reports, one per area). The facts that shape the decision:

1. **Answering a gate is hosting a run.** `relavium gate` and `relavium budget resume` start a fresh process that reconstructs the checkpoint, acquires the lease and **executes** until the next pause or terminal ([commands.md](../reference/cli/commands.md#relavium-gate)). A gate row in the Home is therefore the same problem as "run a workflow" (cross-process resume, secret re-supply, MCP reconnection against the original workspace), not just a card.
2. **The shell's run core is welded to a process.** `driveRun` takes a concrete `WorkflowLifetime`. Its constructor claims the invocation's one signal custody (a second claim throws `cli_internal`), activates the finite-exit fallback and registers a `workflow` owner and a `terminal` owner. The Home's own `SessionSurfaceLifetime` has already claimed the custody, so a `WorkflowLifetime` cannot coexist with it. A session surface also cannot publish the workflow health codes (5, 7, 8): it turns them into `cli_internal`.
3. **The prompts are clack, and secrets are stdin.** The gate card, the budget card and the MCP consent card use `@clack/prompts`, which takes raw mode. In the shell a secret input is not prompted at all: it comes from stdin (`--secret-inputs-stdin`, `gate --secret-stdin`). The Home has exactly one raw-mode owner (`RootApp`'s `useInput`), so a clack card cannot run over it, and [ADR-0122](0122-the-home-is-the-interactive-product.md) §7.7 keeps a secret out of React state, history and the transcript. The Home therefore needs native cards and a native masked field; the native prompt channel already has a password prompt.
4. **`RunApp` is a pure view** (no `useInput`); it can be mounted inside the Home's tree. It was written for a cooked-mode terminal where a keyboard `Ctrl-C` is a real SIGINT. In the Home `Ctrl-C` is a key.
5. **No Ctrl-C rule exists for a run in the Home** (ADR-0115 §4: "out of scope … the later run-hosting ADR's"). The exit rules are written for chats ([commands.md](../reference/cli/commands.md#exit-codes): "Home: clean shell end / nested chat end"), and ADR-0079's two deferral triggers (an observer handle; a long-lived host that keeps one engine across many park-and-resume cycles) are both fired by a Home that hosts runs.
6. **A stale gate card can fail a healthy run** (an owed medium, [deferred-tasks-parked.md](../roadmap/deferred-tasks-parked.md), "Answering a stale gate card after another process decided the gate"): an engine that still holds the run in memory reclaims the lease on an answer, its guarded append is refused on a stale head, and it then writes `run:failed{internal}` at a sequence another process already used. It must be fixed before v0.2.0, and it matters more once a second surface can answer gates.
7. **A workflow run is unattended by contract.** [ADR-0118](0118-a-command-outside-the-allowlist-asks-instead-of-failing.md) §2 keeps `run_command` in a workflow to the allowlist, with no card and no remembered grant; a workflow host wires `fs` and `process` only, and `run` refuses `--allow-fs-root`. A person being present in the Home does not change that. The cards a hosted run can show are the human gate, the budget gate, the MCP stdio consent and masked secret fields, and none of them has a "full view" to back out of (the sentence in `current.md` that said a hosted run "shows approval cards" with the ADR-0137 `Esc` ladder is corrected by this ADR).

## Decision

**The Home hosts a workflow run in its own process by re-hosting the shell's run core under the Home's owners. It hosts one executing leg at a time. A human wait is never held in memory: the leg hands off at the pause and the answer starts a new leg through the one resume core.**

### 1. One run core, two hosts

The shell's run path is split at its process-bound seams, once, and both hosts call the result.

- **`prepareRun`** (workflow resolution and validation, input admission and secret inputs, the key and catalog pre-flights, MCP discovery with its consent gate, history store, engine build) and **`resumeRun`** (the checkpoint reconstruction, selection, decision checks and price pre-check, secret re-supply, MCP reconnection with preserved grants, `resumeFromCheckpoint`) are extracted from `run.ts` and `gate.ts`. `resumeRun` is the shared cross-process resume core of 2.6.K: `relavium gate`, `relavium budget resume` and the Home all call it, and no other path resumes a run.
- **`driveRun`** depends on a **`RunLifetime`** interface, not on `WorkflowLifetime`. Its contract is exactly what `driveRun` uses today (`commands/drive.ts`): `signal`, `stop()`, `stopped`, `checkpoint()`, `isStoppedFailure()`, `failure()`, `cleanupFailed()`, `publish()`, `adoptEngine()`, `adoptHandle()`, `notification()`, the effect-notice owner, and a `terminal` view with `sealed`, `releaseInput()`, `createJobControl()`, `createRenderer()`, `runPrompt()` and `runViewOperation()`. Two implementations exist: `WorkflowLifetime` (the shell, unchanged in behaviour) and `HostedRunLifetime` (the Home, §6). One contract test runs the same drive scenarios against both.
- **The prompts are ports.** The gate, budget and consent prompts sit behind `GatePrompter` and the consent prompter. Each has the clack implementation (the shell, unchanged) and a native implementation (the Home, §4). Secret inputs stay stdin in the shell and use a masked native field in the Home. The Home's run and card paths never import clack; the pre-mount onboarding wizard keeps its clack prompts ([ADR-0054](0054-cli-bare-invocation-interactive-home.md)).
- **The shell's machine surface does not change.** For every invocation `run`, `gate` and `budget resume` accept today, stdout, stderr, `--json` and the exit code are byte-identical ([ADR-0122](0122-the-home-is-the-interactive-product.md) §2, [ADR-0049](0049-cli-machine-output-contract.md)); the existing command harness proves it after the extraction, and a new case pins the `--json` stream of a resumed run.

### 2. One executing leg at a time, a fresh engine for each

- A **leg** is one engine's hosting of a run, from `start` or `resumeFromCheckpoint` to the next pause, terminal or cancellation. A fresh `WorkflowEngine` (a fresh lease owner id) is built for **every** leg. This answers ADR-0079's long-lived-host trigger: no engine lives across legs, so the straggler residual that trigger describes (a long-lived host cannot tell a straggler from the current leg when the same owner and generation repeat) cannot arise in the Home.
- The Home hosts **one executing leg at a time**. A request to run or resume while one executes is refused with a one-line notice naming the hosted run; it is never queued. This is a deliberate bound (one terminal view and one exit authority for a run at a time; a chat's MCP clients are its own), not a missing feature, and it is recorded in the reference. A run that is parked, finished or cancelled is not "hosted".
- **Starting is single-flight.** The controller latches a `launching` flag from the confirmation to the engine's `start` result; a second `Enter` while it is set does nothing (a double submit starts one run). The latch is pinned by a test that drives two `Enter`s in one tick.
- The Home reuses its open `history.db` connection (the one `opened.db`); a hosted leg never opens or closes a second one.

### 3. A leg lives in the background; a pause hands off

(The maintainer's first ruling of 2026-11-22.)

- A started leg runs in the Home process until it ends. It is shown by a **run view**, a Home screen that mounts the existing `RunApp` projection over the existing run store inside the Home's one ink tree. **`Esc` leaves the view and does not stop the leg.** While the leg executes, the landing's strip shows one row (`▶ deploy · running 2m · $0.0210`), and `Enter` on it reopens the view.
- **The leg's events are consumed by exactly one reader** started before any departure ([ADR-0103](0103-a-paused-run-hands-off-its-local-producers-before-its-host-closes.md)): `eventConsumption: 'iterated'`, the reader folds into the run store whether or not the view is open.
- **A pause hands off at once.** When a leg pauses on a human gate or a budget gate, the drive takes the same exit the shell's non-interactive path takes (`shouldBreakOnPause`), `depart()`s, and the leg ends as `paused`. The lease is handed back at the pause, as [ADR-0079](0079-cross-process-run-ownership-lease-and-fencing-token.md) §4 requires for every re-pause (budget and media included), and the next answer re-takes it before it writes. The Home does **not** keep the run in memory waiting for a person. The run view (if open) turns the pending gates into the gate or budget card (§4); if it is not open, the strip gains an Attention row and a transcript notice if a chat is in front (a card never takes the keyboard from another screen). The answer is `resumeRun`, which starts the next leg on a fresh engine. Consequences: the pause is durable and answerable from any process (the Home, another terminal's Home, `relavium gate`); a deadline is re-armed from its persisted `expiresAt` when a leg resumes, as it is today; and the stale-card defect cannot occur on this route, because the answer re-reads the checkpoint after it holds the lease and finds the gate already decided. The shell's inline card, which waits inside the engine, can still meet that race; the same lease-path change (step 2) fixes it there.
- **A media-only park is answered without a gate.** A pause with no gate and `pendingMediaJobNodeIds` set is continued by the same core with no decision: the engine's resume input takes neither a gate nor a decision ([engine](../../packages/core/src/engine/engine.ts)), which no CLI core calls today. Step 2 wires it into `resumeRun` and pins it with a test that re-attaches a parked media job. If that re-attach cannot be completed in step 2, the Home shows the parked media run read-only with the reason, the shell's advice is unchanged, and the fallback is recorded in the phase record rather than left silent.
- **A chat can be in front while a leg executes.** Both use the Home's one connection (WAL, one transaction per durable write). Each engine keeps its own budget ledger as it does today: a chat's session cap does not count against a run's allowance, and the reverse. Only one screen is in front; a leg keeps running behind any screen, and its card waits for the run view or, if none is open, for its strip row.
- **Two warning channels, one owner each.** Warnings about the run itself (a gap, the budget, a gate, a timeout) render inside the run view. A notice about another screen (a park while a chat is open, a finished leg while elsewhere) goes to the Home's notice channel. The Home writes nothing to stderr while it owns the screen.
- **The run view meets [ADR-0122](0122-the-home-is-the-interactive-product.md) §7.** Inline: with `--no-alt-screen` it is the inline live region of the same projection, so the same events and cards appear. Colour off: every state has a word as well as a glyph (`running`, `paused`, `cancelling`, `cancelled`, `completed`, `failed`). 80×24: the header, the current node, the newest event and the key line stay on screen; below 80×24 the screen shows the enlarge line and accepts only `Esc` and `Ctrl+C`. Sanitize: node names, gate messages and errors pass the floor. Bounded: the event list shows the last 200 events with a range marker. Secret-safe: no masked value is in the view or its state.
- **The leg's outcome is view state.** `completed`, `failed`, `cancelled` and `paused` are shown in the run view as a persistent disposition card (the final-summary text with its continuation named as an in-TUI action, [ADR-0122](0122-the-home-is-the-interactive-product.md) §6) and kept until the person starts another run or dismisses it; they never end the Home.
- **Notices stay in the Home.** Everything `run` writes to stderr during a run (the withheld-effort, unpriced and legacy-hold warnings, the snapshot-literal warning, the skipped-MCP lines, the departure diagnostics) goes to the Home's notice channel and, when a chat is in front, to a one-line transcript notice. The Home writes nothing to stderr while it owns the screen.

### 4. The cards are native, answer with chords, and never answer on a paste

The clack prompts are not reused (§Context 3, and the residual that a paste or a hotkey can answer a clack card). The Home gets native ink cards on its one input owner, sibling to the ADR-0132 question card and the ADR-0129 approval card, with the same discipline: every answer is a Ctrl chord or an explicit field submit, a bare letter or a paste answers nothing, the affirmative answers pass the same dwell, quiet-gap, typeahead and lockout guards and the measured-frame acknowledgement (the card must have been painted and measured at 80×24 before an affirmative key counts), and a rejection is never delayed. They are specified in the reference when built; the decisions here are:

| Card | Answers | Notes |
|---|---|---|
| **Human gate, `approval` or `review`** | `Ctrl+Y` Approve, `Ctrl+N` Reject | The decision shape follows the gate type ([commands.md](../reference/cli/commands.md#relavium-gate)); a `rejected` decision does not fail the run (the author routes on it), and the card says so. |
| **Human gate, `input`** | text field + `Enter` submits `input_provided`; `Ctrl+N` rejects | The field is bounded. The value is the gate's recorded payload, as the shell records it ([commands.md](../reference/cli/commands.md)); it is not written to the Home's input history, the transcript or a notice. |
| **Budget gate** ([ADR-0097](0097-a-budget-approval-is-an-allowance-not-an-exemption.md)) | `Ctrl+Y` approves **exactly the frozen allowance**; `Ctrl+N` aborts | The amount is read from the structured `allowanceQuote`, never parsed from message text, in USD with the qualified-cost words; excluded entries are quoted and escaped. A quote that cannot be approved (unpriced, unrepresentable, legacy) offers abort only. A price that moved is refused by `resumeRun` **before** the gate is claimed, leaving it pending and abortable. |
| **MCP stdio consent**, the start card (before the first leg, not in a run view; [ADR-0084](0084-consent-before-a-local-mcp-spawn.md)) | `Ctrl+Y` allows this server for this run; `Ctrl+N`, `Esc` and `Ctrl+C` refuse | Refusing is the default and starts nothing: a refused server is not spawned, as the shell does. A resumed leg reuses the frozen grants and asks nothing new. |
| **Masked secret field** | typed text + `Enter` | One field per declared `secret` input at a start, one per masked slot at a resume (ADR-0083 §6); the value lives only in the native prompt channel and `resumeRun`'s argument, never in React state, history, the transcript or an error. |

- **An overdue gate** shows `overdue`, its `expiresAt` and the timeout policy's outcome (approve, or the run fails with `run_timeout`). The card still answers. The answer goes through `resumeRun`, which re-reads the checkpoint under the lease: if the timeout settled the gate first, the card says so and shows what was decided. A test answers an overdue gate in both orders.
- With more than one pending gate the card lists them with a cursor; an answer applies to the selected gate and the others stay pending.
- `Esc` on a card **leaves it and decides nothing** (the gate stays pending; the strip keeps its row). `Ctrl+C` on a card does the same and never answers. Neither key can reject, because a `rejected` decision continues the run. The start consent card is the one exception: it is not in a run view, and refusing is its default.
- Text that comes from a workflow author or from model output (a gate message, a node or workflow name, an excluded-entry label) passes the sanitize floor and the forged-legend refusals of [ADR-0132](0132-the-model-can-ask-the-user-a-structured-question.md) (host glyphs and answer-chord tokens), because a gate message can interpolate model output.
- The Home answers with `decidedBy: 'cli'`, the constant the event already carries; no event field is added.

### 5. The interrupt ladder of a hosted run (the second ruling)

This amends [ADR-0115](0115-one-interrupt-keymap-for-the-interactive-cli.md) §1 with these rows, kept in `interrupt-keymap.ts` and its table-driven test. Cancelling a run is irreversible (a `run:cancelled` run cannot be resumed), so it takes two presses like ending a session.

| State | First `Ctrl+C` | Second `Ctrl+C` (armed) |
|---|---|---|
| The run view is open and a leg is executing | Arm; the hint reads `Ctrl+C again cancels the run · Esc leaves it running`. Nothing is cancelled | Request the cooperative cancel; the view reads `Cancelling · the run stops at its next safe point (up to 10 s)` |
| The leg is cancelling | A hint only (`Waiting for the run to stop`); arms nothing and cancels nothing more | — |
| A gate, budget or consent card is open in the run view | Close the card and the view, decide nothing, do not arm | — |
| Another screen is in front (the landing, a chat, a sheet) and a leg executes | The key keeps the meaning of the screen in front (ADR-0115 §1 unchanged) | The exit guard of §6 applies when the second press would leave the Home |
| The run view is open and no leg executes (parked at a gate, a disposition card, another project's run) | `Esc` and `Ctrl+C` close the view or card and arm nothing; nothing is cancelled | — |
| A launch form or a masked secret field is open | `Esc` steps back one field (a secret's value is cleared when its field is left); `Ctrl+C` leaves the form, clears every secret value and starts nothing | — |

`Esc` steps back one level and never arms: in the run view it leaves the view with the leg still running; on a card it closes the card. The window is two seconds from the first press (`INTERRUPT_ARM_WINDOW_MS`, `interrupt-keymap.ts`); a press after it starts again, and any other key disarms ([ADR-0115](0115-one-interrupt-keymap-for-the-interactive-cli.md) §1). The cooperative cancel is the engine's own (`handle.cancel()`): the run settles as `run:cancelled`, a non-cooperative executor is abandoned after the engine's 10-second grace window, and cancellation wins over a racing failure ([ADR-0036](0036-run-loop-substrate-event-bus-and-execution-host.md)).

### 6. Leaving the Home with a leg executing; signals; the exit code

- **The exit guard.** A second `Ctrl+C` on the loaded landing, and `Ctrl+D` on an empty prompt, would end the Home. While a leg executes (or is cancelling) they open a confirmation card instead: `Ctrl+Y` cancels the run and exits, and `Esc`, `Ctrl+C` and `Ctrl+N` stay ([ADR-0122](0122-the-home-is-the-interactive-product.md) §7.4: a confirmation treats both interrupt keys as cancel). The confirmed path cancels the leg and waits for it to settle, up to the engine's grace window of ten seconds (the screen says `Stopping the run…`). If the leg has not settled by then, the Home abandons it as the engine does, runs its teardown and exits. The lease expires within one TTL (sixty seconds), and the next start's reconcile settles the run as failed, with the remedy printed once the screen is restored. That is the outcome of a killed `relavium run`, so no path leaves the Home waiting without a bound.
- **Signals keep their process meaning** ([ADR-0115](0115-one-interrupt-keymap-for-the-interactive-cli.md) §4). An external SIGINT, SIGTERM, SIGHUP or SIGQUIT goes to the Home's one finite-exit authority. The hosted leg's owner (below) is told to stop (a cooperative cancel), and the invocation's fatal bound (three seconds) applies. A run that could not settle inside the bound keeps its lease until it expires (sixty seconds) and the next start's reconcile settles it as failed ([ADR-0079](0079-cross-process-run-ownership-lease-and-fencing-token.md)); this is the same as a killed `relavium run`, it is written in the reference, and the Home does not pretend otherwise.
- **The owner.** `HostedRunLifetime` registers a `workflow` owner with the **Home's** invocation registry before any work is admitted (before the engine is built), supplies `readSafetyExit`, and retires after the leg's actual cleanup. It claims no signal custody and no terminal owner (the Home's own owners hold both) and installs no job-control coordinator (the Home has one). It does not inherit `WorkflowLifetime.finish()`'s never-resolving wait for a leg that is not host-safe (the shell's way of keeping the process alive for its exit authority; the Home's own owners already hold it), and it does not inherit `classifyFailure: 'cli_internal'`: a leg's failure is classified by its own cause. The registry already accepts several owners; custody is the only exclusive claim.
- **The Home's exit code.** A leg's ordinary outcomes (0, 1, 3, a cancel) are view state and are **not** published ("a nested chat end is deliberately not published" extends to a nested run end). The workflow **safety** facts (money not confirmed 8, an effect needing attention 7, a held terminal 5, taken over elsewhere 6) are published through the owner and rank above a clean exit by the sticky priority already in force (8, 7, 5, 6, then infrastructure, then a signal, then ordinary). The person is shown the fact and its remedy in the run view; if the Home then exits, it prints one plain line after the screen is restored naming the run id and the shell remedy. These codes mean "do not repeat automatically" and the Home never re-invokes anything. The process exit is computed by `native-bootstrap` from the registry after the Home returns, not from the Home's return value, so step 3 tests the safety exit at that layer.
- **Teardown order**, which `teardownActive` gains: cancel the leg, join its stream, `depart()` (it must return `detached` or `closed`, else it is an internal fault as in the shell), close the leg's MCP clients and work, retire the owner, and only then close the Home's shared database, last.

### 7. Authority, workspace and what a hosted workflow may do

- **Unattended, as in the shell.** A hosted workflow's tools are exactly what its definition and the workflow host grant; `run_command` is allowlist-only with no card and no remembered grant; `--allow-fs-root` does not exist for a workflow ([ADR-0105](0105-filesystem-roots-are-invocation-grants-not-project-authority.md)); a chat's filesystem grants are not inherited. The run's filesystem root is the one `relavium run` would use from the Home's own working directory.
- **A run belongs to the workspace it was started in.** The Home starts workflows only from its own project's catalog. An answer or resume for a run whose recorded `project_root` is another directory is refused with the fixed remedy (open the Home there), exactly as a session in another directory is ([home.md](../reference/cli/home.md#resume-and-continue)); the Home never re-anchors its workspace. Such runs are readable in the History browser, not actionable.
- **The entry points.** A workflow is launched from `/run` on the landing (a picker over the project's catalog) or from `r` on a workflow in the Defined tab ([ADR-0140](0140-management-browsers-the-run-drill-down-and-the-durable-run-detail.md) §2); both open the same launch form.
- **The inputs are the shell's.** The launch form asks the declared inputs through the native prompt channel and validates them with the one core validator (`resolveAndValidateWorkflowInputs`); a secret is only ever a masked field.

### 8. Not decided here, and why

- **Cancelling a run parked at a gate** (the maintainer's third ruling): not in MVP-8. A `rejected` decision continues the run, so there is no cancel for a parked run, and a new terminal-writing path on a run nobody holds would be a new D64 lease-path increment. `current.md`'s MVP sentence is reworded to "cancels chats; resumes chats and gated runs". A parked run's actions are answer or leave.
- **Several concurrent legs, a detached child process, a warm engine kept across answers, and cross-process cancel** are not built (§2; ADR-0122 §2 and ADR-0103 rule out the child and the daemon; each later change is its own ADR).
- **Keychain re-resolution of a secret input on resume** stays unbuilt (`ref` is a self-reference); the masked field re-supplies it.

### Alternatives considered

- **Supervise a child `relavium run --json`.** Rejected: ADR-0122 §2 ("never spawns `relavium <cmd>` as a child"), and a child owns the terminal.
- **Foreground only (leaving the view cancels).** Rejected by the maintainer on 2026-11-22: a long run would block the Home.
- **Keep the run in memory while it waits at a gate.** Rejected: it holds engine, MCP and timers for as long as a person takes, and it is exactly the state in which the stale-card defect arises. A durable park answered by a fresh leg is one path with one set of tests.
- **A long-lived engine for the Home.** Rejected: it fires ADR-0079's long-lived-host residual for no gain a leg-per-engine does not give.
- **Port the clack prompters.** Rejected: raw-mode ownership, ADR-0122 §7.7, and the paste-and-hotkey residual.
- **`Ctrl+C` cancels the run on the first press.** Rejected by the maintainer: one stray key would destroy a long, paid, non-resumable run.
- **Approval cards for a workflow's tools.** Rejected: it would reverse ADR-0118's unattended contract and ADR-0057's floor for workflow runs.
- **Publish a leg's ordinary outcome as the Home's exit code.** Rejected: the Home outlives runs; only the safety facts must survive it.

## Consequences

### Positive

- A person can run, watch, answer and resume from the Home without a shell, and the shell and the Home share one run core and one resume core, so they cannot drift (and the machine contract is proven unchanged).
- A pause is durable and answerable from anywhere; the Home never holds a person-shaped wait in memory, and the owed stale-card defect has no path to occur on the Home's route.
- Cancelling is deliberate and consistent with ending a session; exiting the Home can never silently kill or orphan a run.
- The same native card discipline (chords, guards, no paste answers, sanitized author text) covers every decision the Home asks.

### Negative

- **Each answer rebuilds an engine** (providers, MCP reconnection with preserved grants). A multi-gate workflow pays that once per gate. Mitigation: it is the shell's existing cost; a warm engine is a later ADR if measurement says it matters.
- **One executing leg at a time** can feel limiting. Mitigation: the refusal names the hosted run and how to open it; a second terminal can host another.
- **The refactor touches the shell's run, gate and budget paths** (a D64 lease and resume area). Mitigation: the byte-identity harness, a differential check of the three commands before and after, and a separate security sitting.
- **Raw `Ctrl+C` semantics differ from the shell's** (two presses here, a SIGINT there). Mitigation: the hint says it, and the reference tables show both; new rows are owed to the Windows evidence runbook.

### Amendment note — 2026-11-23 (MVP-8 step 3, as built; each point awaits the maintainer's ruling)

The code differs from the text of this ADR in six places. This note records what is built, not a decision; the maintainer rules on each, by a superseding note or by a change of the code.

- **§4 and [ADR-0115](0115-one-interrupt-keymap-for-the-interactive-cli.md).** A human gate's `Ctrl+N` is held to the card's lockout like an approval, because that rejection continues the run. ADR-0115 says a rejection is never delayed.
- **§6, the database.** A leg that is abandoned past the ten-second grace and the three-second settle bound leaves the shared database open instead of closing it last: closing it under a writing leg is worse than an unclosed file, which the lease expires and the next start settles.
- **§4, resume.** A resumed leg runs the MCP consent check again for a server this machine holds no grant for (the [ADR-0084](0084-consent-before-a-local-mcp-spawn.md) reading). The text says a resumed leg asks nothing new.
- **§4, the consent row.** The grant is per machine and the card says "on this machine". The text says "for this run".
- **§4, the input gate.** The text field is not built; an input gate offers `Ctrl+N` only.
- **§6, the exit wording.** The card and the reference say about thirteen seconds (ten of grace and three of settle). The text says up to ten.

### Amendment note — 2026-11-23 (MVP-8 step 5, the media-only park)

This note records what is built (HOSTLIFE-1); it changes no decision above and rewrites no text.

- **§3, "A media-only park is answered without a gate": the promise of step 2 is kept now.** `resumeRun` takes a third request form, `kind: 'media'`, which names no gate, no decision and no budget approval, and calls the engine's `resumeFromCheckpoint` with neither a gate id nor a decision (the form the engine already had for a run parked only on async media jobs, which re-attaches each job by the id the log recorded and submits nothing again). The run host's `resume` accepts it on the same single-flight path as a gate answer, so the owner, the lease, the fence and the teardown are the other resumes'. The request is refused before an engine, a key or a card exists, with fixed words, for a run that is not parked, that has a human or budget gate open, or that has no media job in flight; a run that already ended is the same clean no-op a doubled decision is; the engine refuses the same misuse on its own (`run_not_paused`, `pending_gate_requires_decision`). It adds no authority: the same filesystem scope tier, the same MCP consent check and the same budget as every other resume, from the same core.
- **The tests.** Engine: the re-attach of a parked job by a fresh engine with no gate and no decision is `m2-e2e-harness.e2e.test.ts` (*a cross-process resume RE-ATTACHES*, MJ-1), and the refusal of the same request for a run parked only on a human gate, with its lease given back and its gate still answerable, is *HOSTLIFE-1 guard* there. CLI: `run-host-media-resume.test.ts` parks a real run on an async media job through the real run core, continues it through the run host, and pins the re-attach (the job is polled by its recorded id and never submitted again), the lease (a run another process holds is refused as a gate answer is, and this process writes nothing), the refusals above, the single flight and the owner's retirement; `media-continue.test.ts` pins the question and its default.
- **§3, the lease.** The text says the lease is handed back at every re-pause, "budget and media included". For a media park the engine does not hand it back at the pause event: it keeps it while this process polls the job, and gives it back when the leg departs at the pause, which the Home's leg does at once (`shouldBreakOnPause`). The effect is the one the text describes (no lease row is left once the leg has ended parked, which the new test pins), and the continue re-takes it before it reads or writes.
- **The Home.** A parked run whose log shows media jobs in flight and no gate has the strip row `waiting for media` (the row of a run with neither a gate nor a job keeps `parked, no gate to decide`). `Enter` on it, on the Active tab's row for it, or at the run view of a leg that ended parked on it, asks `Run <first 8 characters of the id> is waiting for media jobs. Continue it here?` on the native prompt channel with **No** selected; a No, `Esc` and `Ctrl+C` change nothing and say nothing. A Yes starts the leg through the run host and shows its run view, as `/run` does. A run this Home already executes is not offered, and a run with a gate keeps its gate card. The fallback clause of the text (the Home shows the parked media run read-only) is not used.
- **The shell is unchanged.** `relavium run`, `relavium gate` and `relavium status` keep their behaviour and their advice text. A shell command that continues a media park would be a new command, which is a product decision and has not been made.

### Amendment note — 2026-11-23 (the media-only park, after its security sitting)

This note records what the sitting changed in the built behaviour of the continue above; it decides nothing new.

- **The question says what a Yes costs.** It reads `Run <id> is waiting for media jobs. Continue it here? It runs in this Home until the jobs finish, and leaving the Home cancels it.` The resumed engine marks the pause as already announced, so the leg keeps polling, holding the lease and the Home's one leg slot, and leaving the Home cancels it cooperatively: the run becomes `cancelled`, which cannot be resumed, and the paid jobs' output is never fetched. Ending a hosted continue on a leave in a way that keeps the run resumable is a follow-up the maintainer registered; it is not built here.
- **A live lease is refused early.** `runs.status` stays `paused` while a media leg polls, so another process still offers the run. The media form of `resumeRun` reads the run's lease before it asks for a secret or may start a local server, and refuses a live one with `That run is being continued by another process.` An expired lease is not a refusal. The engine's acquire remains the authority and refuses a lease taken in the gap with the holder named.
- **Two wordings.** A secret field left on this path says `Not continued: the secrets were not entered.` (the gate path's sentence names its gate and is unchanged), and a continue called without the secrets a run needs names neither a gate nor a shell command.
