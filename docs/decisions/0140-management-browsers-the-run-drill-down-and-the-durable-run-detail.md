## Context

[ADR-0122](0122-the-home-is-the-interactive-product.md) makes the Home the place a person reads their runs, agents and permissions, not only starts a chat. Phase 2.6's 2.6.G specifies the browsers (a tabbed `/workflows`, `/agents`, a `/permissions` tab, an actionable strip) and 2.6.H the stored record they read. The plan text is a year of drift old in places; the code was read on 2026-11-22 against it, and the facts that decide this ADR are:

1. **Several 2.6.H items are done or cannot be done as written.** The final totals on `run:failed` and `run:cancelled` ship (`cumulativeCostMicrocents`); the content-level identity guard ships (ADR-0083 §5); the chat persister's turn is one transaction. `run_costs.model_id` is a foreign key to the model catalog (a catalog id), but an event carries a raw provider string, so it cannot be filled "from the events"; the agent columns reference a table nothing writes. A store-level "skip a corrupt row and report" contradicts [ADR-0074](0074-durable-conservative-budget-commitments.md) §5 and [ADR-0075](0075-fail-closed-resume-on-an-unreadable-event-log.md): a damaged row fails the read loudly, and the CLI isolates the damage per run.
2. **Per-node attribution and exact per-node cost are already in the log.** Since [ADR-0076](0076-durable-per-attempt-realized-cost-ledger.md) a durable `cost:attempt_settled` event carries the node, the model, the within-chain attempt, the tokens and the exact cost of every attempt. A node's model and exact cost can be **read** from it. The authored agent and model are in the frozen workflow snapshot. A skipped node has a `node:skipped` event and a node type in the snapshot. None of it needs a column to be written.
3. **A node's tool activity is not stored anywhere.** The tool events are streamed and dropped; the node detail the plan wants ("tool activity") needs one bounded durable field.
4. **The reads are synchronous SQLite on the render thread.** The listing plans are already indexed (`idx_runs_created`, `idx_step_exec_run`, the `(run_id, seq)` tail), but there is no keyset page for runs, no tail read, no lease read, no project filter (and `project_root` has no index), and the Home's strip does an N+1 on open. A browser that pages a long history must not block the paint.
5. **There is no tab concept in the Home, and the Home controller has grown by one field and about six reset sites per overlay** (the controller is 2,207 lines; the decomposition that was meant to precede 2.6.G is paused). The permissions sheet cannot be composed under a tab as it stands (it hard-codes its chrome).
6. **Documents disagree** (the plan's `Ctrl+T` collides with the chat's reasoning toggle; "click" and `[Run]` buttons contradict the keyboard-first, mouse-off landing; "Home + chat" collides with ADR-0122 §10; the strip is "never live" while 2.6.G wants an idle refresh).

## Decision

### 1. One tab host, one screen slot

The Home gets **one `screen` slot** for the full-screen and docked screens that [ADR-0139](0139-a-workflow-run-is-hosted-inside-the-home.md) and this ADR add. It is a discriminated union of three kinds: `run-view` (introduced in MVP-8 step 3), `tab-host` (step 4) and `sheet` (the landing's `/help`, step 5). Each kind has one open function, one key route, one interrupt context, one paste gate and **one reset on every state replacement** (`closeScreen`). The six existing overlays (palette, models, effort, the permissions sheet in a chat, mention, search) are not moved: [ADR-0137](0137-permissions-is-a-sheet-and-esc-steps-back-out-of-the-full-view.md) §5 leaves them to the common-language increment, and D65 accepts the undecomposed controller. A chat's own docked sheets (`/permissions`, and `/agent` of §3) use the chat's existing sheet mechanism of ADR-0137, so they add no field to the Home controller.

The **tab host** is the screen of the three management surfaces:

```text
 Workflows │ Agents │ Permissions                       ← top tabs (Tab / Shift+Tab)
 Defined · Active · History                             ← sub-tabs of the current tab (← / →)
 Workflows › History › deploy · 3h ago › build          ← breadcrumb of the drill-down
 … rows (↑ ↓ PgUp PgDn Home End) …
 ↵ open · p pin · f filter · a all projects · Esc back
```

- **It replaces the strip and the prompt** while it is open (the body of the Home is its viewport) and is entered only from the landing (a chat in front keeps its own commands; see §8). Closing it returns to the landing, which re-reads once; a tab host opened by the bare `relavium permissions` ends that invocation with `0` instead.
- **Keys.** `Tab` and `Shift+Tab` change the top tab; `←` and `→` change the sub-tab at a list; `↑ ↓ PgUp PgDn Home End` move; `Enter` opens or drills; `Esc` and `Backspace` go back **one level**, and `Esc` at a tab's list closes the screen; `Ctrl+C` closes the screen from any depth and never arms, except the run view while a leg executes, which follows [ADR-0139](0139-a-workflow-run-is-hosted-inside-the-home.md) §5 (two presses) (a non-approval screen, [ADR-0122](0122-the-home-is-the-interactive-product.md) §7.4, [ADR-0115](0115-one-interrupt-keymap-for-the-interactive-cli.md) §1). A bare letter is an action only where no text field is open and opens a form or toggles a reversible mark (`r` run, `x` export, `p` pin, `f` filter, `a` all projects, `n` first failed node, `c` chat with this agent); an action that has an effect goes through a card with its own chord. A paste is dropped. No key is bound to `Ctrl+T` (the chat's reasoning toggle), `Ctrl+O` or `Ctrl+G` (the card chords), and nothing requires a mouse (the landing keeps mouse capture off; a click is never the only way).
- **The tab remembers its position** for the life of the Home process (the last sub-tab, drill level and focused row identity), not on disk.
- **Entry points:** the palette and typed forms `/workflows`, `/agents`, `/permissions` open the tab host at that tab; the strip rows (§6) open it at the right level; a bare `relavium permissions` on a terminal opens the Home with the Permissions tab (the sheet's old exit behaviour is kept: closing it ends that invocation with `0`). The slash set stays alias-free and takes no argument (ADR-0122 §3); the sub-tab is chosen with the keys, not an argument.
- **Geometry and parity** ([ADR-0122](0122-the-home-is-the-interactive-product.md) §7, applied to every screen below). Rows are drawn from the shared frame (`sheet-frame` and the legend builder): one `SheetLine` model rendered the same in the full-screen and the inline renderer; the tab bar, breadcrumb and legend are always on screen, the body takes the rest and pages (a `▲ N more` marker counts the rows it covers); at 80×24 the body holds eight rows (the tab bar, sub-tabs, breadcrumb, rule, message and legend are drawn inside the twelve-row card budget the permissions sheet already uses, `cardRowBudget`) and a narrower terminal truncates a label before it drops a column; below 80×24 the screen shows the one-line "enlarge" message and accepts only `Esc` and `Ctrl+C`; every state has a glyph **and** a word (colour is never alone); every untrusted string passes the sanitize floor; the exit key is last in the legend and never truncated. The new strings use the legend grammar that [ADR-0137](0137-permissions-is-a-sheet-and-esc-steps-back-out-of-the-full-view.md) §5 adopts (dim, ` · `-separated, `Ctrl+X` with a plus, the leaving key last, the verbs Close and Back). The approval vocabularies, the money notation and the muted colour are provisional for these screens (D2, D3, D6 and D8 of the common-language analysis, still with the maintainer); if the maintainer rules otherwise, the strings change in one place.

### 2. `/workflows`

- **Defined.** The project's catalog (`discoverCatalog`: valid and invalid files, the invalid ones flagged with their sanitized reason), with node count (an additive field of the catalog entry, absent for an invalid file, which has no parsed graph), tags, and the **last run's status and age scoped to this project** (a project-scoped read, `loadLatestRunPerWorkflowInProject`; the shell's `list` overlay and its JSON do not change, §4). `Enter` opens a **workflow detail** page (description, declared inputs with type, required and secret marks, node count, the three latest runs). `r` starts the launch form of ADR-0139 (inputs, then a confirmation card, then the run view). `x` exports the YAML through the `export` core behind a card that shows the destination and defaults to *No* (it refuses an existing file). Only the Home's own project is listed; the global directories keep only the existing notice.
- **Active.** One row per run the Home can see that is not finished, in three classes that never mix. (1) The leg this Home hosts: `Enter` reopens its view, and it is actionable. (2) Another process's run that is `pending` or `running`: read-only. `Enter` shows its node boundaries; there is no cross-process cancel, and the screen says so. (3) Another process's run that is `paused` at a human or budget gate **in the same project**: `Enter` opens the gate or budget card, answered by `resumeRun`. A paused run in another project, a paused media park and a run whose terminal is held in the outbox are read-only, and the row says why. This tab is the first surface that watches another process's run, which is the observer trigger of [ADR-0079](0079-cross-process-run-ownership-lease-and-fencing-token.md); the mechanism is the read-only poll below, and the observer handle stays a named follow-up. Freshness: a **poll while the screen is visible**, every 1.5 seconds, paused while a card is open or the terminal is below 80×24, coalesced, and guarded by a generation token so a late read cannot replace a newer one. The poll re-reads when **either** the Home's own in-process generation or `PRAGMA data_version` has moved. `data_version` does not change for writes made through the same connection (checked in SQLite), so the leg's own durable writes bump the in-process generation from the run store that folds its events, and the poll does not depend on another process committing. The granularity is the node boundary, and the screen says so (streamed tokens are never persisted, [ADR-0078](0078-ordered-durable-append-and-the-terminal-outbox.md)). A `running` run whose lease is missing or expired for more than one TTL is labelled `stalled`; the poll never reconciles (reconcile writes, and it stays at Home open, [home.md](../reference/cli/home.md)).
- **History.** Finished runs, most recent first, **this project's by default** with `a` to widen to every project (as `/resume` does for sessions), `f` to cycle the status filter. The list is a **keyset page** (twenty rows, cursor `(created_at, id)`, at most three pages cached, older ones evicted); the cost column is coverage-qualified through the one formatter and fetched lazily for the rows on screen, kept per run once it is terminal (a terminal run never changes). A pinned section sits above the list (§5). A run whose rows cannot be read is shown as an **unreadable run** row with its id, never hidden (the per-run isolation of `readPerRunOrDegrade`). `Enter` drills to the run.
- **Run detail.** A header (status glyph and word, workflow, short id, start, duration, token totals, qualified cost, the error summary of a failed run with its root-cause node) and the **node table**: per node the last attempt's status, the attempt count, duration, tokens and cost. The cost is the sum of the node's `cost:attempt_settled` rows; where a node has none (a media node, or a run written before [ADR-0076](0076-durable-per-attempt-realized-cost-ledger.md)), it is the node's boundary cost from `step_executions.cost_microcents`, marked `~`; where neither exists the page says `not recorded`, never `0`. The run's total minus its node rows is an `unattributed` row (a sibling's abandoned media fail-cost, for example, which no attempt row carries). The attempt count is the node's `node:started` count, and its attempt costs are grouped by the `node:started` boundaries in sequence order, because `cost:attempt_settled.attemptNumber` counts within a fallback chain and resets for each node retry. `n` jumps to the first node whose **last** attempt failed (a retried-then-successful node does not match). A step row left `running` under a finished run (a decided gate, a node killed by a failure, a parked media node) is shown as `stopped`, as `status` does. A skipped node is read from its `node:skipped` event with its reason and its type from the frozen snapshot. A run from another project can be opened here and is never actionable (ADR-0139 §7).
- **Node detail.** Status and attempts, duration, tokens, cost per attempt, the **model(s) actually used** (from `cost:attempt_settled`), the **authored agent and model** (from the frozen snapshot), the error (sanitized, bounded), the output (bounded view with scroll, through the same bounded and scrubbed renderer the final summary uses: forty lines, 4,000 characters per value, 12,000 per run), the event timeline (`Scheduled`, `Started`, `Completed` collapsed into one row), and the **tool activity** of §4. A node's **input is not shown as recorded**: it is the rendered template, can be secret-tainted ([ADR-0113](0113-secret-derived-context-keeps-provenance-at-public-sinks.md)) and no value is recorded for it (`step_executions.input_json` is never written); the page shows the authored template, sanitized, and says so.
- **Nothing here can delete, retry or edit a run.** (Retry from a node is Phase 3; the node detail is laid out so that a later action slots in. History retention is Wave 4b.)

### 3. `/agents`, the bound-agent view, `/permissions`, `/help`

- **`/agents` Defined** is the project's agent catalog; `Enter` opens an **agent detail** (system prompt head, model, provider, tool grant, temperature, reasoning effort, all read-only and sanitized); `c` starts a chat bound to that agent (the Home's chat today always binds the built-in agent). Binding a repository-defined agent is the same path as `relavium chat --agent <ref>`: its tool grant is exactly what its definition declares, and every tool call still goes through the chat's per-tool approval ([ADR-0057](0057-cli-chat-modes-and-per-tool-approval.md)); the Home adds no authority. **`/agents` Sessions** is the recent and in-progress sessions of this project, the data and the resume path of the `/resume` picker (`Enter` resumes in place with the transcript repainted); the parent-and-child tree of 2.6.G waits for child sessions to exist (2.6.N) and is recorded there.
- **The bound-agent view.** A chat command `/agent` (read-only, a docked sheet of the chat's existing sheet mechanism, [ADR-0137](0137-permissions-is-a-sheet-and-esc-steps-back-out-of-the-full-view.md), not the Home's slot) shows the agent bound to the **current** session with the fields of the agent detail plus the resolved provider and model. It belongs to the chat commands (both hosts, because a standalone `--agent` session needs it), not to the Home tree.
- **Three entry points, one rule each.** The landing's `/permissions` opens the tab host at Permissions, and closing returns to the landing. The bare `relavium permissions` opens the Home on that tab, and closing it ends the invocation with `0`. The chat's `/permissions` stays the docked sheet of [ADR-0137](0137-permissions-is-a-sheet-and-esc-steps-back-out-of-the-full-view.md); ADR-0137 §3 is amended to match.
- **The `/permissions` tab composes the ADR-0137 sheet** and does not build a second permissions screen. The sheet is split into a body (the list lines, cursor and the arm-and-confirm fold) and its chrome; the tab host frames the body with its own tab bar and legend and delegates the keys to the sheet's fold, keeping its `Esc` ladder (an armed question drops first, then the screen closes). Today the tab has two sections: **remembered commands** (withdraw only, as ADR-0137 decided: a grant can only be made on a command card) and the repository's `[chat].allowed_commands` (read-only: it pre-approves nothing and only labels a card, ADR-0118). The **domain, MCP and egress sections do not exist yet because their stores do not**: the network-grant store lands with MVP-7's web tools and MCP registration with MVP-9's config-write ADR. Each of those milestones adds its section to the tab; this ADR does not draw an empty tab for them. The in-chat `/permissions` stays the docked sheet.
- **`/help`** is a docked sheet on the shared frame, on the landing, as a `sheet` of the slot (in a chat, `/help` keeps printing its list into the transcript, as it does today): the commands of the registry for the current surface with their descriptions, and the keys of each screen taken from the same constants the reducers and the legends use (a test presses every key it names), with every use of the word "mode" qualified (the chat mode, the renderer, the startup default). A typed `/word` on the landing **never starts a chat**: a word the Home owns runs, a chat-only word answers with a notice naming where it works. The richer cheat sheet of 2.6.E stays in Wave 6.

### 4. The data contract: additive, read-derived where it can be, one optional field where it cannot

- **No new event type and no new column write for attribution.** The `agent_id`, `model_id` and `input_json` columns of `step_executions` and `run_costs.model_id` stay unwritten and are recorded as such; per-node model and cost are **read** from `cost:attempt_settled`, the authored agent and model from the frozen snapshot, a skipped node from its event. `nodeCostMicrocents` is **not added**: the exact per-node cost already exists as that fold, and an unqualified dollar figure per node is not allowed anyway ([ADR-0104](0104-unknown-provider-usage-is-durable-cost-uncertainty.md)).
- **One optional bounded field, `toolActivity`,** on the durable `node:completed` and `node:failed` events: at most fifty entries `{ toolId, ok, durationMs }` plus a `truncated` count. It is **content-free**: no summary, no arguments and no result text are stored, because a tool's result is not kept as durable content elsewhere either (the precedent of [ADR-0132](0132-the-model-can-ask-the-user-a-structured-question.md)). The aggregator pairs each `agent:tool_result` with the oldest unpaired `agent:tool_call` of the same node and tool, because the events carry no call id; an unpaired call shows as `no result recorded`. The field is optional, the two schemas are not strict, so an older binary ignores it, and no new event type is introduced ([ADR-0075](0075-fail-closed-resume-on-an-unreadable-event-log.md)). The schema, [sse-event-schema.md](../reference/contracts/sse-event-schema.md), the wire-conformance, budget-replay and usage-coverage controls and their mutation checks change together, and the tests include two parallel calls of one tool.
- **`applyDerived` gets an exhaustiveness guard.** The types it does not fold today (`node:skipped` and the others its `default` arm names) are listed as explicit no-op cases with the reason; every other `RunEvent` type must have an arm, and `default` is `assertNever`, so a new money event cannot be dropped silently.
- **Migration `0022`, additive and older-writer-safe:** a `run_pins` table (`kind` `run` or `workflow`, `project_root` (empty for a run), `ref` (the run id, or the workflow's slug within its project), pinned-at; primary key `(kind, project_root, ref)`; the fifty-row cap is checked inside the insert's `BEGIN IMMEDIATE` transaction) and the index `idx_runs_project_created` on `(project_root, created_at DESC, id DESC) WHERE deleted_at IS NULL`, matching the keyset cursor `(created_at, id)`. A project-and-status filter is served by the same index with a filter; a second index is added only if its plan test fails. Hand-written if the generator would rebuild a table, with `schema.ts` and the `meta` snapshot kept in step, a seeded-then-migrated test in the pattern of the `0016` to `0021` upgrade tests, and an older-writer insert case.
- **New reads, all additive and bounded.** Summary projections for every list read: `listRunSummaries` and `listStepSummaries` select no `workflow_definition_snapshot`, `input_json`, `output_json` or `error_json` column, and a plan test asserts it. The existing `listRuns` and `loadStepExecutions` and their callers do not change, so `list`, `status` and the other shell surfaces stay byte-identical. The blob-bearing detail reads, `loadRunDetail` and `loadStepDetail`, select one run or one node. `loadRunEventsAfter(runId, afterSeq, limit)` uses the `(run_id, seq)` index and reuses the row reader. It returns its events and `scannedThroughSeq`, the highest sequence it scanned, including the rows it skipped, and the caller advances its cursor to `scannedThroughSeq`, never to the last event returned, so a trailing row of a newer type cannot be re-read forever (a test pins a log whose tail is such a row). `loadRunLeases(runIds)` is a primary-key lookup, `loadLatestRunPerWorkflowInProject(projectRoot)` is the project-scoped overlay, and the pins store is the one above. Every new plan is added to the perf-budget test.
- **What stays as it is.** A damaged event row still fails a single-run read loudly (`logs <id>`, `gate list <id>`) and is isolated per run in listings; there is no store-level skip-and-report. There is no retention or delete (Wave 4b). The store-level gate uniqueness constraint is **not added**: the lease first, then the compare-and-append guard and the fence already close the window, and MVP-8 step 2 proves it with a two-process test.

### 5. Pins

`p` pins or unpins the run or workflow in front of it (the detail page or a row). Pinned runs appear in a section above the History list; pinned workflows sort first in Defined. Pins are global to the home database like the runs they name, survive restarts, and are capped (a fifty-first is refused with a notice). A workflow pin is keyed by its project root and slug, so a same-slug workflow in another project is not pinned, and a pinned workflow whose file is gone shows `not in catalog` until it is unpinned; a run pin is keyed by its run id. A pin never changes a run.

### 6. The strip becomes actionable, and it refreshes

[ADR-0122](0122-the-home-is-the-interactive-product.md) §4 made the strip actionable by direction; the rows follow. At an empty prompt `Down` focuses the first actionable row across the sections in their displayed order; `Up` and `Down` move; `Esc` or any other key leaves the focus (a key that is typing starts typing). `Enter`:

| Row | Opens |
|---|---|
| A pending human gate | the run view on the gate card, **without starting an engine** until the person answers (ADR-0139) |
| A budget-paused run (now lifted into Attention; the strip has to read the pending budget gates) | the run view on the budget card |
| A failed or recent run | the run detail in History |
| The leg this Home hosts | the run view |
| A session | the resume, as today |
| An agent | the agent detail, if it is in the catalog |
| An unreadable run | nothing; it stays a display row |

The focused row is tracked by identity (run id, session id), so a refresh never moves it, and an Enter on a row whose record vanished does nothing but a notice. **The strip re-reads on an idle tick** (every five seconds, only while the landing is in front, no card is open, the terminal is at least 80×24 and the Home's own generation or `PRAGMA data_version` moved, for the reason given for the Active tab in §2), as well as on open and on return from a chat or a screen. The row budget stays the one of ADR-0122 and MVP-3: the prompt, the keyless row, errors and notices have priority, optional rows trim first, the focused row and the active input never leave the screen, and the measured-frame acknowledgement covers the tab bar's rows too (an Enter on a row is inert until the frame holding it has been painted and measured). The attention ordering note of the reference (a recency proxy) stays.

### 7. `logs --follow` and `--failed`

Both are additive flags (new optional options; every existing invocation is byte-identical), recorded in the [ADR-0110](0110-cli-diagnostics-and-discovery-have-explicit-compatibility.md) compatibility table with their TTY, non-TTY and `--json` behaviour. `--failed` prints only the events that carry a failure (`node:failed`, `node:retrying`, `run:failed`) and the closing run line. `--follow` prints the existing log, then polls `loadRunEventsAfter` and prints each new durable event until the run is terminal **or parked at a gate** (it then says so and names the answer), at node-boundary granularity; it ends with exit `0` when it reaches the end of the log whatever the run's own outcome (a log reader reports no run's result) and keeps the existing signal exits otherwise. Under `--json` it is a pure NDJSON stream of run events, one line each, flushed per line; with `--failed` the lines are the matching run events themselves, and the closing line is the run's terminal event, not a text line.

### 8. Where these commands live, and what they do not do

- The browsers, `/help` and the forms are **Home-tree commands**: they are not offered in the standalone chat host's palette ([ADR-0122](0122-the-home-is-the-interactive-product.md) §10, which MVP-2 recorded with its measured cost). The chat's existing `/workflows` text notice stays. In the in-Home chat only `/agent` is added (a chat command).
- A screen opens only from the landing, never over a live chat or a card, so a card and a screen never compete for the keyboard; a hosted leg that parks while a chat is in front is announced by a transcript notice.
- No browser starts an effect on its own: running, exporting, answering, pinning, importing and pricing are each an explicit key and, where they write or spend, a card.

### 9. The forms for `import` and `models pricing`

Both re-host their shell cores ([ADR-0122](0122-the-home-is-the-interactive-product.md) §2) on the native prompt channel and are landing palette entries (`/import`, `/pricing`). Each core is split into `prepare` (no write: it resolves the target, validates and collects the warnings) and `commit` (the write), so the card shows exactly what the commit will do. The shell calls the same two steps with its own output, and a test per command proves that output is byte-identical.

- **`/import`:** a path field (bounded, expanded, a path prompt and not a file browser), then the core's validation shown on a card (kind, slug, the target file, a collision, any snapshot-literal warning), a default of *No*, and the write only on an explicit Yes; it refuses to overwrite and surfaces the same refusals as `relavium import`. It is a filesystem write and carries the D64 tier.
- **`/pricing`** (the palette name, described as `models pricing`): the picker chooses the model; the form's fields are generated from the same field table the shell's `models pricing` uses (input and output, cached input, the media modalities and `--clear`), so the form cannot offer less than the shell. A card shows exactly what will be recorded and that the override belongs to the operator. The pairing rule (input and output are set together or not at all, and `--clear` removes an override) is the core's and is pinned by a test in both surfaces. It is a money-floor write.
- Both keep the shell commands unchanged for scripts.

## Alternatives considered

- **Poll tail against the observer handle.** Rejected for now. A push needs a cross-process notification channel, and SQLite has none; an indexed tail every 1.5 seconds is cheap. The handle stays a named follow-up, and its trigger is met.
- **One screen slot against a field per screen.** Rejected: a field per screen repeats the six-site reset pattern the controller already carries.
- **A `toolActivity` field against a table.** A table needs a migration for each change of shape and a new read path; the optional field rides events that already exist, and older binaries ignore it.
- **`nodeCostMicrocents` against read-derivation.** It would duplicate `cost:attempt_settled`, could not carry coverage ([ADR-0104](0104-unknown-provider-usage-is-durable-cost-uncertainty.md)), and would need a second writer.
- **Store-level skip-and-report for a corrupt row.** Rejected: [ADR-0074](0074-durable-conservative-budget-commitments.md) §5 and [ADR-0075](0075-fail-closed-resume-on-an-unreadable-event-log.md) keep a damaged row loud on a single read.

## Consequences

### Positive

- The record is complete enough for a first-class drill-down with **one** optional field and one small additive migration, because attribution and exact cost were already durable.
- Every read is indexed, bounded and generation-guarded; a long history pages instead of loading, and nothing scans the table on the render path.
- One tab host and one screen slot mean the next management surface (MVP-9's providers and MCP, MVP-7's network grants) adds a tab, not another overlay field.
- The permissions tab reuses the reviewed sheet; no second permissions screen exists.
- `logs --follow` gives scripts the same live view the Active tab gives people, without a second mechanism.

### Negative

- **A new terminal sink for stored, partly secret-derived content** (node output and errors; `toolActivity` is content-free). Mitigation: only the bounded, scrubbed renderer the final summary already uses; sanitize floor; a separate security sitting.
- **`toolActivity` is a new durable field.** It holds a tool's id, its outcome and its duration, and nothing else; a mutation check pins that no text reaches the stored value.
- **A poll is not a push.** The Active tab is 1.5 seconds stale at worst and node-granular. Mitigation: said on screen; the observer handle of ADR-0079 stays a named follow-up.
- **The controller grows by one screen slot** on a file that is already large. Mitigation: one slot, one reset, one route; the decomposition stays paused and its trigger is recorded.
- **The permissions tab has two sections today.** Mitigation: stated; MVP-7 and MVP-9 add theirs when the stores exist.

### Correction note — 2026-11-23 (MVP-8 step 5, typed words)

The third bullet of the 2026-11-23 amendment note above ("a line where text follows the word is a first message and starts a chat, so no typed text is dropped") is withdrawn. The premise was false: the chat reads every line that starts with `/` as a slash command (its own line handler answers an unknown one `unknown command`), so a message cannot begin with `/`, and a chat started for such a line only creates a session that answers that. The landing answers every line that starts with `/` and never starts a chat for it, which is the literal text of §3 ("a typed `/word` on the landing never starts a chat"). The first word decides the answer, whatever follows it: a registry word is answered as before, a near miss gets its suggestion, any other lower-case word is said to be unknown by name, and any other line that starts with `/` (a path, a word with an upper-case letter) is said to be unknown as the chat says it, in printable ASCII and at most 64 characters. A line that does not start with `/` is a message.

### Maintainer ruling — 2026-11-23 (MVP-8 step 5, typed words)

The maintainer confirmed the rule of the correction note above: at the landing, a line that starts with `/` is a command line. A Home word runs, a word that only works in a chat says where it works, and any other word or path says `Unknown command: … /help lists the commands.`; it never starts a chat. A message cannot begin with `/`, in a chat or at the landing, because the chat reads every line that starts with `/` as a command.

### Amendment note — 2026-11-24 (PR #102 review)

This note records where §§2, 4 and 6 said more than the code does, and what the review changed. It reverses nothing; the phase record's [PR #102 review corrections](../roadmap/phases/phase-2.6-conversational-authoring.md#pr-102-review-corrections--2026-11-24) lists the commits and the register holds what stays open.

- **Three behaviours the text describes are not built.** (1) **§2 Defined, the workflow detail page.** `Enter` on a Defined row opens nothing; it says `No workflow detail yet. r runs it, x exports it, p pins it.` The page (description, declared inputs with their marks, node count, the three latest runs) needs a bounded read of the workflow's detail and of its latest runs through the Defined port, and a page on the `tab-host` slot. (2) **§2 Active, `Enter` on another process's `pending` or `running` run shows its node boundaries.** `Enter` says why the row is read-only; the node boundary is only the granularity the tab states. (3) **§6, a strip row for an agent opens the agent detail.** An agent row stays a display row and opens nothing (the table in [home.md](../reference/cli/home.md) says so). Each is registered; (2) already was.
- **§2 Active, one snapshot and focus by identity.** The Active read takes its three status pages, the leases and the gate reads in one read transaction, so another process's run is not listed twice or missing for a tick; the poll pauses while a native question is open as well as a card; an Active run that leaves the list no longer hands `Enter` to the row that took its place; and a full page whose last row has no usable keyset position is shown as it is, where it used to end the whole read with `invalid_cursor`.
- **§4, the reads are bounded.** `listStepSummaries` returns at most `MAX_RUN_STEP_SUMMARIES` rows (5,000, ten times what the writer's own ceiling of 500 dispatches allows), the first ones in execution order. `loadRunEventsAfter` stops after `MAX_RUN_TAIL_SCAN_ROWS` scanned rows (50,000), readable or not; its statement that it keeps scanning until it holds `limit` events or the log ends is read with that cap, and a caller that must reach the end continues until `scannedThroughSeq` stops moving. [database-schema.md](../reference/shared-core/database-schema.md) owns both.
- **§4, `toolActivity`.** The schema refuses the two combinations no writer produces: an entry with no recorded result that is `ok`, and one that carries a `durationMs` (zero included). In a workflow node only an unknown tool and invalid arguments are handed back to the model as a refused call; a grant, policy or user denial ends the node and is an unpaired call. [sse-event-schema.md](../reference/contracts/sse-event-schema.md) owns the table.
- **§2, the node page's output.** The member-name rule shared with the final summary is an exact list of credential names (a listed name masks a string or a number whole, never a boolean or a null), and a value is cut without splitting a character. The node page also scrubs its emitted text once more as a whole; that second pass can corrupt indented JSON where a header- or query-named member holds an object or an array, and the summary has no such pass. Keeping or removing it is the maintainer's decision, registered.
