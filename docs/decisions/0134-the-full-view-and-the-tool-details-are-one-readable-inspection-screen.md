# ADR-0134: The full view and the tool details are one readable inspection screen

- **Status**: Accepted — 2026-11-17, by the maintainer, who found the full view (`[v]`) and the tool details (`/details`) hard to use after a manual test and chose, from the options below, to keep the approval answer keys as Ctrl chords and to keep the tool-call list and detail screens and rebuild them. Implemented on `development`; its four review rounds and four separate security sittings are recorded in the [phase register](../roadmap/phases/phase-2.6-conversational-authoring.md#the-full-view-and-the-tool-details--adr-0134-2026-11-17) and in the amendments below.
- **Date**: 2026-11-17
- **Amends**: [ADR-0120](0120-the-toolbelt-grows-and-a-tool-call-shows-what-it-does.md) (the full view's layout, keys and row budget) and [ADR-0129](0129-the-approval-card-is-docked-bounded-and-says-only-what-matters.md) §1, whose sentence "the details and call-list screens keep the key set and behaviour ADR-0120 gave them" no longer holds. The card, its keys, its guard and its words do not change.
- **Related**: [ADR-0130](0130-chat-modes-ask-prompts-plan-reads-accept-edits-accepts.md), [ADR-0132](0132-the-model-can-ask-the-user-a-structured-question.md)

## Context

The card is where a change is decided; the full view is where it is read, and `/details` is where a finished call is looked up. Both were built for the safety rules (every byte inspectable, a frame that is measured, a page that is copied exactly) and not for reading. A probe through the real host at 80×24 showed:

- the full view's body was **9 rows**, 8 of them the first four unchanged lines each drawn twice (`=before 1` and `=1`), so the first page showed **none of five changes**; it opened on line 1 while the card opens on the change;
- `↓` and `PgDn` both jumped a page; there was no line scroll, no `End`, no way to the next change and no sign of position;
- fifteen rows of chrome (`tool`, `action`, `endings lf → lf`, `0 masked spans`, `Inspection requirements met.`, two legend rows that wrapped), no colour;
- `/details` opened on the **oldest** call, listed `edit_file — success` with no target (three edits could not be told apart), and showed a call without a preview `0 changed lines · 0 masked spans`, `field name` / `field value` rows and keys that did nothing for it.

Other terminal coding agents were read from their source and public records on 2026-11-17. None has a screen that lists a session's tool calls: they fold calls into transcript rows and expand them in place. The best of their full-screen diffs is a pager with a position percentage, line and page scrolling, `Home`/`End`, and the approval left pending underneath; one jumps from change to change. Those that draw a diff in the prompt use a line-number gutter, `+`/`-` marks, tinted rows and three or four lines of context. One lets a command that truncation hid be approved (a reported defect): the rule that a partial view earns no session-wide grant is not common.

## Decision

### 1. One screen, two doors

The full view (from the card, `[v]`) and the tool details (from the list, Enter) draw **one** screen, `ReviewScreen`. The card, the call list's data and every key that answers an approval are as before. The details list is a separate, simpler screen (§6).

### 2. The listing

A review document is a list of source lines; the full view lists **one row per unchanged line**. The `=before N` copy of a context line is left out when no mask touches it (`fullSkip`): its twin is byte-identical, so nothing is lost; a masked before copy stays listed, because that is where its mask is inspected. Rows use the card's format — a gutter number, `+`/`-`, dim context, colour where it is on — and a call's fields are a name with its value indented below. Every projection rule is unchanged: escape notation, `<MASK:…>` tokens, the ending token rule of ADR-0129 §4, source-backed rows, the masked companion that copy uses.

### 3. Chrome, counted once

Header (the screen's name, the tool's identity and the counts — `+3 −2 · 205 bytes · 0 masked values` for a change; a call without a diff shows the masked count only when it is not zero — on one row when they fit; when they do not, the title keeps the counts and the identity goes on one row under it, and on a row each only if even that does not fit — the identity is never shortened), a target row (the target while the body is scrolled away from it; a blank row at the top, where the body's own first row is the target, so it is not said twice and the body keeps its height), the warnings that apply, the body, a status rule, a message row (always one row, blank when there is no message) and a search row while the search box is open, the navigation legend (the card's `[key] words` style, keys coloured; a key that can never apply — `Tab` without a change, `r` without a mask, `c` without a clipboard — is not listed; movement and inspection each on their own row), the answer rows (the way back, `[b] Back to the card`, sits with them), and one closing note (the protected-path sentence on an approval, `Esc closes · viewing never executes a tool` on details). One row stays empty under the screen. The status rule is fitted to the width (its change counts shorten and then give way before a mode a person must not forget). `fullChrome` returns the chrome and its row count; the page is projected into exactly the rows left, so the model that sizes the body and the view that draws the rest cannot disagree. At 80×24 the body is 14–17 rows instead of 9.

- **The lock names its cause.** `Allow is locked until the whole target has been on screen — press Home.` / `… until every masked value has been revealed — press [r], then scroll over each.` A met requirement prints nothing. `reviewInspected` is now defined as "`inspectionPending` owes nothing", so the sentence and the keys share one definition.
- **The status rule** says how far down the page reaches and which changed lines are **not** on it, by side (`changed lines off this page: 2 above, 4 below`), plus the two modes a person must not forget: `masked values revealed (view only)` and `code points`.
- **The answer rows are the card's two rows**, without the keys only the card has (`[Ctrl+R]`, `[v]`); the question for the session-wide grant is the card's two rows too, so the row count never changes while it waits.

### 4. Where it opens

From the card the full view opens **on the first change with up to three unchanged lines above it**, as the card does. It opens on the **top** instead when the card had to shorten the target (the target is read first) or when field rows come before the diff (they are the call's identity). Details open on the top: the result summary is the first thing read.

### 5. Keys

`↑`/`↓` and `k`/`j` move one listed line; `PgUp`/`PgDn` and `Space` a page (a page cut inside a long line continues there); `Home`/`End` go to the ends; `Tab`/`Shift+Tab` go to the next or previous **change** — a run of changed lines, joined to the next run when no more than six unchanged lines lie between (the unified diff's hunk rule) and at most about 40 listed lines long — and, inside a change longer than a page, to the next page that shows a changed line not yet seen: they take the nearer of the next change's opening and the landing for the nearest changed line the page does not draw — forwards the page that opens on it, backwards the page that **ends** on it (a page up from just below it) — so no changed line is stepped over. Scrolling down stops at the last page that begins on a line, so the screen ends on the document's last row (a page of whole lines can be shorter than the screen when wrapped lines do not fit it exactly, and after `p`, `r`, a search jump or a resize). `/` search, `r` reveal (offered, and working, only when something is masked), `c` copy and `b` back are as before. `p` shows **every non-ASCII character as its code point** (`<U+0131>`) and says so (`[p] Unicode codes` / `[p] back to text`, and `Unicode code points` in the status rule); printable ASCII stays readable, and a tab (`<TAB>`), a trailing space (`<SP>`), a control, an invisible character and `<` are the same tokens in both views. The maintainer chose this on 2026-11-17 after seeing the earlier all-numeric view, which made `Merhaba` read `<U+004D><U+0065>…`: everything that can imitate or hide another character is still numbered, and the ADR-0120 requirement of a bounded numeric inspection for ambiguous-width and unsupported characters is met by the same rule. Brackets were not used for changes: on some keyboard layouts they need AltGr. None of these answers anything; a navigation key that acts is not a foreign key. The 4,096-position back stack is gone: geometry replaces it.

The details view with no approval pending is unchanged: `Esc` closes it. *(Implemented 2026-11-21, MVP-4 step 6; while a session-wide or remember question waits on the full view its second row reads `Any other key cancels · Esc back · Ctrl+C stops the turn` (a command's: `Enter confirms · any other key cancels · Esc back · Ctrl+C stops the turn`), because the card's `Esc stops the turn` would be false there. [ADR-0137](0137-permissions-is-a-sheet-and-esc-steps-back-out-of-the-full-view.md) owns the detail.)*

### 6. The tool-call list

Oldest first, the newest at the bottom, opening on the **newest**. A row is a mark (`✓`, `✗ failed`, `⊘ denied`, `? outcome unknown`, `… running`), the tool, what it touched, `+a −r`; never what it returned — a result can carry secrets and is read in the details view, through the masks. Every model-named string is escaped before it is drawn. `Home`/`End`/`PgUp`/`PgDn` move the selection; the status row says `call 3 of 12` and how many are above or below.

### 7. What does not change, and why it still holds

- Inspection (`required` ranges, the target, `acknowledgeToolReview`) is untouched: it reads the rows the page emitted, whatever the layout.
- `reviewOffersAlways` is page-based and counts changed lines **above and below** the page, so opening on the change can never withhold less than before; a hidden changed line still earns no session-wide grant, on the card and here.
- The measured frame acknowledgement still gates every answer; the terminal floor is still 80×24; a frame is never as tall as the terminal.
- **A row is measured as the string the renderer measures.** The projection fits a row to its page by the width of the WHOLE row (`string-width`, the function Ink uses), not by the sum of the tokens' widths: tokens can join into a wider cluster (a digit and a combining enclosing keycap are two cells, not one plus none). To keep the cost near linear it grows a row by the sum of its tokens' own widths (a close estimate: exact for most text, short for a keycap and long for some emoji and jamo sequences), measures the row as the string it is and, when that is too wide, finds a prefix that fits by halving — each probe one whole-row measure, verified, because width is not monotone in the prefix so the prefix found is always one that fits but not always the longest — so the cost is the row times its logarithm; a row holds at most three tokens per column (zero-width material goes on in the next row, every byte still drawn once) and never ends between a base character and the zero-width mark that follows it. The full view's body rows and the card's title rows are not truncated by the renderer either: a row wider than its page would wrap — one wrapped row uses the spare row and is drawn whole, a second makes the frame taller than the terminal and the measured acknowledgement refuses it — instead of cutting bytes the page reports as shown (see Amendments). What a real terminal draws for a cluster `string-width` counts differently is the standing ADR-0069 assumption, which the measured acknowledgement cannot see.
- Copy is still the masked companion of the exact page drawn.

### 8. Not done

Syntax highlighting (a new dependency; ADR), word-level highlight, a side-by-side view, and a readable leading-tab glyph (`<TAB>` stays — it is a safety notation, and changing it is its own decision). The answer keys stay Ctrl chords (ADR-0129 note 12): the maintainer was shown that the exposure is the composer's type-ahead, not the card's content, and that peers who kept bare letters rely on holding the prompt, which our typeahead window already does.

## Consequences

- `ToolReviewState` loses `previous`; `ReviewPage` gains `labels`, the above/below split of the hidden changes, `position`, `columns` and `rowLimit`; `ReviewDocument` gains the full-view skip set and `changeStarts`. Everything is additive but the removed field.
- New pure modules: `tool-review-scroll.ts` (motion) and `tool-review-screen.ts` (words, chrome, call list). The view draws what they return.
- Tests that pinned the old layout were rewritten to the new contract; new tests pin the listing's losslessness, every motion, the chrome's arithmetic and the frame's height.
- Docs: `chat-session.md` and the home reference's note that the same screens serve the Home chat.

## Alternatives considered

- **Expand tool calls inside the transcript** (the peers' way): a larger change to the transcript's rendering and focus model, and it loses the one screen that lists a session's calls. Rejected for now.
- **Keep the back stack**: it only knew pages it had itself produced, so a line scroll or a jump could not be undone by it.
- **Pad the screen to the full terminal height**: a frame as tall as the terminal makes the renderer clear and redraw on every update.
- **Show every unchanged line twice, as before**: no information it carried was needed for an unmasked line.

## Amendments — 2026-11-17 (review round and separate security sitting)

1. **A row wider than its page hid bytes (security sitting F1, high; and the same cause on the card's title rows, present before this ADR).** The first version of the full view drew body rows with the renderer's `truncate-end`, and the projection fitted a row by summing token widths. A digit, `#` or `*` followed by U+20E3 measures two cells as a cluster but one as a sum, so a model-written row the page called 78 columns could be up to twice as wide; the renderer cut it and added `…`, the cut bytes were never written, and `visibleSource`, `hiddenChanges` and the locks went on counting them as shown. The reproductions opened the mask lock and the shortened-target lock and offered `[Ctrl+G]` over content that was never drawn. Fixed at the root (§7's measurement rule), and the full view's body rows and the card's title rows no longer truncate. A test now projects adversarial strings (keycaps, flags, skin tones, ZWJ sequences, combining marks) and requires every row to fit by the whole-string measure.
2. **Reserved rows (review mediums M1, M2).** The body's height used to change when a message appeared or when the cursor left the first line (the target row came and went), while a motion's limit was taken from the page drawn before it: `End` could leave the last row undrawn, and a lingering message could make `↓`/`PgDn`/`End` do nothing. The message row is now always drawn and a row is always kept for the target, so the body does not move.
3. **Search skips unlisted copies (review medium M3).** A match in an unchanged line was found first in its skipped `=before` copy, parking the cursor on a line the screen does not draw; it is now found in the listed twin.
4. **Smaller corrections**: a change spans about 40 listed lines at most (`CHANGE_SPAN_LINES`; 41 counting its first line), so `Tab` keeps reaching a chain of edits; a step down inside a long last line no longer jumps back to its start; the empty-list sentence fits 80 columns; call-list targets are cut in the middle so a name survives; the lock sentence for a shortened target that hides a masked value names `[r]`; the full view's locked answer row points to the warning instead of repeating it; `b` leaves the code-point view off; `inspectionPending` is a binary search and is computed once per frame.
5. **The F1 fix was quadratic (second security sitting M1, second review round M1 — both medium).** Measuring `displayWidth(text + token)` for every token cost O(row²): a line of 65,536 combining marks froze one page for 65 seconds (a prompt-injected write or `/details` could stall the approval UI, an availability problem, not a consent bypass), and any row with one non-ASCII character lost `string-width`'s ASCII fast path (Turkish text at 300×80: 533 ms against 4 ms before). The row builder now grows a row by the sum of its tokens' widths, measures it as a whole and, if it is too wide, finds the longest fitting prefix (see §7), holds at most three tokens per column per row, and ends a row before a base character whose mark comes next; `escapedFit` follows the same rules. Measured on the same probes: 8,000 marks 3 ms (was 1,003 ms), Turkish 300×80 7 ms. Tests bound the time of a 65,536-mark line and pin the cluster rule.
6. **`b` carried the full view's message and details opened on a skipped copy (second review round).** `b` now clears the message (a stale `No later change` showed on the card and made a full call list as tall as the terminal); the call list draws no message row; details open on the first listed line; the full view's target row ends with `…` when the target took more than one title row on the card; `[PgUp/PgDn]` is in the list's hint; `inspectionPending` is computed once per frame; the 200-row body cap is one constant.
7. **Third round (second review round's findings, third security sitting).** (a) The giving-back loop was still quadratic for keycap rows (a keycap sums to one cell and measures two, so a full row gave back about a row's worth of tokens, each re-measuring the row): a page of keycap lines took 1.9 s at 300×80 and every key 6 s or more at 300×80. The loop is now a halving search over the prefix length, verified by the measure it ends on, in the row builder and in `escapedFit`; the last page of a document is computed once per geometry. Measured: keycap page at 300×80 75 ms (was 1.9 s), keycap-plus-marks 95 ms (was 2.7 s), a key in the real host 53–62 ms at 200×60 (was 2.5 s). (b) The rule that keeps a base with its mark is applied only if the shorter row still fits (width is not monotone: a modifier can narrow a cluster, so giving the base back could widen the row by one cell). (c) **The first page did not show the change for wrapped text.** The card and the full view opened on three context LINES; for prose or Markdown (one line is many rows) three lines can fill the whole page, so the change was not on screen, and `Tab` then said `No later change` while the status rule counted changed lines below. Context is now also counted in ROWS — at most a third of the page, never less than three rows — for the card, the full view's opening and `Tab`'s landing; and when no further change opens elsewhere but changed lines remain off the page, `Tab`/`Shift+Tab` page toward them instead of claiming there are none. (d) A key that cannot move now takes down a note that is no longer true; a refusal is explained again once a move has taken the note down; the rows of a wrapped target after the first are indented under its label instead of repeating it; the target lock sentence says `press Home and page through it (PgDn)`.
8. **Fourth round (review round 4, fourth security sitting).** (a) **`Tab` was O(document) (sitting M1, medium, availability):** the "context in rows" change made `changeJump` project three context lines for every change it passed; on an 8 MiB keycap document one `Tab` froze the UI 13–16 s and on a 200,000-line diff 0.8 s. `changeJump` now finds its change by halving (the landing line strictly increases with the change's index), `contextStartLine` measures a line only up to the rows the budget has left, and the last page is memoised: a `Tab` in the real host is 27 ms on that document (16,169 ms before) and about 1 ms on the 200,000-line diff. (b) **`Tab` stepped over part of a long change (review M1, sitting L3):** the page-down fallback ran only after the LAST change, so in the middle of a document the off-page part of a merged change was skipped (the status rule disclosed it; `↓`/`PgDn` reached it; no lock depended on it). `Tab` and `Shift+Tab` now land on the nearer of the next change's opening and the landing for the nearest changed line the page does not draw, so every changed line appears on some landing. Going backwards that landing is the page that ENDS on the line (`pageUp` from the line below it), not the page that opens its context: opening the line's context crawled backward through a long contiguous run (a new file of 100 added lines). (c) A key that only takes a stale note down counts as typing for the typeahead guard again (one key per note had escaped it); `escapedFit`'s cluster rule keeps a base only when the shorter cut still fits and drops a lone zero-width tail mark.
9. **After the push (SonarCloud, 2026-11-17).** The key legend's splitter, a regular expression, backtracked quadratically on a long run of `[` (100,000 took 3.4 s; a row is bounded by the terminal's width, so a real row costs well under a millisecond). It is now `keyLabelParts`, one pass, equal to the expression on every string of up to six pieces and about a millisecond on 100,000 `[`. Nothing else in this ADR changed: the other fixes of that round are style (nested ternaries, `.at()`, row keys that do not depend on position) and are recorded in the deferred-tasks entry with the seven complexity findings left open.
